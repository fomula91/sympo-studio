# SYMPO STUDIO

**제약 심포지엄 마이크로사이트를 만들고 운영하는 스튜디오.**

운영자가 콘솔에서 행사를 관리하고, 에디터에서 아젠다·자료·참여·테마를 편집하면 참가자용 마이크로사이트에 즉시 반영된다.

**라이브 데모** — <https://sympo.superjacob.com> · 프로젝트 소개는 [/intro](https://sympo.superjacob.com/intro)

> 제약 심포지엄 마이크로사이트를 **만들고 현장에서 운영하는 일**을 했습니다. 대행사에서 아젠다·이미지·강의자료를 받아 사이트에 올리고, 행사 당일에는 태블릿을 세팅하고 운영했습니다.
>
> 이 프로젝트는 그때 관찰한 문제를 처음부터 다시 설계한 개인 작업입니다. 기획·설계·구현 전부 개인 작업이며, 등장하는 브랜드·인물·소속기관·의약품·행사장은 **모두 가상**입니다.

---

## 문제

제약 심포지엄은 회차마다 새 마이크로사이트가 필요하다. 연 수십 회씩 열리는데, 매번 같은 일이 반복됐다.

겪은 문제는 **성격이 다른 두 층**이었다. 하나는 도구로 풀리는 것이었고, 다른 하나는 도구를 바꿔도 풀리지 않았다.

### 1층 — 제작·운영 효율

전달 과정에서 정보가 새고, 그 자리를 사람의 왕복이 메웠다.

- **브랜드 컬러가 이미지로만 온다** — 정확한 색상 값이 전달되지 않는 경우가 많았다. 브랜드 대표 이미지를 보고 **눈으로 맞춰 입력**했다. 아무 색이나 쓸 수는 없고 그 이미지의 컬러셋에 맞춰야 했으며, 재사용할 프리셋이 없어 회차마다 반복됐다. 문제는 입력 횟수가 아니라 **입력값이 애초에 없다는 것**이었다.
- **아젠다 변경이 이미지 왕복이다** — 연자 정보가 바뀌면 새 이미지를 다시 받아 다시 올렸다. 내 쪽 비용은 디자인 재작업이 아니라 **받아서 다시 올리는 왕복**이었다.
- **URL을 돌려쓰면 공유 캐시가 오염된다** — 편의상 이벤트 URL을 재사용했더니 카카오톡 공유 캐시에 **이전 회차 정보가 미리보기로** 남았다. 조치는 어렵지 않았지만, 회차가 고유한 주소를 갖지 않는 한 계속 생기는 종류의 일이었다.
- **강의자료는 행사가 시작된 뒤에 도착한다** — 연자가 제때 오지 않아 자료 업로드가 늦어졌다. 자료를 올리는 곳은 사무실 책상이 아니라 **행사가 진행 중인 현장**이었다.
- **현장 네트워크를 신뢰할 수 없다** — 인터넷이 끊기는 일이 있었다. 참가자 수십·수백 명이 같은 행사장 와이파이를 쓰기 때문에, **네트워크가 가장 느려지는 시점이 참여 기능을 써야 하는 시점**이다.

이 층의 공통점은 하나다. **운영에 필요한 정보가 데이터가 아니라 이미지와 문자열 안에 갇혀 있었다.**

### 2층 — 참여율, 도구를 바꿔도 풀리지 않은 것

Q&A와 설문은 처음에 외부 링크와 QR로 붙어 있었다. 참가자가 페이지를 떠나는 것이 원인이라고 보고 **프로덕트 안에서 직접 하도록 바꿨다.** 결과는 절반의 성공이었다.

- **Q&A는 올랐다.** 다만 즉시가 아니라 회차가 쌓이면서 올랐다. 참가자들이 반복 노출로 익숙해진 것이다.
- **설문은 거의 그대로였다.** 참가자 나잇대가 고령이라서다. 응답률을 올려보려 **다른 플랫폼으로 갈아타기도 했지만 효과가 없었다.**
- 결국 **현장에서 사람이 안내해 드리는 것**이 유일하게 통한 방법이었다.

즉 **이탈 지점을 없애는 것은 필요조건이었지 충분조건이 아니었다.** 그리고 플랫폼 교체로는 풀리지 않는다는 것을 직접 확인했다. 남은 접근은 인터페이스인데, 그건 그때 시도해 보지 못했다.

> **이 프로젝트가 도전하는 지점이 여기다 — 현장에서 사람이 하던 안내를 UI가 대신할 수 있는가.**

## 관찰과 가설을 갈라 둡니다

포트폴리오에서 가장 위험한 건 그럴듯하게 지어낸 문제 정의라고 생각합니다. 그래서 근거의 층을 표시해 둡니다.

- **관찰** — 위 `## 문제`의 내용. 직접 겪은 것이며 원자료는 [`llm-wiki/Reference/field-experience.md`](llm-wiki/Reference/field-experience.md)에 있습니다.
- **가설(검증 안 됨)** — ① **운영자가 직접 편집하면 전달 왕복이 사라진다.** 저는 중간 전달자였고, 운영자가 직접 쓰는 상황을 관찰한 적은 없습니다. ② **UI 개선이 고령 사용자의 응답률을 올린다.** 아직 근거가 없습니다.

**이 도구가 없애려는 중간 역할은 제가 하던 일입니다.** 대행사와 운영자 사이에서 자료를 받아 옮기는 일이 병목이었다면, 운영자가 직접 편집하는 것이 맞다고 판단했습니다. 판단의 근거는 [`ADR 0004`](llm-wiki/Decisions/0004-problem-redefinition.md)에 적어두었습니다.

## 설계 판단

| 무엇을 | Before | After | 왜 |
|---|---|---|---|
| **행사 식별** | 제목 한 문자열 + URL 재사용 | 행사명·일시·장소·좌장 필드 분해 + **회차별 고유 슬러그** | 회차마다 주소가 달라져 공유 캐시가 이전 회차를 물고 있을 수 없다. 분해된 필드는 리마인더·장소 참조의 소스가 된다 |
| **아젠다** | 이미지 슬라이드 | 구조화된 세션 레코드 + 드래그 정렬 | 이미지를 다시 받아 다시 올리는 **왕복이 사라진다.** 세션 라이브러리에서 가져다 쓸 수 있다 |
| **테마** | 이미지 보고 눈으로 맞춘 HEX | 브랜드 프리셋 선택 → OKLCH 파생 | `{hue, chroma}` 두 값에서 배경·표면·경계·본문·브랜드색을 전부 유도한다. **다만 이건 절반의 해법이다 — 아래 한계 참조** |
| **접근성** | 검증 수단 없음 | WCAG 대비비를 **저장 게이트**로 | 색을 눈으로 맞추던 시절엔 그 색이 읽히는지 확인할 방법이 없었다. 사고가 난 적은 없지만 안 났다는 보장도 없었다 |
| **참여** | 외부 링크 + QR | 페이지 내에서 완결 | 이탈 지점을 없앤다. **실무에서 여기까지는 해봤고, 설문 응답률은 오르지 않았다.** 그 다음이 이 프로젝트의 과제다 |
| **프리뷰** | 별도 구현 | 참가자 화면과 **같은 컴포넌트** | "프리뷰와 실물이 다르다"를 구조적으로 불가능하게 만든다 |
| **뷰어** | — | 모바일·태블릿 동시 렌더 | 현장에서 참가자에게 보여주는 화면이 태블릿이었다. 두 폭을 나란히 확인해야 세팅 전에 문제를 잡는다 |

마지막에서 두 번째 항목이 이 프로젝트에서 가장 마음에 드는 결정이다. 에디터의 라이브 프리뷰와 참가자 뷰어가 `Microsite` 하나를 공유하기 때문에, 두 화면이 어긋날 방법이 없다.

## 다시 만들면서 바꾼 것

실무판에는 없었지만 이번에 넣은 것:

- **운영 리포트 층** — 세션별 열람률, 설문 응답률, 행사 셋업 소요시간. 도구가 스스로를 측정하지 않으면 개선됐는지 알 수 없다. 참가자 공개 리포트(`/[slug]/report`)는 **실측 데이터로 돈다.**
- **대비비 검증의 게이트화** — 원래는 색상 검증이라는 개념 자체가 없었다.
- **세션 라이브러리** — 반복 등장하는 연자·세션을 매번 새로 입력하지 않도록.
- **발행 상태와 행사 시점의 분리** — 처음엔 상태 6종이 한 축에 섞여 있었는데, `초안·검수대기·공개·보관`은 **사람이 바꾸는 것**이고 `예정·진행중·종료`는 **날짜에서 파생되는 것**이라 성격이 달랐다. 두 축으로 갈라 파생 쪽은 저장하지 않는다 — 저장하면 자정마다 틀려진다.

> ⚠️ 리포트 화면의 수치는 **샘플 데이터**입니다. 실측값이 아니며, "어떤 지표를 봐야 하는가"에 대한 판단을 보여주기 위한 화면입니다.

## 화면

운영자가 쓰는 스튜디오와 참가자가 여는 공개 페이지가 나뉜다.

| 운영자 | 하는 일 | 서버 |
|---|---|---|
| **콘솔** `/console` | 행사 목록·검색·상태 필터·선택 모드 벌크 액션 | ⚠️ 목업 |
| **에디터** `/events/[id]/edit` | 기본 정보 / 아젠다 / 자료 / 참여 / 테마 5개 섹션 + 라이브 프리뷰 (모바일·태블릿) | ⚠️ 목업 |
| **뷰어** | 참가자 화면을 모바일·태블릿 동시 렌더해 반응형 검증 | ⚠️ 목업 |
| **리포트** `/report` | 도구 자체의 제작 효율 지표 (샘플) | ⚠️ 목업 |

| 참가자 | 하는 일 | 서버 |
|---|---|---|
| **마이크로사이트** `/[slug]` | 아젠다·강의자료 PDF 뷰어·Q&A·설문·수료증. 발행 상태가 `공개`일 때만 열린다 | ✅ 실제 D1 |
| **공개 리포트** `/[slug]/report` | 그 행사의 **실측** 방문·열람 집계 | ✅ 실제 D1 |

⚠️ **운영자 스튜디오는 아직 서버에 연결돼 있지 않다.** 화면과 상호작용은 전부 동작하지만 편집 결과가 로컬 상태에만 남는다 — 자세한 것은 아래 「알고 있는 한계」. 참가자가 보는 쪽은 실제 D1을 읽고 쓴다.

에디터 프리뷰와 참가자 화면은 **같은 `Microsite` 컴포넌트**를 쓴다 — 프리뷰가 실물과 어긋날 수 없다.

## 기술 선택

**Next.js 16 (App Router) · React 19 · TypeScript**

런타임 의존성은 **7개**다 — `next`·`react`·`react-dom`에 `culori`(대비비 판정), `pdf-lib`·`@pdf-lib/fontkit`(수료증 생성), `pdfjs-dist`(강의자료 뷰어)가 붙었다. **넷 다 클라이언트에서 하는 일**을 위한 것이고, 서버 쪽에는 어댑터 외에 아무것도 추가하지 않았다. 의존성을 세는 이유는 이 프로젝트가 오래 살아 있어야 해서다 — 적을수록 2년 뒤에도 `npm install`이 그냥 된다.

백엔드는 **Cloudflare 단일 벤더**다. Workers + D1(이벤트·아젠다·자료·Q&A·설문·로그·계정·세션) + R2(강의자료 원본) + Cron(자정 시드 리셋·R2 고아 정리·만료 세션 정리)이 전부 살아 있다. API는 **18개 라우트**이고, 참가자 경로는 무인증(제품이 그래야 한다), 운영자 쓰기 경로는 이벤트 소유권 검사를 지난다.

원칙은 **"저장·조회는 서버, 렌더링·생성은 클라이언트"** — 무료 티어가 인색한 자원은 저장 공간이 아니라 CPU 시간이기 때문이다. 강의자료 PDF는 **브라우저에서 canvas로 렌더**하고(서버는 바이트를 서명 URL로 넘길 뿐 열어보지 않는다 — 페이지 수 추출도, 썸네일도, 워터마크도 없다), 수료증도 클라이언트에서 생성한다. 근거는 [`ADR 0002`](llm-wiki/Decisions/0002-cloudflare-free-tier-stack.md).

**배포는 자동이다.** main에 머지되면 GitHub Actions가 `lint → test → build`를 게이트로 통과시킨 뒤 Workers에 배포한다. 다만 **원격 DB 마이그레이션은 일부러 자동화하지 않았다** — 배포는 되돌릴 수 있지만 마이그레이션은 아니다.

트레이드오프로 남겨둔 것:

- **인라인 스타일 + OKLCH 리터럴** — 디자인 프로토타입 충실도를 우선한 결과다. hover를 CSS 헬퍼 클래스로 우회해야 하는 비용이 있다. Microsite는 테마가 런타임 파생값이라 CSS 변수로, 스튜디오 셸은 Tailwind로 나누는 것이 정리 방향이다.
- **어댑터 마찰** — Cloudflare Workers 배포는 Next.js 네이티브보다 손이 간다. 그럼에도 고른 이유는 무료 티어의 상업적 사용 제한이 없고 비활성 pause가 없다는 것 — 포트폴리오 링크가 몇 달 뒤에 죽어 있는 시나리오를 피하는 것이 최우선이었다.

## 알고 있는 한계

포트폴리오이므로 미완인 지점도 적어둔다. **여기 적힌 것은 전부 [`llm-wiki/Next-Tasks.md`](llm-wiki/Next-Tasks.md)에 과제로 등록돼 있다** — 무엇을 할지, 왜 해야 하는지, 무엇을 확인해야 끝인지까지. 지금 상태 요약은 [`llm-wiki/Summaries/Status.md`](llm-wiki/Summaries/Status.md)에 한 장으로 있다.

**문제를 아직 못 푼 것**

- **설문 응답률 가설이 아직 증명되지 않았다** — Q&A는 참가자 페이지에서 실제로 저장·폴링되고(프로덕션 왕복 확인), 열람 로그와 공개 리포트도 실측으로 돈다. **설문도 이제 참가자 화면에 붙어 실제로 저장된다** — 2단 구조는 유지하되(세션별 1문항 즉시 응답 안은 트리거 설계 부담과 인터럽션 위험을 감수할 근거가 없어 채택하지 않았다, [`field-experience.md`](llm-wiki/Reference/field-experience.md)) 버튼·글자를 키우고 문항을 최소화했다(전체 만족도 1문항 + 세션별 평가, 전부 큰 터치 타깃). **하지만 이건 화면을 만든 것이지 가설을 검증한 것이 아니다** — 이 프로젝트가 도전한다고 밝힌 지점은 정확히 "고령 사용자의 실제 응답률"인데, 그건 실사용 데이터로만 증명되고 이 데모엔 그 데이터가 없다.
- **추출한 브랜드 색이 참가자 화면까지 오지 않는다** — 대표 이미지에서 색을 뽑아 프리셋으로 쌓는 흐름은 만들었고 **서버도 그 색(`hue`·`chroma`)을 응답에 실어 보낸다.** 그런데 **참가자 페이지가 그 값을 버리고 빌트인 프리셋 5종에서만 찾는다.** 한 줄짜리 분기가 빠진 것이고, 실무에서 넘어오는 게 색상 값이 아니라 이미지라는 문제의 마지막 한 칸이 그래서 비어 있다.
- **현장 업로드 UI가 없다** — 강의자료를 R2에 올리고 서명 URL로 내려주는 것도, 참가자가 앱 안에서 PDF를 보는 것도 이제 된다(페이지 이동·확대). **다만 운영자가 태블릿에서 자료를 올리는 화면이 없다** — 서버 API는 동작하고 왕복까지 확인했지만, 그걸 호출할 화면이 아래의 "스튜디오 미연결"에 막혀 있다. **"자료가 행사 중에 도착한다"는 관찰을 절반만 푼 상태다.**

**구현이 미완인 것**

- **운영자 스튜디오가 서버에 연결된 적이 없다** — 콘솔·에디터·리포트 화면에 **서버 호출이 한 줄도 없고** 전부 로컬 상태만 고친다. 편집이 D1에 남지 않고, 「공개하기」 버튼은 미리보기만 열며, 발행 상태를 화면에서 바꿀 수 없다. **이 저장소에서 가장 큰 미완이고, 위에 적은 여러 한계가 실은 전부 이 하나에서 파생된다.** 연결 경로를 정하는 것 자체를 선행 과제로 등록해 뒀다.
- **운영자 API의 읽기 경로가 아직 열려 있다** — Google SSO와 이벤트 소유권은 구현·배포됐고([`ADR 0007`](llm-wiki/Decisions/0007-sso-and-account-model.md)) **쓰기 경로(생성·수정·삭제, 아젠다·자료 저장, 질문 숨김, 파일 업로드)는 소유자 검사를 지난다** — 남의 것이면 존재를 흘리지 않도록 403이 아니라 404다. 하지만 **목록·상세·운영 지표 조회와 프리셋 쓰기는 여전히 인가 검사가 없다.** 공개 데모라 계정을 요구하지 않기로 한 결정의 잔재인데, **"무인증"과 "무보호"는 다르다는 점을 늦게 인식했다.** 각각 과제로 등록돼 있다.
- **업로드 상한은 걸었지만 요청 자체는 못 막는다** — 업로드 경로에 상한 세 겹을 뒀다: 파일당 20MB, 이벤트당 300MB, 그리고 **MB 단위 rate limit**(5분 200MB·하루 1GB). 다른 rate limit이 "요청 몇 건"을 세는 것과 달리 여기만 MB를 세는데, 지키려는 자원이 D1 행이 아니라 R2의 저장량·연산이라 "1MB를 20번"과 "20MB를 20번"을 같게 볼 수 없기 때문이다. **다만 이건 전부 요청이 워커에 도착한 뒤의 방어다** — 무효 요청 플러드는 애플리케이션 층에서 원리적으로 막히지 않고, 맞는 층은 엣지(WAF)이며 그건 커스텀 도메인이 필요하다.
- **대비비 게이트가 이미지 위 텍스트는 검사하지 않는다** — 브랜드 색 조합은 실제 sRGB 변환으로 판정해 미달 시 공개를 막지만, 키비주얼 이미지 위에 얹히는 텍스트는 그 판정에 들어가지 않는다. 흰 이미지를 올리면 게이트를 통과한 채로 대비가 무너질 수 있다.
- **키비주얼이 새로고침을 못 넘긴다** — 업로드한 이미지를 `blob:` URL로 들고 있어 브라우저를 새로고침하면 깨지고, 서버에도 저장되지 않는다.
- **자동 테스트가 순수 함수까지다** — 테마 파생·슬러그 생성·상태 검증·시드 가드가 단위 테스트 23건으로 덮여 CI에서 돌지만, **React 컴포넌트와 컨텍스트를 검증할 인프라가 없다.** 에디터→프리뷰 반영 같은 것은 여전히 사람이 브라우저로 확인한다. (컴포넌트 테스트 인프라를 한 번 붙였다가 우선순위 판단으로 되돌렸다.)
- **키보드 접근성** — 콘솔 카드와 아젠다 드래그가 포인터 전용이다. **강의자료 뷰어도 포커스 트랩이 없어** 오버레이가 열린 채 Tab을 계속 누르면 포커스가 뒤에 가려진 버튼으로 넘어간다.
- **모바일 실기기 확인이 밀려 있다** — 반응형 CSS와 44px 터치 타깃은 적용했지만, PDF 뷰어를 실제 태블릿·폰에서 확인하지 못한 채로 남겨 뒀다. **현장에서 참가자에게 보여주는 화면이 태블릿이라는 게 이 프로젝트의 전제인데** 그 확인이 비어 있다.

## 로컬 실행

```bash
npm install
npm run db:migrate   # 로컬 D1에 스키마 적용 (최초 1회 — 없으면 /api/*가 500)
npm run dev          # http://localhost:3000

npm run lint
npm test             # vitest 23건
npm run build
```

**참가자 페이지(`/[slug]`)를 로컬에서 보려면 두 가지가 더 필요하다.**

1. 저장소 루트에 `.dev.vars`(gitignore됨)를 만들고 `DOC_URL_SECRET=아무-로컬-전용-문자열`을 넣는다. 없으면 서명 URL 발급이 실패해 참가자 라우트가 전부 500이다.
2. **로컬 D1은 비어 있는 게 정상이다** — 데모 시드는 자정 Cron에서만 돌아 `npm run dev`로는 채워지지 않는다. API로 직접 만든다.
   ```bash
   curl -X POST localhost:3000/api/events -H 'content-type: application/json' \
     -d '{"title":"로컬 확인용","venue":"로컬","date":"2026-09-20"}'
   curl -X PATCH localhost:3000/api/events/<id> -H 'content-type: application/json' \
     -d '{"status":"공개"}'   # 공개 상태여야 /[slug]가 열린다
   ```

**배포는 main 머지 시 자동**이다(GitHub Actions). 손으로 하려면 `npm run preview`(workerd 로컬 검증) → `npm run deploy`.

**원격 D1 스키마만 수동이다** — `npm run db:migrate:remote`를 배포 **전에** 돌린다.

## 데이터에 대하여

이 저장소의 모든 데이터는 가상이다.

브랜드(`MERIDIAN`, `AURORA` …), 의료인과 소속기관, 의약품(`ATELOVAN`, `KEIROSTA`), 행사장은 실존하는 캠페인·인물·기관·제품·장소와 무관하며 화면 구성을 위해 지어낸 것이다. 리포트의 수치 역시 샘플이다.
