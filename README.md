# SYMPO STUDIO

**제약 심포지엄 마이크로사이트를 만들고 운영하는 스튜디오.**

운영자가 콘솔에서 행사를 관리하고, 에디터에서 아젠다·자료·참여·테마를 편집하면 참가자용 마이크로사이트에 즉시 반영된다.

> 제약 심포지엄 마이크로사이트를 **만들고 현장에서 운영하는 일**을 했습니다. 대행사에서 아젠다·이미지·강의자료를 받아 사이트에 올리고, 행사 당일에는 태블릿을 세팅하고 운영했습니다.
>
> 이 프로젝트는 그때 관찰한 문제를 처음부터 다시 설계한 개인 작업입니다. 기획·설계·구현 전부 개인 작업이며, 등장하는 브랜드·인물·소속기관·의약품·행사장은 **모두 가상**입니다.

---

## 문제

제약 심포지엄은 회차마다 새 마이크로사이트가 필요하다. 연 수십 회씩 열리는데, 매번 같은 일이 반복됐다.

겪은 문제는 **성격이 다른 두 층**이었다. 하나는 도구로 풀리는 것이었고, 다른 하나는 도구를 바꿔도 풀리지 않았다.

### 1층 — 제작·운영 효율

전달 과정에서 정보가 새고, 그 자리를 사람의 왕복이 메웠다.

- **브랜드 컬러가 이미지로만 온다** — 정확한 색상 값이 전달되지 않는 경우가 많았다. 브랜드 대표 이미지를 보고 **눈으로 맞춰 입력**했다. 아무 색이나 쓸 수는 없고 그 이미지의 컬러셋에 맞춰야 했으며, 재사용할 프리셋이 없어 회차마다 반복됐다. 문제는 입력 횟수가 아니라 **입력값이 애초에 없다는 것**이었다.
- **아젠다 변경이 이미지 왕복이다** — 연자 정보가 바뀌면 새 이미지를 다시 받아 다시 올렸다. 내 쪽 비용은 디자인 재작업이 아니라 **받아서 다시 올리는 왕복**이었다.
- **URL을 돌려쓰면 공유 캐시가 오염된다** — 편의상 이벤트 URL을 재사용했더니 카카오톡 공유 캐시에 **이전 회차 정보가 미리보기로** 남았다. 조치는 어렵지 않았지만, 회차가 고유한 주소를 갖지 않는 한 계속 생기는 종류의 일이었다.
- **강의자료는 행사가 시작된 뒤에 도착한다** — 연자가 제때 오지 않아 자료 업로드가 늦어졌다. 자료를 올리는 곳은 사무실 책상이 아니라 **행사가 진행 중인 현장**이었다.
- **현장 네트워크를 신뢰할 수 없다** — 인터넷이 끊기는 일이 있었다. 참가자 수십·수백 명이 같은 행사장 와이파이를 쓰기 때문에, **네트워크가 가장 느려지는 시점이 참여 기능을 써야 하는 시점**이다.

이 층의 공통점은 하나다. **운영에 필요한 정보가 데이터가 아니라 이미지와 문자열 안에 갇혀 있었다.**

### 2층 — 참여율, 도구를 바꿔도 풀리지 않은 것

Q&A와 설문은 처음에 외부 링크와 QR로 붙어 있었다. 참가자가 페이지를 떠나는 것이 원인이라고 보고 **프로덕트 안에서 직접 하도록 바꿨다.** 결과는 절반의 성공이었다.

- **Q&A는 올랐다.** 다만 즉시가 아니라 회차가 쌓이면서 올랐다. 참가자들이 반복 노출로 익숙해진 것이다.
- **설문은 거의 그대로였다.** 참가자 나잇대가 고령이라서다. 응답률을 올려보려 **다른 플랫폼으로 갈아타기도 했지만 효과가 없었다.**
- 결국 **현장에서 사람이 안내해 드리는 것**이 유일하게 통한 방법이었다.

즉 **이탈 지점을 없애는 것은 필요조건이었지 충분조건이 아니었다.** 그리고 플랫폼 교체로는 풀리지 않는다는 것을 직접 확인했다. 남은 접근은 인터페이스인데, 그건 그때 시도해 보지 못했다.

> **이 프로젝트가 도전하는 지점이 여기다 — 현장에서 사람이 하던 안내를 UI가 대신할 수 있는가.**

## 관찰과 가설을 갈라 둡니다

포트폴리오에서 가장 위험한 건 그럴듯하게 지어낸 문제 정의라고 생각합니다. 그래서 근거의 층을 표시해 둡니다.

- **관찰** — 위 `## 문제`의 내용. 직접 겪은 것이며 원자료는 [`llm-wiki/Reference/field-experience.md`](llm-wiki/Reference/field-experience.md)에 있습니다.
- **가설(검증 안 됨)** — ① **운영자가 직접 편집하면 전달 왕복이 사라진다.** 저는 중간 전달자였고, 운영자가 직접 쓰는 상황을 관찰한 적은 없습니다. ② **UI 개선이 고령 사용자의 응답률을 올린다.** 아직 근거가 없습니다.

**이 도구가 없애려는 중간 역할은 제가 하던 일입니다.** 대행사와 운영자 사이에서 자료를 받아 옮기는 일이 병목이었다면, 운영자가 직접 편집하는 것이 맞다고 판단했습니다. 판단의 근거는 [`ADR 0004`](llm-wiki/Decisions/0004-problem-redefinition.md)에 적어두었습니다.

## 설계 판단

| 무엇을 | Before | After | 왜 |
|---|---|---|---|
| **행사 식별** | 제목 한 문자열 + URL 재사용 | 행사명·일시·장소·좌장 필드 분해 + **회차별 고유 슬러그** | 회차마다 주소가 달라져 공유 캐시가 이전 회차를 물고 있을 수 없다. 분해된 필드는 리마인더·장소 참조의 소스가 된다 |
| **아젠다** | 이미지 슬라이드 | 구조화된 세션 레코드 + 드래그 정렬 | 이미지를 다시 받아 다시 올리는 **왕복이 사라진다.** 세션 라이브러리에서 가져다 쓸 수 있다 |
| **테마** | 이미지 보고 눈으로 맞춘 HEX | 브랜드 프리셋 선택 → OKLCH 파생 | `{hue, chroma}` 두 값에서 배경·표면·경계·본문·브랜드색을 전부 유도한다. **다만 이건 절반의 해법이다 — 아래 한계 참조** |
| **접근성** | 검증 수단 없음 | WCAG 대비비를 **저장 게이트**로 | 색을 눈으로 맞추던 시절엔 그 색이 읽히는지 확인할 방법이 없었다. 사고가 난 적은 없지만 안 났다는 보장도 없었다 |
| **참여** | 외부 링크 + QR | 페이지 내에서 완결 | 이탈 지점을 없앤다. **실무에서 여기까지는 해봤고, 설문 응답률은 오르지 않았다.** 그 다음이 이 프로젝트의 과제다 |
| **프리뷰** | 별도 구현 | 참가자 화면과 **같은 컴포넌트** | "프리뷰와 실물이 다르다"를 구조적으로 불가능하게 만든다 |
| **뷰어** | — | 모바일·태블릿 동시 렌더 | 현장에서 참가자에게 보여주는 화면이 태블릿이었다. 두 폭을 나란히 확인해야 세팅 전에 문제를 잡는다 |

마지막에서 두 번째 항목이 이 프로젝트에서 가장 마음에 드는 결정이다. 에디터의 라이브 프리뷰와 참가자 뷰어가 `Microsite` 하나를 공유하기 때문에, 두 화면이 어긋날 방법이 없다.

## 다시 만들면서 바꾼 것

실무판에는 없었지만 이번에 넣은 것:

- **운영 리포트 층** — 세션별 열람률, 설문 응답률, 행사 셋업 소요시간. 도구가 스스로를 측정하지 않으면 개선됐는지 알 수 없다.
- **대비비 검증의 게이트화** — 원래는 색상 검증이라는 개념 자체가 없었다.
- **세션 라이브러리** — 반복 등장하는 연자·세션을 매번 새로 입력하지 않도록.

> ⚠️ 리포트 화면의 수치는 **샘플 데이터**입니다. 실측값이 아니며, "어떤 지표를 봐야 하는가"에 대한 판단을 보여주기 위한 화면입니다.

## 화면

| 화면 | 하는 일 |
|---|---|
| **콘솔** | 행사 목록·검색·상태 필터·선택 모드 벌크 액션 |
| **에디터** | 기본 정보 / 아젠다 / 자료 / 참여 / 테마 5개 섹션 + 라이브 프리뷰 (모바일·태블릿) |
| **뷰어** | 참가자 화면을 모바일·태블릿 동시 렌더해 반응형 검증 |
| **리포트** | 세션별 열람률과 운영 지표 |

## 기술 선택

**Next.js 16 (App Router) · React 19 · TypeScript**

런타임 의존성이 `next`, `react`, `react-dom` **3개뿐**이다. 의도적이다 — 이 프로젝트는 오래 살아 있어야 하고, 의존성이 적을수록 2년 뒤에도 `npm install`이 그냥 된다.

백엔드는 **Cloudflare 단일 벤더**(Workers + D1 + R2)로 붙이는 중이다. 원칙은 **"저장·조회는 서버, 렌더링·생성은 클라이언트"** — 무료 티어가 인색한 자원은 저장 공간이 아니라 CPU 시간이기 때문이다. 근거는 [`ADR 0002`](llm-wiki/Decisions/0002-cloudflare-free-tier-stack.md).

트레이드오프로 남겨둔 것:

- **인라인 스타일 + OKLCH 리터럴** — 디자인 프로토타입 충실도를 우선한 결과다. hover를 CSS 헬퍼 클래스로 우회해야 하는 비용이 있다. Microsite는 테마가 런타임 파생값이라 CSS 변수로, 스튜디오 셸은 Tailwind로 나누는 것이 정리 방향이다.
- **어댑터 마찰** — Cloudflare Workers 배포는 Next.js 네이티브보다 손이 간다. 그럼에도 고른 이유는 무료 티어의 상업적 사용 제한이 없고 비활성 pause가 없다는 것 — 포트폴리오 링크가 몇 달 뒤에 죽어 있는 시나리오를 피하는 것이 최우선이었다.

## 알고 있는 한계

포트폴리오이므로 미완인 지점도 적어둔다. 상세는 [`llm-wiki/Next-Tasks.md`](llm-wiki/Next-Tasks.md)에 과제로 등록돼 있다.

**문제를 아직 못 푼 것**

- **참여 기능이 실제로 동작하지 않는다** — Q&A·설문 UI는 있지만 백엔드가 붙기 전이라 저장되지 않는다. 이 프로젝트의 핵심 주장이 아직 증명되지 않은 상태다.
- **테마 프리셋이 실제 문제를 절반만 푼다** — 실무에서 넘어온 건 색상 값이 아니라 **이미지**였다. 프리셋 목록에 그 브랜드가 있을 리 없으므로, **대표 이미지에서 색을 추출해 프리셋으로 쌓는** 흐름이 있어야 실제 해법이 된다. 현재는 미구현이다.
- **고령 사용자를 위한 설계가 없다** — 응답률 문제의 원인으로 지목한 지점인데, 정작 글자 크기·터치 타깃·단계 수는 손대지 않았다. 특히 설문이 2단인 것은 재검토 대상이다.
- **네트워크 단절 대응이 없다** — 현장 와이파이를 신뢰할 수 없다고 써놓고, 오프라인 폴백은 설계에 없다.

**구현이 미완인 것**

- **이벤트별 상태가 분리돼 있지 않다** — 콘솔에서 어떤 카드를 열어도 같은 아젠다를 편집한다.
- **저장 게이트가 아직 강제되지 않는다** — 대비비 미달 배지는 뜨지만 공개를 막지는 않는다.
- **대비비가 근사 계산이다** — OKLCH 명도를 감마 보정 휘도로 취급하는 휴리스틱이라, 실제 sRGB 변환으로 교체해야 한다.
- **자동 테스트가 없다** — 테마 파생·슬러그 생성은 순수 함수라 단위 테스트 대상이고, 에디터→프리뷰 반영은 E2E 대상이다.
- **키보드 접근성** — 콘솔 카드와 아젠다 드래그가 포인터 전용이다.

## 데이터에 대하여

이 저장소의 모든 데이터는 가상이다.

브랜드(`MERIDIAN`, `AURORA` …), 의료인과 소속기관, 의약품(`ATELOVAN`, `KEIROSTA`), 행사장은 실존하는 캠페인·인물·기관·제품·장소와 무관하며 화면 구성을 위해 지어낸 것이다. 리포트의 수치 역시 샘플이다.
