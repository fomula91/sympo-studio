# 0012 — 업로드 한도를 예약(admission)으로 판정한다 — 0008의 "성공한 쓰기에만 증가"를 업로드에 한해 개정

## 상태
채택 — [[0008-rate-limit-counter]]의 증가 시점을 **업로드 정책에 한해** 개정한다. 나머지 정책(질문·설문·로그·이벤트 생성)은 그대로다.

## 맥락

[[0008-rate-limit-counter]]가 세운 구조는 **읽고 → 부작용을 일으키고 → 성공하면 올린다**였다. 그 순서에는 판정과 증가 사이에 창이 있다. 동시에 들어온 요청은 모두 같은 카운터를 읽어 전부 통과하므로, **초과량이 동시성만큼 생긴다.** Codex 교차 리뷰가 16개 동시 업로드를 재현 경로로 제시했고, BE-29가 이걸 알면서도 닫지 않고 BE-31로 등록했다 — 가장 간단한 해법(먼저 올리고 거절 시 되돌리기)이 0008이 명시적으로 기각한 구조였기 때문이다.

**실측으로 크기를 먼저 쟀다.** 같은 토큰으로 20MB 16개를 동시에 시작한 결과:

| | 통과 | 실제 저장량 | 실제로 멈춘 것 |
|---|---|---|---|
| 수정 전 | **15건**(+400 1건) | **300MB** | rate limit이 아니라 **이벤트 총량 300MB** |
| 수정 후 | 10건(+429 6건) | 200MB | 정책(5분 200MB) 그대로 |

정책이 "5분에 200MB"라고 적어 둔 자리에서 **300MB가 지나갔다.** 초과분은 저장량이 아니라 R2 Class A 연산과 대역폭으로 샜다(저장량은 이벤트 총량이 잡았다).

## 결정

**업로드는 R2 `put` 직전에 한도를 예약한다.** 판정과 증가를 한 SQL 문장으로 묶어 그 사이에 창이 없게 한다.

**다른 정책은 바꾸지 않는다.** 그쪽이 지키는 자원은 D1 행이고, 쓰기 술어가 커밋 시점에 평가돼 이미 천장 역할을 한다. 업로드만 지키는 자원이 D1 밖(R2)에 있어 같은 보호를 못 받는다.

## 근거 — 왜 버킷마다 한 문장이 아니라 통째로 한 문장인가

버킷은 넷이다(토큰 창·토큰 일·IP 창·IP 일). 버킷마다 조건부 upsert를 따로 보내면 **일부만 통과**한다. 통과한 것을 되돌리는 보상 쓰기가 생기고, 플러드에서 그게 요청마다 반복되면 **거절된 요청이 D1 쓰기를 태운다** — 0008이 *"무효 요청이 쓰기 티어를 태우면 Q&A·설문·로그가 전부 죽는다"*며 기각한 바로 그 구조다. 이 경로로 가면 0008의 판단을 뒤집는 것이 되고, 뒤집을 근거가 없다.

그래서 게이트를 **SELECT의 WHERE 한 곳**에 모으고 버킷 행들을 그 SELECT가 만들게 했다.

```sql
INSERT INTO rate_counters (key_hash, scope, window_key, count, expires_at)
SELECT b.k, b.s, b.w, ?cost, datetime('now', b.ttl) FROM (버킷 4행) b
 WHERE (버킷마다) COALESCE((SELECT count FROM rate_counters c WHERE …), 0) + ?cost <= ?limit
ON CONFLICT(key_hash, scope, window_key) DO UPDATE SET count = count + excluded.count
RETURNING key_hash, scope, window_key
```

조건이 거짓이면 SELECT가 0행을 내놓아 **어떤 버킷도 오르지 않는다.** 즉 **거절 경로의 쓰기 비용이 0**이라 0008의 성질이 그대로 남는다.

### 실측으로 확인한 것 (추측하지 않았다)

로컬 D1에 직접 걸어 넷을 쟀다.

1. **거절**: 게이트가 거짓 → `changes=0`, 네 버킷 값 전부 불변.
2. **통과**: `changes=4`, 각 버킷이 정확히 `cost`만큼. **자기 관찰이 없다** — SQLite가 대상 테이블을 읽는 `INSERT…SELECT`를 먼저 물질화하기 때문이다. 되읽었다면 첫 행이 오른 뒤 조건이 거짓이 돼 나머지가 누락되고 `changes=1`이 됐을 것이라, `195+5<=200`이라는 **경계를 일부러 만들어** 갈랐다.
3. **`RETURNING`** 이 upsert에서 동작해 **실제로 오른 버킷**을 돌려준다.
4. **거절 플러드 12건** 뒤에도 카운터가 200에서 **1도 움직이지 않았다**.

2는 엔진 구현 세부다. 그래서 **거기 기대지 않는다** — `RETURNING`으로 받은 버킷이 전부가 아니면 오른 것만 정확히 되돌리고 거절한다. 물질화 동작이 언젠가 달라져도 카운터가 어긋난 채 남지 않는다.

### 되돌리는 기준은 하나 — R2 `put`이 실제로 일어났는가

- `put`이 던졌다 → 연산이 일어나지 않았다 → **예약을 되돌린다.**
- `put` 뒤의 실패(D1 갱신 실패, 총량 술어에 걸려 `changes === 0`) → **되돌리지 않는다.** Class A 연산은 이미 썼고, 이 정책이 지키는 자원이 바로 그것이다.

### 거절 사유 문구

게이트는 어느 버킷이 막았는지 알려주지 않는다. 사용자에게 "5분 한도"와 "오늘 한도"는 다른 안내라, **거절 경로에서만** 카운터를 한 번 더 읽어 `evaluateRateLimit`으로 정확한 문구를 고른다. 읽기는 500만/일이라 거절 경로의 읽기 1회는 문제되지 않는다 — 0008이 피하려던 것은 **쓰기**다.

## 결과·트레이드오프

**얻는 것** — 정책에 적힌 한도가 실제 천장이 된다. 거절 경로의 D1 쓰기는 여전히 0이다.

**감수하는 것**
- **사전 판정이 두 번 남는다.** 신고 크기(`Content-Length`)로 하는 읽기 판정은 20MB를 버퍼에 담기 전에 걸러내는 최적화로 남긴다 — 천장이 아니라 최적화라는 것이 코드 주석에 적혀 있어야 한다.
- **예약은 성공을 전제한다.** `put`과 D1 갱신 사이에 워커가 죽으면 예약이 남는다. 창이 지나면 사라지고(5분), 하루 카운터도 만료가 붙어 있어 누적되지 않는다.
- **분 단위 근사는 그대로다**(0008). 창 경계에서 최대 2배가 지나갈 수 있다 — 예약은 동시성 창을 닫은 것이지 슬라이딩 윈도우로 바꾼 것이 아니다.
- 게이트가 버킷 수만큼 상관 서브쿼리를 만든다(4개). 전부 PK 조회라 대상 테이블 크기와 무관하다 — 0008이 카운터를 도입한 이유가 유지된다.

## 재검토 트리거

- 다른 정책에서도 초과가 실제 피해로 드러날 때 → 같은 예약 헬퍼를 그 정책에 붙인다. 구조는 정책 무관이다.
- SQLite/D1이 `INSERT…SELECT` 물질화를 바꿔 `RETURNING`이 부분 집합을 돌려주기 시작할 때 → 보상 경로가 그걸 흡수하지만, 그때는 거절 경로의 쓰기 비용이 0이 아니게 되므로 0008과 함께 다시 본다.
- 커스텀 도메인 + 엣지 rate limiting(BE-22)이 붙을 때 → 애플리케이션 층 한도를 완화할 수 있는지 0008과 같이 재검토.
