# 0008 — rate limit 판정을 (키, 창) 카운터로 옮긴다 — 단, 무효 요청은 이 층에서 풀지 않는다

## 상태
채택 — [[0006-rate-limit-key]]의 "별도 저장소 없이 대상 테이블로 판정"을 **부분 개정**한다.

## 맥락

BE-4·BE-8이 각각 닫지 못한 것 셋이 남았고, 셋 다 **판정이 대상 테이블의 행을 세는 구조**라는 한 뿌리에서 나온다.

1. **무효 요청이 세어지지 않는다.** 한 번도 성공한 적 없는 클라이언트는 셀 행이 없어, 400·403으로 끝나는 POST를 아무리 던져도 한도에 걸리지 않는다.
2. **60초 창이 단일 행 해머링을 못 본다.** 설문 재제출은 upsert라 행이 안 늘고, `write_count`는 하루 누적이라 창 쿼리에 쓰면 그 행의 하루치를 통째로 세게 되어 오히려 틀린다.
3. **판정 SELECT가 같은 키의 당일 행을 전부 훑는다.** 429로 거절되는 요청도 예외가 아니다.

셋을 같은 무게로 두고 "카운터를 도입할까"를 물으면 답이 안 나온다. **무료 티어 한도와 대조하면 셋의 크기가 전혀 다르다.**

## 결정

**하루 한도와 60초 창 판정을 `(키, 창)` 단위 카운터 테이블로 옮긴다.** 카운터는 **성공한 쓰기에만** 증가시킨다.

**무효 요청 제한은 이 층에서 풀지 않는다** — 아래 근거대로 애플리케이션 rate limit이 다룰 문제가 아니다.

구현은 별도 과제로 분리한다(이 ADR은 결정과 설계까지).

## 근거

### 셋의 실제 크기 — 무료 티어와 대조

| 한도 | 값 |
|---|---|
| Workers 요청 | **10만 / 일** |
| D1 행 읽기 | 500만 / 일 |
| D1 행 쓰기 | 10만 / 일 |

**① 무효 요청은 D1을 소진할 수 없다.** 무효 POST 하나가 쓰는 D1은 읽기 2회·쓰기 0이다. Workers 한도인 10만 요청을 다 써도 읽기 20만 — 500만의 4%다. **요청 한도가 D1 한도보다 먼저 걸린다.**

그러니 무효 요청 플러드의 실제 피해는 "D1이 마른다"가 아니라 **"그날 Worker 요청 한도가 소진돼 사이트가 죽는다"**이고, 그건 요청이 이미 워커에 도착한 뒤라 **애플리케이션 rate limit으로는 원리적으로 막을 수 없다.** 카운터를 넣어도 못 막는다 — 오히려 요청마다 카운터를 쓰면 **쓰기 10만이 요청 10만과 1:1로 붙어 쓰기 티어가 먼저 터진다.**

> BE-17의 완료 기준에 *"도입한다면 무효 POST 플러드가 실제로 제한되는 것을 실측"*이 있었는데, **그 기준 자체가 카운터로 풀리지 않는 것을 요구하고 있었다.** 이 ADR이 그 전제를 정정한다.

**② 60초 창 해머링은 하루 쓰기 캡이 이미 상한이다.** 설문 재제출을 아무리 두드려도 `write_count` 합이 하루 200(브라우저)·2000(IP)에서 멈춘다. 창이 못 보는 것은 사실이나 **노출의 절대량이 작다.**

**③ 판정 스캔만이 실제로 읽기 티어를 소진할 수 있다.** 그리고 이건 공격이 아니라 **정상 운영에서 밟힌다.**

행사장은 단일 egress IP다([[field-experience]]). 참가자 100명이 설문을 내면 그 IP의 당일 행이 IP 일일 상한(2000)에 도달할 수 있고, **그 이후 모든 요청이 매번 2000행을 훑는다** — 429로 거절되는 요청까지. 남은 요청이 몇만 건이면 읽기 500만을 넘긴다.

**즉 도입 근거는 ①이 아니라 ③이고, 성격은 "남용 방어"가 아니라 "정상 운영 비용"이다.**

### 카운터가 O(1)이 되는 이유

`(키, 창)`으로 행 하나를 잡아 값만 읽는다. 대상 테이블의 당일 행 수와 무관해져 ③이 사라진다. 창을 분리해 두면 ②도 자연히 닫힌다 — 60초 창은 행이 아니라 쓰기를 센다.

### 왜 성공한 쓰기에만 증가시키는가

요청마다 증가시키면 무효 요청도 쓰기를 유발한다. Workers 요청 한도(10만)와 D1 쓰기 한도(10만)가 같은 자릿수라 **플러드가 읽기 티어 대신 쓰기 티어를 태우게 되고, 쓰기가 마르면 Q&A·설문·로그가 전부 죽는다.** 지금은 읽기만 타서 서비스가 살아남는다 — 이 성질을 잃으면 안 된다.

### ADR 0006의 무엇을 개정하고 무엇을 유지하는가

0006이 KV/Durable Objects 카운터를 기각한 이유는 *"바인딩·과금 축이 하나 더 생긴다"*였다. **D1 테이블 카운터는 그 이유에 해당하지 않는다** — 바인딩도 과금 축도 늘지 않는다. 기각 근거가 겨냥한 것은 저장소 추가였지 카운터 자체가 아니었다.

유지하는 것: 2층 키(브라우저 토큰 버킷 + IP 총량)와 그 범위 구분(이벤트별 / 전역, BE-19)은 그대로다. 바뀌는 것은 **세는 방법**뿐이다.

## 설계

```
rate_counters (
  key_hash   TEXT NOT NULL,   -- token_hash 또는 client_hash
  scope      TEXT NOT NULL,   -- 'questions:event:12' | 'survey:ip' 등 정책+범위
  window_key TEXT NOT NULL,   -- 하루: 'd:2026-09-07' / 창: 'm:2026-09-07T11:23'
  count      INTEGER NOT NULL DEFAULT 0,
  expires_at TEXT NOT NULL,
  PRIMARY KEY (key_hash, scope, window_key)
)
```

- 판정은 PK 조회 1행. 증가는 `INSERT … ON CONFLICT DO UPDATE SET count = count + ?`
- `window_key`에 시각을 넣어 창이 자연히 롤오버한다 — 별도 리셋이 필요 없다
- `expires_at` 기준 정리를 자정 Cron에 얹는다(이벤트 로그·만료 세션과 같은 자리)
- 60초 창을 분 단위 버킷으로 근사한다. **정확한 슬라이딩 윈도우가 아니다** — 경계에서 최대 2배가 통과할 수 있다. 목적이 "무료 티어 소진 방지"라 그 오차는 감수한다(0006이 검사·삽입 사이 동시성 창을 감수한 것과 같은 이유)

## 결과·트레이드오프

**얻는 것** — 판정이 대상 테이블 크기와 무관해진다. 행사장 단일 IP가 상한에 닿아도 이후 요청이 1행만 읽는다.

**감수하는 것**
- 성공 쓰기마다 카운터 UPSERT 1회가 붙는다. 정상 트래픽(월 500명 견적, [[0002-cloudflare-free-tier-stack]])에서는 무시할 수준이지만 **쓰기 티어를 쓰는 것은 사실이다.**
- 분 단위 근사라 창 경계에서 한도의 최대 2배가 지나갈 수 있다.
- **무효 요청은 여전히 제한되지 않는다.** 이 ADR은 그것을 이 층의 문제가 아니라고 판정한 것이지 해결한 것이 아니다.
- 판정 로직이 대상 테이블에서 떨어져 나와, "쓴 만큼만 센다"는 0006의 단순함을 잃는다. 카운터와 실제 행이 어긋날 수 있고(부분 실패 등) 그때 진실은 카운터 쪽이 된다.

## 무효 요청은 어디서 푸는가

**엣지다.** 요청이 워커에 도달하기 전에 끊어야 Workers 요청 한도를 지킬 수 있다.

다만 지금 배포는 `sympo-studio.fomula91.workers.dev`이고 **workers.dev 도메인에는 WAF·Rate Limiting Rules를 적용할 수 없다** — 존(zone)이 필요하다. 즉 **커스텀 도메인이 선행 조건**이고, 그건 BE-2가 "이번에 하지 않는 것"으로 명시해 미뤄 둔 항목이다.

따라서 무효 요청 방어는 **커스텀 도메인 + 엣지 rate limiting**을 한 묶음으로 별도 과제화한다. 그 전까지는 "Workers 요청 한도가 그날의 상한"이라는 것을 알려진 한계로 문서에 남긴다.

## 재검토 트리거

- 정상 트래픽에서 카운터 쓰기가 D1 쓰기 티어의 눈에 띄는 비중을 차지할 때 → 창 버킷 해상도를 낮추거나(분→5분) 성공 쓰기 N건마다 한 번만 증가시키는 근사로 전환.
- 창 경계 2배 통과가 실제 문제로 드러날 때 → 슬라이딩 윈도우(직전 창 가중 합)로 교체. 같은 테이블로 가능하다.
- 커스텀 도메인이 생겨 엣지 rate limiting을 붙일 수 있게 될 때 → 애플리케이션 층 한도를 완화할 수 있는지 재검토.
