# 0006 — rate limit 키: 브라우저 토큰 버킷 + IP 총량 상한의 2층 구조

## 상태
채택

## 맥락
BE-3의 rate limit 키는 소스 IP 단독이다(SHA-256(ip|KST날짜) 앞 16자). 행사장 Wi-Fi는 단일 egress IP라([[field-experience]]의 표준 운영 환경, 통신사 CGNAT도 동일) **참가자 전원이 분당 3건·일 30건 버킷 하나를 공유**한다 — 4번째 제출자부터 429, 30건 이후 방 전체 잠김. 반대로 키를 브라우저 식별자만으로 바꾸면 봇이 요청마다 새 식별자를 지어내 무제한이 된다. FE-3이 이 키 설계에 의존하므로(토큰 전송부) 착수 전에 확정해야 한다.

## 결정
키를 **두 층**으로 나눈다. 판정은 두 층 모두 통과해야 한다.

1. **브라우저 버킷** — FE가 생성·보관하는 익명 토큰(UUID, `localStorage`)을 `x-client-token` 헤더로 보내면, `token_hash = SHA-256(token|KST날짜)` 기준으로 **60초 3건 / 일 30건**. IP를 섞지 않아 Wi-Fi↔LTE 전환에도 버킷이 유지된다.
2. **IP 총량 상한** — 기존 `client_hash = SHA-256(ip|KST날짜)` 기준으로 **60초 20건 / 일 300건**. 토큰을 위조로 바꿔가며 보내도 여기서 잡힌다.

토큰이 없거나 형식이 틀린 요청은 거절하지 않고 **IP 단독 버킷(60초 3건/일 30건, 기존 정책)으로 강등**한다 — 토큰 생략이 우회 수단이 되지 않는다. 저장은 `questions`에 `token_hash` 컬럼 추가(마이그레이션 0002), 판정은 기존처럼 테이블 자체 COUNT로 한다.

## 근거
비교한 대안과 기각 이유:

- **이벤트 단위 총량 상한** — 공격자 하나가 이벤트 전체 한도를 소진시켜 **정상 참가자까지 잠그는 자기-DoS 벡터**가 된다. IP 상한은 공격자의 네트워크만 잠근다. (행사장 IP에서의 공격은 IP 상한 300건이 무료 티어를 보호하는 선에서 감수 — 그 안에서는 현장 운영자가 대응 가능한 규모다.)
- **Cloudflare Turnstile/CAPTCHA** — 무료지만 외부 스크립트 의존이 생기고, 고령 사용자 기준(FE-3)의 입력 흐름에 마찰을 더한다. 남용이 실측되면 재검토.
- **KV/Durable Objects 카운터** — 정확하지만 바인딩·과금 축이 하나 더 생긴다. "쓴 만큼만 센다(questions 테이블 자체 판정)"의 단순함을 유지([[0002-cloudflare-free-tier-stack]]).
- **쿠키 기반 식별** — 헤더보다 FE 구현이 편하지 않고(브라우저가 자동 전송), 공개 GET 캐시와 얽히면 오염 위험이 있다. 헤더는 POST에만 실려 캐시와 무관하다.
- **토큰 서버 발급(서명)** — 위조 불가가 되지만 발급 엔드포인트·검증 로직이 추가되고, 어차피 IP 상한이 위조 비용을 무의미하게 만든다.

숫자의 근거: 브라우저 3/60초·30/일은 BE-3 값 유지(사람의 질문 속도). IP 20/60초는 시드 정원 120명 규모 행사의 Q&A 세션 피크(분당 10~20건 관측 가정)를 막지 않는 선, 300/일은 브라우저 일 한도 30의 10배 — 한 IP 뒤에서 10개 브라우저가 꽉 채워 쓸 수 있는 양이며 D1 무료 티어(쓰기 10만/일)의 0.3%다.

## 결과·트레이드오프
- 얻는 것: 행사장 Wi-Fi에서 참가자별 독립 한도. 위조 토큰은 IP 상한에, 토큰 생략은 강등 버킷에 걸림. 스키마 컬럼 하나·쿼리 하나로 구현(무료 티어 부담 없음).
- 감수하는 것: ① 같은 브라우저라도 `localStorage`를 지우면 새 버킷 — 익명성의 대가로 받아들인다(토큰은 어디에도 원문 저장되지 않고 날짜 소금으로 매일 로테이션). ② 진짜 분산 봇넷(IP 다수)은 못 막는다 — 그건 rate limit이 아니라 Cloudflare 레벨의 문제. ③ 시크릿 창 남용(창마다 새 토큰)은 IP 상한까지는 통과 — 300건/일 한도 내 감수.

## 재검토 트리거
- 프로덕션에서 IP 상한 429가 정상 행사 중 관측되면(현장 로그) 상한 재조정.
- 남용이 IP 상한을 우회하는 패턴(분산 IP)으로 실측되면 Turnstile 재검토.
- BE-5의 이벤트 로그가 쌓이면 "실측 기반 상한"으로 숫자를 교체.
