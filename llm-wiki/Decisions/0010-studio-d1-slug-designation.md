# 0010 — 스튜디오를 D1에 연결하는 경로: id 지목 (워크스페이스 아님)

## 상태
채택

## 맥락

`ConsoleScreen`·`EditorScreen`·`ReportScreen`·`ViewerScreen`·`StudioShell` 다섯 화면은
`fetch` 호출이 0건이고 `useStudio()`의 로컬 목업(`SEEDED_EVENTS`, id 0~14)만 고친다.
백엔드 CRUD(`GET/PATCH/DELETE /api/events/[id]`, `PUT .../sessions`, `PUT .../documents`
등)는 이미 동작하는데 스튜디오가 그걸 호출하지 않는다. 이 미연결 때문에 FE-15·19·23·24·25
다섯 과제가 막혀 있고, 과거 세 번(FE-5·FE-19·FE-23) 같은 벽에서 범위를 좁힌 이력이 있다
([[Next-Tasks]] FE-30, [[Context]]).

두 경로가 후보였다:
- ⓐ **워크스페이스 경로** — [[0007-sso-and-account-model]]이 이미 설계한 게스트
  `localStorage` 워크스페이스를 먼저 세우고, 로그인 시 `POST /api/events/import`로
  서버와 동기화한다. `BE-15`(아직 구현 안 됨) 선행 필요.
- ⓑ **slug/id 지목 경로** — `/[slug]`·`/[slug]/report`(FE-3·FE-5)가 이미 쓰는 방식대로,
  스튜디오도 URL의 이벤트 id로 실제 D1 행 하나를 지목해 그 CRUD를 그대로 호출한다.
  BE 의존 없음.

## 결정

**ⓑ slug/id 지목 경로를 채택한다.** `/events/[id]/edit`가 그 id의 실제 D1 이벤트를
`GET /api/events/[id]`로 읽어와 로컬 목업 배열에 병합하고, 기본 정보(제목·장소·일시·
좌장·예상 인원·테마 프리셋·아이콘셋·밀도·키비주얼·kv패턴·참여 토글) 편집은
`PATCH /api/events/[id]`로 서버에도 반영한다. 아젠다(`sessions`)·자료(`documents`)
쓰기는 이번 범위에 넣지 않았다 — 각각 `PUT .../sessions`·`PUT .../documents`라는
별도 diff 계약이 있어 이 과제(연결 경로 증명)보다 큰 작업이고, FE-24/FE-25가 다룰
영역이다.

**워크스페이스(ⓐ)는 기각이 아니라 유예다.** ADR 0007이 이미 설계를 확정해 뒀고
FE-15가 그 구현을 맡는다 — 로그인·게스트 이원화가 실제로 필요해지는 시점(FE-15
착수 시)에 되짚는다.

## 근거

| 기준 | ⓐ 워크스페이스 | ⓑ id 지목 |
|---|---|---|
| BE 의존 | `BE-15`(미구현) 필요 | 없음 — 오늘 바로 착수 가능 |
| 구현 범위 | 게스트 `localStorage` 전체 계층 + 가져오기 흐름 | 기존 CRUD를 호출하는 어댑터 하나 |
| "연결 경로가 있다"는 것 자체를 증명하는 데 필요한 최소 작업 | 아니다 — 훨씬 크다 | 그렇다 |
| 기존 코드베이스와의 일관성 | 신규 패턴 | `/[slug]`가 이미 쓰는 패턴 재사용 |

FE-30의 완료 기준 자체가 "경로를 뚫는 것까지 — 다섯 과제를 여기서 다 하지 않는다"로
작게 잡혀 있다. ⓐ를 택하면 이 과제 하나가 사실상 FE-15 전체를 흡수해버려 범위가
설계 의도와 어긋난다. ⓑ는 BE 없이 오늘 증명할 수 있고, 이미 검증된 패턴(참가자 페이지)을
그대로 반복하므로 새로운 위험을 들이지 않는다.

## 결과·트레이드오프

### 얻는 것

- `GET /api/events/[id]`가 반환하는 임의의 실제 D1 이벤트가 스튜디오 에디터에 뜨고,
  기본 정보 필드 편집이 실제로 서버에 저장돼 새로고침 후에도 남으며, 같은 이벤트의
  참가자 페이지(`/[slug]`)에 그 변경이 반영된다 — 브라우저로 실측 확인(로컬 D1,
  event id=1과 id=17 두 경우로 검증. id=17은 목업 시드 범위(0~14) 밖의 순수 D1
  전용 id다).
- **슬러그를 로컬에서 재계산하지 않는다.** `PATCH /api/events/[id]`는 "slug는 여기서
  바꾸지 않는다"는 계약인데, 기존 `patchEvent`는 제목·장소·일시가 바뀌면 항상 로컬
  slug를 재계산했다. 서버가 실제로 붙어 있는 이벤트는 이 재계산을 건너뛴다 — 안 그러면
  화면이 보여주는 "공개 URL"이 실제로 열리는 주소와 어긋나는 FE-23류 버그가 재발한다.

### 게스트에게 이 화면이 어떻게 보이는가

**로그인 사용자와 구분 없이 똑같이 보인다 — 지금은 구분할 방법 자체가 없다.**
`PATCH /api/events/[id]`를 비롯한 운영자 쓰기 라우트에 아직 인가가 없다(`BE-13`
미착수, [[Context]] "운영자 API에는 인증이 없다"). 이번 연결은 그 위에 그대로
얹혔을 뿐 새로운 노출을 만들지 않았다 — 이미 누구나 `curl`로 호출할 수 있던
엔드포인트를 스튜디오 화면이 처음으로 호출하게 됐을 뿐이다. 게스트/로그인을 실제로
가르는 것은 `FE-15`(화면)와 `BE-13`(서버 인가)의 몫이고, 그 전까지는 "이 화면을
여는 모두가 편집할 수 있다"가 사실이다.

### 감수하는 것 (정직하게)

- **아젠다·자료 편집은 아직 로컬 전용이다.** 드래그로 세션을 재배열하거나 자료를
  추가해도 서버에 안 나간다. FE-24(발행 상태·아젠다 저장 UI)·FE-25(현장 업로드)의
  몫으로 남겨뒀다 — `detailPatchToBody`가 `sessions`를 다루지 않아 그런 델타는
  조용히 로컬에만 남는다(에러도 없다). 사용자가 "아젠다도 저장되는 줄 알았는데
  아니었다"로 오인하지 않도록, 이 문서와 `Next-Tasks.md`에 명시한다.
- **최초 진입 시 서버 fetch가 끝나기 전까지 헤더(로고 옆 이벤트명)가 순간적으로
  엉뚱한 값을 보여준다** — `StudioShell`의 헤더는 `loadStatus`를 보지 않고 항상
  `ev`를 그대로 쓰기 때문이다. 본문 영역은 `loadStatus==='loading'`일 때 "불러오는
  중…"으로 가리므로 실사용에 지장은 적지만, 완벽하지 않다. 폴리싱은 이번 범위 밖.
- **저장 상태 표시(`s.saved`)가 실제 저장과 완전히 동기화되지 않는다.** 아젠다
  드래그처럼 서버로 안 나가는 편집도 기존 컴포넌트 코드가 자체적으로
  `patch({saved:'방금 저장됨'})`을 부르므로, "저장됨"이 곧 "서버에 저장됨"을 뜻하지
  않는 경우가 여전히 있다. 이 문서가 새로 만든 문제는 아니고(기존에도 전부 로컬
  전용이라 같은 표시가 항상 거짓이었다), 서버 동기화 필드에 한해서만 참이 되도록
  개선했을 뿐이다.
- **디바운스 저장의 부작용** — 제목 등 폼 입력은 700ms 무입력 후 한 번에 PATCH를
  보낸다(키 입력마다 보내던 첫 구현은 12글자 제목 하나에 요청 12번이 나가는 것을
  실측으로 확인해 수정). 사용자가 입력 직후 즉시 다른 화면으로 이동하면 언마운트
  cleanup이 대기 중인 델타를 flush하지만, **탭을 그냥 닫으면** 그 마지막 700ms
  구간의 편집이 유실될 수 있다 — `beforeunload`/`visibilitychange` 훅은 이번
  범위에 넣지 않았다.

## 재검토 트리거

- FE-15 착수 시 ⓐ 워크스페이스 경로가 실제로 필요해지면, 이 문서의 `patchEvent`
  서버 동기화 로직을 게스트/로그인 분기와 합치도록 다시 본다.
- 아젠다·자료 편집도 서버에 반영해야 하는 시점(FE-24·FE-25)에 `detailPatchToBody`
  범위를 넓히거나 별도 동기화 경로를 추가한다.
