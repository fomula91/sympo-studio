# 0007 — Google SSO + 개인 계정 소유권 모델 (게스트 경로 유지)

## 상태
채택 — [[0001-backend-for-working-demo]] 결정 1번을 **개정**한다(폐기 아님, 아래 「0001과의 관계」).

## 맥락

운영자 CRUD가 인터넷에 완전히 열려 있다. `POST /api/events`(생성)·`PATCH /api/events/[id]`(수정, engage 토글 포함)·`DELETE /api/events/[id]`(CASCADE 삭제)에 인가 검사가 없고, 참가자 쓰기와 달리 **rate limit조차 없다.** 프로덕션 검증 때마다 `curl`로 이벤트를 만들고 지웠던 것이 그 증거다.

ADR 0001은 이 상태를 "운영자 콘솔은 데모 계정으로 즉시 진입"으로 적었지만, **실제로는 계정 개념 자체가 없었다.** 문서와 구현이 어긋나 있었고, 어긋난 쪽은 구현이 아니라 문서였다 — "데모 계정"이라는 말이 존재하지 않는 것을 존재하는 것처럼 서술했다.

여기에 사용자가 실제 SSO 가입과 계정 관리를 요구했다. 그런데 0001이 회원가입을 기각한 근거 — **"채용담당자는 가입하지 않는다. 링크를 열고 30초 안에 판단한다"** — 는 지금도 유효하다. 이 프로젝트는 여전히 채용용 포트폴리오다.

두 요구가 충돌하는 것처럼 보이지만 실제로는 **관객이 둘**이다. 링크를 열고 30초 안에 판단하는 사람과, 자기 행사를 실제로 만들려는 사람은 같은 사람이 아니다.

## 결정

**Google SSO로 개인 계정을 만들고 이벤트에 소유권을 부여한다. 단, 로그인 없이 데모를 보는 경로를 유지한다.**

### 1. 게스트/계정 이원화 — 게스트는 **로컬 워크스페이스**를 가진다

게스트의 편집은 **`localStorage`에 영속한다.** 새로고침해도, 브라우저를 닫았다 다시 열어도 그대로 남는다. "서버에 저장되지 않는다"가 "사라진다"를 뜻하지 않는다 — **만져본 결과를 확인할 수 없으면 체험이 성립하지 않기 때문이다.**

| | 게스트(비로그인) | 로그인 사용자 |
|---|---|---|
| 콘솔·에디터·테마 조작 | O | O |
| 편집 결과 유지 | O — **`localStorage`에 영속**(재방문에도 남음) | O — D1 |
| 이벤트 생성·삭제 | O — 로컬 워크스페이스 안에서 | O — 서버(owner_id = 자신) |
| 참가자 화면 공개 URL | X — 로컬 프리뷰까지 | O |
| 남의 이벤트 | 보이지 않음 | 보이지 않음 |

**게스트 워크스페이스는 서버 데이터를 참조하지 않는다.** 첫 진입 시 클라이언트 시드로 초기화하고 그 뒤로는 전부 로컬에서 완결한다. 서버 데모 이벤트의 id를 참조하는 오버레이 방식이 아니다 — 그렇게 하면 **매일 자정 Cron이 데모를 리셋할 때 로컬 편집분의 기준이 사라져** 조용히 깨진다.

서버의 데모 이벤트(`owner_id IS NULL`)는 없어지지 않고 **다른 역할을 맡는다**: 참가자 마이크로사이트(`/[slug]`)에서 Q&A·설문이 실제로 저장되는 것을 보여주는 경로다. 운영자 도구 체험은 로컬에서, 참가자 참여 증명은 서버에서 — 둘은 겹치지 않는다.

게스트 경로 자체는 새로 만드는 것이 아니다. **0001 결정 3번의 "하이브리드 실패 모드"(콘솔·에디터·테마는 서버 없이도 동작)가 이미 그 구조**이며, 여기서는 발동 조건이 "서버가 죽었을 때"에서 "로그인하지 않았을 때"로 하나 늘어날 뿐이다. 0001이 기각한 A안(정적 + localStorage)이 **폐기되지 않고 게스트 모드로 살아남는** 셈이다.

### 1-1. 로그인 시 로컬 작업을 계정으로 가져온다

로그인 직후 로컬 워크스페이스에 편집분이 있으면 **"체험 중 만든 이벤트 N개를 내 계정으로 가져올까요?"** 를 묻는다. 묻지 않고 버리면 게스트가 공들여 만든 것이 로그인이라는 행동으로 사라진다 — **사용자 입장에서 로그인은 잃는 행동이 되어서는 안 된다.** 반대로 자동 병합은 남의 컴퓨터에서 로그인했을 때 모르는 데이터가 계정에 섞이므로 확인을 거친다.

**전제: 지금 API로는 불가능하다.** `POST /api/events`는 이벤트 헤더 필드(brand/title/venue/date/host/capacity/status)만 받고, 테마는 `PATCH`로만 들어가며, **아젠다(`sessions`)를 쓰는 라우트는 존재하지 않는다**(`app/api/events/[id]/`에 `questions`·`survey`뿐). 이벤트 껍데기만 가져오면 게스트가 짠 아젠다가 버려져 "로그인은 잃는 행동이 아니다"라는 취지 자체가 무너진다. 따라서 가져오기는 **아젠다 쓰기 API(BE-14)를 전제로 한 전용 엔드포인트**로 만든다.

**`POST /api/events/import`** — 이벤트 + 테마 + 아젠다를 **묶어서** 받고 D1 `batch` 한 번으로 생성한다. 이벤트마다 `POST` → `PATCH` → 아젠다 N회를 돌리지 않는 이유는 셋이다: 왕복이 수십 회로 늘어 무료 티어 쓰기를 낭비하고, 중간에 끊기면 **테마 없는 이벤트·아젠다 없는 이벤트 같은 반쪽 상태**가 서버에 남으며, 재시도 시 중복이 생긴다.

- **멱등성** — 로컬 워크스페이스의 각 이벤트는 생성 시 로컬 UUID(`localRef`)를 갖는다. 서버는 `events.client_ref` + `UNIQUE(owner_id, client_ref)`로 받아 재요청 시 새로 만들지 않고 기존 행을 돌려준다. 네트워크가 끊겨 사용자가 다시 누르는 것은 **정상 경로**로 취급한다.
- **원자성의 단위는 이벤트 하나** — 이벤트 A가 성공하고 B가 실패하면 A는 커밋된 채로 두고 B만 재시도한다. 전체 롤백은 "9개 성공했는데 10번째 때문에 처음부터"가 되어 더 나쁘다. 응답은 건별 결과 배열이며, **로컬에서 제거하는 것은 성공한 항목만**이다.
- **slug는 바뀔 수 있다** — 서버의 `ensureUniqueSlug`가 충돌 시 접미사를 붙이므로 게스트가 보던 주소와 달라진다. 조용히 바꾸지 않고 결과에 어떤 이벤트의 slug가 바뀌었는지 실어 화면에서 알린다.
- **상한** — 한 번에 가져올 이벤트 수와 이벤트당 아젠다 수에 상한을 두고 초과 시 400. 가져오기는 계정당 최대 쓰기 경로이므로 BE-13의 운영자 쓰기 rate limit이 여기에도 걸린다.
- **거절하면 로컬 보존** — 서버 워크스페이스만 보여주고 로컬은 건드리지 않는다. 로그아웃하면 게스트 워크스페이스가 그대로 다시 보인다.

### 2. 인증은 직접 구현한다 — Google OAuth 2.0 + D1 세션

라이브러리(Auth.js·Better Auth)나 Cloudflare Access를 쓰지 않고 Authorization Code + PKCE 흐름을 직접 구현한다. 세션은 랜덤 토큰을 httpOnly 쿠키에 담고 D1에 **해시만** 저장한다.

- `GET /api/auth/google` — `state` + PKCE `code_verifier` 생성 → 단기 httpOnly 쿠키에 보관 → Google authorize로 302
- `GET /api/auth/callback/google` — `state` 대조 → code+verifier로 토큰 교환 → `id_token`의 `iss`/`aud`/`exp` 확인 → 사용자 upsert → 세션 발급 → 원래 있던 곳으로 복귀
- `POST /api/auth/logout` — 세션 행 삭제 + 쿠키 만료
- `GET /api/auth/me` — 현재 사용자(없으면 200 + `null`, 401 아님 — 게스트가 정상 상태이기 때문)

`id_token`은 **토큰 엔드포인트에서 HTTPS로 직접 받았으므로 서명 로컬 검증을 생략**한다(Google이 문서에서 명시적으로 허용하는 경로). JWKS 조회·캐싱이 사라져 Workers CPU와 바인딩이 늘지 않는다. 대신 `iss`/`aud`/`exp`는 파싱해 확인한다.

### 3. 계정 관리 범위는 개인 계정까지 — 조직·팀·역할은 넣지 않는다

프로필(이름·아바타·연결된 제공자), 로그아웃, **계정 삭제**(CASCADE로 이벤트·아젠다·자료·질문·설문 응답까지)까지가 이번 범위다. `organizations`/`memberships`/`roles`는 넣지 않는다.

## 근거

### 왜 게스트 경로를 남기는가

전면 로그인은 인가 경계가 가장 깔끔하지만 **이 저장소의 존재 목적을 훼손한다.** 링크를 연 채용담당자가 처음 만나는 화면이 로그인 벽이면 0001이 기각한 C안과 결과가 같아진다 — 데모가 없는 것이 된다. 반대로 게스트에게 서버 쓰기를 허용하면 지금의 무보호 상태와 다를 바 없다. **"게스트는 만져볼 수 있지만 서버에 남기지는 못한다"**가 두 요구를 동시에 만족시키는 유일한 지점이다.

### 왜 직접 구현인가

| 안 | 기각/채택 사유 |
|---|---|
| **직접 구현 (Google OAuth + D1 세션)** | **채택.** 런타임 의존성 0 — 0001이 "감수하는 것"으로 적은 *"2년 뒤에도 `npm install`이 그냥 된다는 성질이 약해진다"*를 더 약화시키지 않는다. raw SQL·손으로 쓴 마이그레이션이라는 이 저장소의 기존 스타일과 일치하고, OpenNext 어댑터 마찰이 없다 |
| Better Auth + D1 | 위험은 가장 낮으나 스키마 소유권이 라이브러리로 넘어가 `migrations/*.sql` 방식과 어긋난다. 의존성도 늘어난다 |
| Auth.js (NextAuth v5) | OpenNext Cloudflare 조합에 알려진 마찰이 있다. **0001이 이미 "어댑터가 Next.js 업그레이드를 따라오지 못하면 배포가 막힌다"를 최대 위험으로 꼽았는데**, 같은 종류의 의존성을 하나 더 얹는 셈이다 |
| Cloudflare Access | 코드 0줄로 SSO가 서지만 로그인 화면이 Cloudflare의 것이고 앱 안에 계정·프로필 개념이 생기지 않아 "계정 관리를 만든다"는 요구를 충족하지 못한다 |

"인증을 직접 만들지 말라"는 통념은 **비밀번호 해싱·크리덴셜 저장·크립토 프리미티브**를 겨냥한 것이다. 여기서 신원 검증이라는 어려운 부분은 전부 Google에 위임하고, 우리가 쓰는 것은 OAuth **클라이언트** 흐름과 랜덤 토큰 세션뿐이다. 다만 `state`/PKCE/세션 회전은 직접 맞춰야 하므로 **코드리뷰를 완료 기준에 포함**한다.

### 왜 조직·역할까지 가지 않는가

실무형이고 인가 설계 역량을 크게 보여주지만 스키마·API·화면이 모두 배가된다. 지금 막아야 하는 구멍은 "아무나 남의 이벤트를 지운다"이고, 그것은 `owner_id` 하나로 막힌다. 조직은 그 위에 얹는 것이지 그것 없이 못 하는 일이 아니다.

## 결과·트레이드오프

### 스키마 (마이그레이션 0004)

```
users            (id, email UNIQUE, name, avatar_url, created_at, updated_at)
oauth_accounts   (id, user_id → users CASCADE, provider, provider_account_id,
                  UNIQUE(provider, provider_account_id))
auth_sessions    (id = SHA-256(세션 토큰), user_id → users CASCADE, expires_at, created_at)
events.owner_id  INTEGER REFERENCES users(id) ON DELETE CASCADE   -- NULL = 데모
```

**이름 충돌 주의**: 이 저장소의 `sessions` 테이블은 **아젠다 세션**([[0005-d1-schema]])이다. 인증 세션은 반드시 `auth_sessions`로 쓴다 — 같은 이름을 재사용하면 스키마·쿼리·타입 전반에서 조용히 뒤섞인다.

세션 원문 토큰은 저장하지 않고 SHA-256 해시를 PK로 쓴다. D1 내용이 유출돼도 세션을 탈취할 수 없다. 해싱 패턴 자체는 이미 `client_hash`/`token_hash`([[0006-rate-limit-key]])에서 쓰던 것이라 새로운 개념이 아니다.

### 반드시 함께 고쳐야 하는 것 — Cron 시드 리셋

`lib/seed.ts:22`의 `resetDemoData`는 **`DELETE FROM events`로 전체를 지운다.** `owner_id`를 추가하는 순간 이 한 줄이 **매일 자정(KST) 사용자 계정의 이벤트를 전부 삭제**하며, `events`의 CASCADE를 타고 아젠다·자료·질문·설문 응답까지 함께 날아간다. 스키마 변경과 **같은 커밋에서** `WHERE owner_id IS NULL`로 한정해야 한다. 별도 과제로 미루면 안 되는 종류의 결함이다.

### 쿠키

`SameSite=Lax`(OAuth 리다이렉트 복귀는 top-level GET 내비게이션이라 Lax로 실린다 — `Strict`면 콜백 후 세션이 사라진다), `HttpOnly`, `Secure`, `Path=/`. 프로덕션은 `__Host-` 접두사를 쓰되 **로컬 dev는 http라 접두사가 동작하지 않으므로 이름을 환경별로 분기**한다. 이 분기를 빠뜨리면 로컬에서만 로그인이 안 되는 형태로 드러난다.

### 무료 티어 영향

세션 검증이 요청당 D1 읽기 1회를 더한다. **운영자 라우트에만 걸리므로 폴링 경로(참가자 Q&A·설문·공개 조회)의 읽기 비용은 그대로**다 — [[0002-cloudflare-free-tier-stack]]의 견적과 BE-8의 읽기 통제 계산이 흔들리지 않는다. 콘솔 화면이 여러 API를 연속 호출하는 구간에서는 세션 조회를 대상 조회와 D1 `batch`로 묶는다.

### 감수하는 것 (정직하게)

- **`state`/PKCE/세션 회전을 직접 맞춰야 한다.** 라이브러리를 골랐다면 남이 검증한 구현을 받았을 부분이다. 코드리뷰로 상쇄하되, 상쇄지 제거가 아니다.
- **Google 계정이 없는 사람은 로그인할 수 없다.** 제공자 확장(GitHub 등)은 `oauth_accounts`가 이미 `provider` 컬럼으로 열어뒀으므로 추가 마이그레이션 없이 가능하다.
- **비밀값이 늘어난다.** `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`을 `wrangler secret`으로 관리해야 하고, Google Cloud Console에서 redirect URI를 등록하는 **사람 손 작업**이 배포 절차에 추가된다(BE-2의 대시보드 잔여 항목과 같은 성격).
- **화면마다 게스트/계정 두 모드를 다뤄야 한다.** FE 분기가 늘고, "이 버튼이 게스트에게 어떻게 보이는가"가 모든 운영자 화면의 검토 항목이 된다.
- **로컬 워크스페이스는 그 브라우저에만 있다.** 기기를 바꾸거나 시크릿 창을 닫으면 사라지고, 사파리의 7일 스토리지 만료에도 걸린다. 게스트 모드에 이 사실을 문구로 드러내고(조용히 사라지지 않게), 그것이 로그인의 이유가 되게 한다.
- **`localStorage`는 5MB 정도다.** FE-8이 대표 이미지 업로드를 추가하면 `key_visual`이 base64로 들어가 한도에 닿을 수 있다. 게스트 워크스페이스는 이미지를 담지 않거나(참조만) IndexedDB로 옮기는 판단이 FE-8·FE-15 착수 시점에 필요하다.
- **가져오기가 대량 쓰기 경로가 된다.** 로컬 이벤트 N개를 한 번에 서버로 올리므로, 지금 rate limit이 전혀 없는 운영자 쓰기에 통제를 함께 넣어야 한다(BE-13).

## 0001과의 관계

[[0001-backend-for-working-demo]]의 결정 1번 *"방문자에게 회원가입을 요구하지 않는다. 운영자 콘솔은 데모 계정으로 즉시 진입"* 을 다음으로 대체한다:

> **방문자에게 회원가입을 요구하지 않는다.** 운영자 콘솔은 비로그인으로 즉시 진입해 조작할 수 있으며, 이때 편집은 서버에 저장되지 않는다. 서버에 남기려는 사용자만 Google SSO로 가입하고, 자기가 만든 이벤트만 소유·수정·삭제한다.

기각 근거였던 *"채용담당자는 가입하지 않는다"* 는 유지된다 — 가입은 이제 선택지이지 장벽이 아니다. 0001의 대안표 C안(회원가입 후 각자 이벤트 생성)은 **가입을 강제했기 때문에** 기각된 것이고, 여기서는 강제하지 않는다.

## 재검토 트리거

- 데모 이벤트에 스팸 계정이 몰려 무료 티어를 압박할 때 → 계정당 이벤트 수 상한, 또는 가입 승인제.
- 여러 사람이 한 행사를 함께 운영해야 할 때 → `organizations`/`memberships` 도입(이번에 기각한 안).
- 직접 구현한 OAuth 흐름에서 보안 결함이 반복될 때 → Better Auth로 이전. `oauth_accounts`/`auth_sessions`를 표준 형태로 두면 이전 비용이 낮다.
