# 0005 — D1 스키마: 회차 고유성·프리셋 축적·문항 단위 설문

## 상태
채택

## 맥락

BE-1은 나머지 BE 다섯 과제와 FE-1이 전부 얹히는 바닥이고, [[Next-Tasks]]에도 **"가장 되돌리기 비싼 결정"** 이라고 적혀 있다. 한 번 쓰기 시작하면 스키마 변경에 마이그레이션과 데이터 이관이 따라붙는다.

착수 시점에 문제가 하나 있었다. 같은 날 인터뷰로 **문제 정의가 크게 바뀌었는데**(브랜치 `docs/problem-redefinition`, ADR 0004), 그 결과가 아직 `main`에 병합되지 않았다. `main`의 과제 정의만 보고 스키마를 짜면 다음이 빠진다.

- 브랜드 프리셋을 **저장·재사용**할 자리 (실무에서 색상 값이 아니라 이미지가 왔다)
- 설문을 **세션별 1문항**으로 받을 수 있는 구조 (2단 몰아받기가 고령 사용자에게 장벽이었을 가능성)
- 자료가 **행사 진행 중에** 올라오는 상황 (연자 지각)

이 셋은 전부 스키마에 직접 영향을 준다. 나중에 반영하면 정확히 "되돌리기 비싼" 작업이 된다.

## 결정

**`main`을 기준으로 작업하되, 아직 병합되지 않은 문제 정의의 결과를 스키마에 미리 반영한다.** 테이블은 일곱이며(`brand_presets` `events` `sessions` `documents` `questions` `survey_responses` `event_logs`), 그중 넷은 실무 경험에서 직접 나온 설계다.

| 결정 | 무엇을 보장하나 |
|---|---|
| `events.slug` **UNIQUE** | 회차마다 주소가 달라 공유 캐시가 이전 회차를 물고 있을 수 없다 |
| `brand_presets`를 **별도 테이블**로, `origin='extracted'` + `source_key` | 이미지에서 추출한 색이 프리셋으로 **쌓인다**. 다음 회차에 재사용 |
| `survey_responses`는 **문항 하나 = 행 하나**, `session_id` nullable | 세션별 1문항과 행사 전체 문항을 **같은 테이블로** 담는다 |
| `documents.status='pending'` + `r2_key` nullable | 파일보다 자료 행이 먼저 생긴다. 그동안 "준비 중"으로 표시 |

## 근거

**왜 slug를 UNIQUE로 거는가** — 실무에서 이벤트 URL을 돌려쓰다 카카오톡 공유 캐시에 이전 회차 정보가 미리보기로 남았다. 애플리케이션에서 중복을 검사할 수도 있지만, **동시 생성에서는 검사와 삽입 사이가 벌어진다.** DB 제약으로 걸면 그 창이 사라진다. 충돌 시 예외를 던지지 않고 `-2`, `-3` 접미사를 붙이는 이유는 운영자가 같은 이름으로 회차를 여러 번 만드는 것이 정상 흐름이기 때문이다(`lib/db.ts`의 `ensureUniqueSlug`).

**왜 프리셋이 테이블인가** — 현재 구현은 프리셋을 코드 상수로 갖는다. 그런데 실무에서 넘어오는 건 색상 값이 아니라 브랜드 대표 이미지 한 장이고, 회차마다 다른 브랜드가 온다. **프리셋 목록에 그 브랜드가 있을 리 없다.** 프리셋은 미리 준비된 목록이 아니라 이미지에서 추출해 쌓이는 것이어야 하고, 그러려면 저장소가 필요하다. `origin`으로 내장/추출을 구분하고 `source_key`로 원본 이미지를 가리킨다.

**왜 설문을 문항 단위로 쪼개는가** — 이것이 이 스키마에서 가장 중요한 판단이다. 응답 하나를 JSON 한 덩어리로 저장하면(`answers_json`) 2단 폼에는 맞지만, 세션별 1문항으로 바꾸는 순간 구조가 어긋나 마이그레이션이 필요하다. **문항 하나를 행 하나로 두면 두 형태가 같은 테이블에 들어간다** — 세션별은 `session_id`를 채우고, 행사 전체 문항은 비운다. 설문 구조는 아직 정해지지 않았고(FE-4에서 정한다), **정해지지 않은 것을 스키마로 못 박지 않는 것**이 여기서의 요점이다.

부작용으로 중복 응답 방지가 필요해졌다. 같은 응답자가 같은 문항에 두 번 답하면 응답률 집계가 왜곡되는데, 응답률은 이 제품의 핵심 지표다. SQLite의 UNIQUE는 NULL을 서로 다른 값으로 보므로 `IFNULL(session_id, -1)`로 접은 표현식 인덱스를 걸었다. 로컬 D1에서 두 번째 삽입이 `SQLITE_CONSTRAINT_UNIQUE`로 거부되는 것을 확인했다.

**왜 자료에 `pending` 상태가 필요한가** — 연자가 제때 도착하지 않아 강의자료 업로드가 늦어졌다. 자료 목록은 파일이 도착하기 전에도 존재해야 하고(제목은 미리 안다), 그 상태가 **빈 목록과 구분**돼야 한다. 빈 목록은 결함처럼 보이지만 "준비 중"은 상태다.

**왜 status 컬럼에 CHECK 제약을 걸지 않았나** — `초안|검수대기|공개예정|진행중|완료|보관`은 값이 고정적이라 CHECK를 걸고 싶었다. 걸지 않은 이유는 SQLite에서 **CHECK 변경이 테이블 재생성**이기 때문이다. 상태 목록은 제품 정의라 바뀔 여지가 있고, 그때마다 데이터 이관을 하는 것은 이득에 비해 비싸다. 검증은 애플리케이션 층에 둔다.

**왜 이벤트 로그에 `created_at` 단독 인덱스를 두는가** — [[0002-cloudflare-free-tier-stack]]이 30일 보존 후 삭제 Cron을 요구한다. 로그는 방치하면 무한 증가하고, 삭제 쿼리는 `created_at < ?`로 스캔한다. **삭제 경로를 스키마 단계에서 준비해 두지 않으면 나중에 지우는 것 자체가 비싸진다.**

## 결과·트레이드오프

**얻는 것** — FE-8(프리셋 축적)·FE-4(설문 흐름 재설계)·FE-6(현장 업로드)이 스키마 변경 없이 착수 가능하다. BE-3~6은 테이블이 이미 있으므로 엔드포인트만 쓰면 된다.

**감수하는 것**
- **아직 병합되지 않은 문서를 근거로 삼았다.** 이 ADR이 인용하는 실무 경험의 정본은 `llm-wiki/Reference/field-experience.md`인데, 지금은 `docs/problem-redefinition` 브랜치에만 있다. **그 브랜치가 병합되기 전까지 여기 근거의 출처를 `main`에서 확인할 수 없다.** 병합 후 위키 링크로 바꿔야 한다.
- **아직 쓰이지 않는 테이블이 넷 있다.** `questions` `survey_responses` `event_logs` `brand_presets`는 BE-3~6과 FE-8에서 비로소 쓰인다. 미리 만든 이유는 위와 같지만, 실제로 붙일 때 컬럼이 모자랄 가능성은 남는다.
- **`preset_id`가 FK인데 `brand_presets`는 아직 비어 있다.** 현재 프리셋은 코드 상수(`lib/theme.ts`)이므로, FE-8 전까지는 시드로 채우거나 NULL로 둔다.
- **D1의 FK 강제 여부에 의존한다.** CASCADE 삭제가 로컬에서는 동작함을 확인했으나(이벤트 삭제 시 세션 동반 삭제), 원격 D1에서도 같은지는 BE-2 배포 때 재확인해야 한다.

## 재검토 트리거

- **FE-4가 설문 구조를 확정할 때** → 문항 단위 설계가 실제로 그 구조를 담는지 확인. 담지 못하면 이 ADR의 핵심 근거가 무너진 것이다.
- `docs/problem-redefinition` 병합 시 → 근거 출처를 위키 링크로 교체.
- BE-2 배포 시 → 원격 D1의 FK 동작, `wrangler.jsonc`의 `database_id` 치환.
- 이벤트 로그가 예상보다 빨리 커질 때 → 보존 기간 단축 또는 사전 집계 테이블 도입 검토([[0002-cloudflare-free-tier-stack]]는 데모 규모에서 사전 집계를 하지 않기로 했다).
