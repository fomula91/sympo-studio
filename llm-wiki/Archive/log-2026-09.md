- **[BE] BE-8 — Q&A 폴링 GET 읽기 통제 + POST 왕복 절감**: FE-3이 4초 폴링을 실제로 띄우면서 "폴링이 무료 티어를 소진"이 가설에서 현재 위험이 됐다(PR #9 리뷰). GET에 3층을 넣었다: ① 존재 확인과 목록 조회를 batch로 묶어 **요청당 D1 왕복 1회**, ② `Cache-Control: public, max-age=3` — **읽기 티어를 실제로 줄이는 건 이것뿐이다**(참가자 100명이 4초 폴링하면 같은 URL에 초당 25건이 몰리는데 엣지가 창당 1건만 오리진에 넘긴다), ③ `?since=<createdAt>` 커서와 ETag/304. **`since`와 ETag의 효과를 구분해 기록**: `since`는 D1이 인덱스 범위 끝만 읽게 하지만, ETag는 태그를 계산하려면 어차피 조회해야 해서 **바이트만 아끼고 읽기는 그대로다**. 셋 다 선택이라 기존 클라이언트가 안 깨진다(`since` 없으면 전체 윈도우). POST는 이벤트 조회와 rate limit 판정을 batch로 묶어 왕복 2→1 — 403으로 끝나는 무효 POST도 읽기 1회다. 이를 위해 판정을 `rateLimitStatement`(쿼리만 만듦)와 `evaluateRateLimit`(행을 정책과 대조)으로 갈랐고 `assertRateLimit`은 둘의 합성으로 남겨 설문 라우트는 무수정·동작 불변. `survey/summary`에도 `max-age=5` — 처음엔 "운영자가 열어 보는 화면이라 폴링 대상 아님"으로 캐시를 뺐는데 **그 전제가 틀렸다**(분포 쿼리가 응답 행을 전부 GROUP BY로 훑어 요청 하나가 응답 수에 비례해 읽는다). **닫지 못한 것을 정직하게 남겼다**: 무효 POST는 왕복만 줄었을 뿐 *제한되지 않는다* — 판정이 행을 세는 구조라 한 번도 성공 못 한 클라이언트는 셀 행이 없다. 이 한계와 60초 창 해머링·판정 SELECT 2000행 스캔이 전부 같은 뿌리라 **BE-17**(rate limit을 (키,창) 카운터로 전환할지 ADR로 결정)로 묶어 등록했다. 로컬 실측: 캐시 헤더·ETag 확인, `If-None-Match` → 304 0바이트, `since=마지막` → 0건 / `since=과거` → 3건 / 형식오류 400, 회귀 전부 불변(60초 4건째 429, 토큰 없음 강등 4건째 429, qa off 403, null 본문 400, 없는 이벤트 404), summary `max-age=5`. lint·build 통과. **배포(버전 `4e1d118d`, Cron 유지) 후 프로덕션 실측 완료**: 캐시 헤더·ETag, `If-None-Match` → 304 0바이트, `since=마지막` → 0건, `since` 형식오류 400, 같은 토큰 4연타 429(첫 시도는 토큰을 3개 다르게 써서 201이 나왔는데 이는 버킷이 각각 독립인 정상 동작 — 테스트가 틀렸던 것), summary `max-age=5`, 스모크 이벤트 DELETE 정리. **BE-8 종료.**
