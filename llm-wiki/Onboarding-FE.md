# 프론트엔드 담당자 진입 문서

이 프로젝트에 합류했다면 여기부터 읽는다. **위키 전체를 읽지 말 것** — 아래 순서대로 필요한 만큼만 본다.

## 1. 이 프로젝트가 무엇인가

제약 심포지엄 마이크로사이트를 만들고 운영하는 스튜디오. 운영자가 콘솔에서 행사를 관리하고, 에디터에서 아젠다·자료·참여·테마를 편집하면 참가자용 마이크로사이트에 즉시 반영된다.

**채용용 포트폴리오**이며, 리포지토리 히스토리도 심사 대상이다. 그래서 커밋과 문서에 지켜야 할 규칙이 몇 가지 있다(아래 4절).

## 2. 읽는 순서

| 순서 | 문서 | 왜 |
|---|---|---|
| 1 | [[Context]] | 지금 무엇을 만드는가. 스택·디렉터리 구조·핵심 판단이 한 장에 있다 |
| 2 | [[field-experience]] | **문제 정의의 정본.** 무엇을 직접 겪었고 무엇을 겪지 않았는가 |
| 3 | [[Next-Tasks]] | 열린 과제. `FE-`로 시작하는 것이 당신 몫이다 |
| 4 | `README.md` | 외부에 보이는 얼굴. 문서를 고칠 때 여기와 어긋나지 않게 |
| 5 | [[index]] | 그 밖에 필요한 것을 찾을 때의 지도 |

ADR(`Decisions/`)은 전부 읽지 말고, 과제에서 링크로 걸린 것만 그때 본다.

**서버에 붙는 과제(FE-3·FE-5, FE-2의 `/[slug]` 등)를 잡았다면 [[API-Guide-FE]]가 엔드포인트·에러 규약의 정본이다** — 응답의 `error` 문구는 화면에 그대로 노출해도 되게 작성돼 있으니 별도 매핑을 만들지 말 것.

## 3. 지금 착수할 수 있는 것

FE 과제는 **서로 독립**이라 순서 없이 아무거나 잡아도 된다. 다만 대부분 대응하는 BE 과제에 의존하므로, **서버 없이 지금 바로 되는 것**은 다음이다.

- **FE-2** 라우트 분리 + 폰트 자체 호스팅
- **FE-7** 대비비 저장 게이트 실장
- **FE-8** 브랜드 컬러를 대표 이미지에서 추출 + 프리셋 축적
- **FE-9** 네트워크 단절 대응
- **FE-4**의 수료증 생성 부분 (`pdf-lib` 클라이언트 생성)

각 과제의 `무엇 → 왜 → 완료 기준`은 [[Next-Tasks]]에 있다. **`왜`를 먼저 읽을 것** — 이 프로젝트는 무엇을 만드는지보다 왜 그렇게 만드는지가 결과물이다.

## 4. 지켜야 할 규칙

### 문제를 서술할 때
**[[field-experience]]에 없는 내용을 "관찰"이나 "실무에서 겪은 일"로 쓰지 않는다.** 기존 README가 정확히 그 방식으로 무너졌다 — 실무 확인 없이 화면에서 역산해 문제를 지어냈고, 네 항목 중 셋이 사실과 달랐다([[0004-problem-redefinition]]). 검증되지 않은 것은 **가설이라고 표기**한다.

### 작업이 끝나면
[[log]]의 오늘 날짜 섹션(`## YYYY-MM-DD`)에 기록한다. 형식은 **`- **[FE] 제목**: 내용`** — 태그를 빠뜨리지 말 것. 코드를 고쳤는데 오늘 기록이 없으면 Stop 훅이 경고한다. 로그는 코드와 **같은 커밋**에 넣는다.

무엇을 썼는지가 아니라 **왜 그렇게 했고 무엇을 확인했는지**를 쓴다. 제목만 봐도 무슨 일이 있었는지 알 수 있게.

### 과제를 추가·종료할 때
`### FE-N. 제목` 형식을 지킨다. **이 접두사가 훅 파싱 계약이다** — 없으면 세션에 주입되지 않는다. 번호는 FE·BE 각각 독립이며, **과제가 끝나도 남은 번호를 다시 매기지 않는다**(로그·ADR의 참조가 깨진다). 종료된 과제는 종료 기록 표로 옮긴다.

### 커밋
- **`Co-Authored-By: Claude` 트레일러를 넣지 않는다.** 히스토리도 심사 대상이다.
- 브랜치를 파고 작업한다. `main` 직접 커밋은 하지 않는다.
- 위키 기록을 코드와 함께 커밋한다.

### 설계 결정을 내렸을 때
되돌리기 비싼 판단은 `Decisions/NNNN-*.md`에 ADR로 남긴다. 형식은 `Decisions/0000-adr-template.md`. **기각한 대안과 그 이유**를 반드시 쓴다 — 그게 ADR의 절반이다.

## 5. 검증

공식 검증 입구는 아직 없다. 아래 두 명령이 전부이며, 우회 실행(`npx tsc` 단독 등) 대신 npm 스크립트를 쓴다.

```bash
npm run lint     # 컴포넌트·lib 등 TS/TSX를 고쳤으면 최소 이것
npm run build    # 라우팅·설정까지 건드렸으면 이것 (타입 검사 포함)
npm run dev      # UI 동작은 브라우저로 직접 확인 (자동 테스트 없음)
```

실패하면 원인부터 가른다. `Type error:`나 `✖ N problems`는 코드 문제, `command not found`·`Cannot find module`은 환경 문제(`npm install`), `EADDRINUSE`는 기존 dev 서버를 끄면 된다. **환경 문제를 코드로 고치려 들지 말 것.**

자동 테스트가 없는 것은 알려진 한계다. FE-7이 Vitest 도입의 첫 지점이 된다.

## 6. 알아두면 좋은 것

- **에디터 프리뷰와 참가자 뷰어는 같은 `Microsite` 컴포넌트를 공유한다.** 이게 이 프로젝트에서 가장 마음에 드는 설계 판단이라 README에도 적혀 있다. 프리뷰용 별도 구현을 만들지 말 것.
- **스타일이 인라인 + OKLCH 리터럴이다.** 디자인 프로토타입 충실도를 우선한 결과이며 hover는 `app/globals.css`의 헬퍼 클래스로 우회한다. 정리 방향은 Microsite를 CSS 변수로, 스튜디오 셸을 Tailwind로 나누는 것이지만 아직 과제로 등록돼 있지 않다.
- **데이터는 전부 가상이다.** 브랜드·인물·소속기관·의약품·행사장 모두 지어낸 것이며, 실존으로 보이는 값을 새로 넣지 않는다.
- **리포트 수치는 샘플이다.** 실측으로 바뀌기 전까지 `샘플 데이터` 배지를 유지한다.
