# sympo-studio — 과제

앞으로 할 일 전체의 정본. **에이전트용 고밀도 문서**이고, 사람이 읽고 바로 착수할 판단은 → **[[Summaries/Next]]**

## 과제와 Next-Task의 관계

```
과제 (이 문서 전체)
├── Next-Task ······· 핫픽스 · 긴급 · 꼭 필요한 것.  먼저 처리한다
├── 열린 과제 — FE ·· 나머지 프론트엔드 백로그
└── 열린 과제 — BE ·· 나머지 백엔드 백로그
```

- **과제**는 총칭이다. 아래 세 섹션에 있는 것이 전부 과제다.
- **Next-Task**는 과제 중 **지금 먼저 해야 할 것**만 골라 담는 자리다. 아래 셋 중 하나에 해당하면 여기 적는다.

| 넣는 기준 | 뜻 |
|---|---|
| **핫픽스** | 배포된 것이 실제로 깨져 있다 |
| **차단** | 이게 정해지지 않으면 다른 과제를 착수할 수 없다 |
| **필수** | 이미 완료 기준을 어기고 있거나, 사용자에게 드러나는 결함이다 |

- **새 과제는 기본적으로 FE/BE 백로그에 넣는다.** 위 기준에 맞을 때만 Next-Task로 올린다 — 전부 급하면 아무것도 급하지 않다.
- Next-Task도 **똑같은 과제**라 번호 체계(`FE-N`/`BE-N`)를 공유한다. 급한 상태가 풀리면 백로그로 내리고, 끝나면 [[Archive/Closed-Tasks]]로 옮긴다.

> **형식 계약 (훅이 파싱한다)** — 과제 제목은 `### FE-N. 제목` / `### BE-N. 제목`.
> SessionStart 훅은 **`## 열린 과제`로 시작하는 섹션**의 `### FE-`·`### BE-` 줄만 추출해 주입한다. 그래서 세 섹션 제목이 전부 `## 열린 과제`로 시작한다 — **바꾸면 그 섹션이 통째로 주입에서 빠진다.** 파일명 `Next-Tasks.md`도 훅이 하드코딩해 읽으므로 바꾸지 않는다.
> 섹션 헤더는 주입되지 않아 **제목의 `FE-`/`BE-` 접두사가 유일한 구분자**다. 추출이 0건이면 형식 오류 문구가 대신 주입된다.
> 새 과제는 `무엇 → 왜 → 완료 기준`으로 쓴다. **남은 번호를 다시 매기지 않는다**(로그·ADR 참조가 깨진다).
> 근거 [[0003-next-tasks-fe-be-split]] · 작성 규칙 본문은 `CLAUDE.md`의 「Next-Tasks 작성 규칙」.

문제 정의의 정본은 [[field-experience]]다. 과제의 `왜`를 쓸 때 **거기 없는 내용을 근거로 삼지 않는다** — 기존 README가 그렇게 무너졌다([[0004-problem-redefinition]]).

## 열린 과제 — Next-Task (먼저 처리한다)

핫픽스·차단·필수에 해당하는 것만 여기 둔다. 급한 상태가 풀리면 아래 백로그로 내린다.

### FE-26. 자료 뷰어 오버레이 접근성 — role="dialog" + 포커스 트랩
**무엇** — `PdfViewer.tsx`의 전체화면 오버레이에 `role="dialog"`·`aria-modal="true"`를 추가하고, 열릴 때 첫 컨트롤로 포커스를 옮기고 Tab이 오버레이 안의 컨트롤(축소·확대·이전·다음·닫기)만 순환하도록 포커스 트랩을 건다.
**왜** — 지금은 배경이 `rgba(0,0,0,0.72)`로 시각적으로만 가려질 뿐이라, 키보드로 계속 Tab하면 포커스가 뒤에 가려진 Q&A/설문 버튼으로 넘어가 보이지 않는 요소를 조작할 수 있다(PR #39 `/code-review` 발견).
**완료 기준** — 뷰어가 열리면 포커스가 오버레이 안으로 이동하고, Tab·Shift+Tab이 오버레이 컨트롤 사이에서만 순환한다(뒤의 Q&A/설문 버튼으로 못 넘어감). 스크린리더가 오버레이를 대화상자로 인식한다. 기존 Esc 닫기 동작 회귀 없음.

### FE-28. doc_view 로그 중복 방지
**무엇** — `Microsite.tsx`의 `openDocument`가 열 때마다 조건 없이 `doc_view` 로그를 보낸다. `session_view`가 `seenSessionsRef`로 하는 것처럼 같은 방문 내 중복 열람을 한 번으로 셀지 결정하고 구현(또는 "매번 세는 게 의도"라면 그 판단을 기록).
**왜** — 참가자가 같은 자료를 여러 번 다시 열 때마다 조회수가 부풀어 `/ops`의 자료별 `hits`가 실제 순유효 방문자 수를 왜곡한다(PR #39 `/code-review` 발견 — `Microsite.tsx`의 기존 주석이 이걸 "FE-6·FE-4가 붙일 때 판단할 것"으로 이미 표시해뒀었다).
**완료 기준** — 같은 문서를 같은 방문에서 여러 번 열어도(또는 의도적으로 매번 세기로 했다면 그 근거와 함께) `/ops` 수치가 정한 정책과 일치함을 실측으로 확인.

### BE-26. 계정 연결을 이메일에서 끊는다 + 인증 콜백 잔여 3건
**무엇** — ① **`upsertUser`의 이메일 자동 연결을 없앤다.** 지금 `lib/auth.ts`가 `SELECT id FROM users WHERE email = ?`로 **이메일이 같으면 기존 계정에 제공자를 잇는다**(주석: "나중에 GitHub 등을 붙일 때 같은 사람이 계정 두 개로 갈리지 않게"). 연결 키를 `oauth_accounts(provider, provider_account_id)` **하나로만** 두고, 같은 이메일의 다른 계정이 있으면 잇지 말고 별개 계정으로 만들거나 명시적 연결 흐름을 요구한다. ② **`upsertUser`의 비원자성** — `SELECT` → `INSERT users` → `INSERT oauth_accounts`가 따로 돌아, 중간에 실패하면 **oauth 링크 없는 고아 user 행**이 남고 다음 로그인이 또 이메일 매칭으로 흘러간다. D1 `batch`로 묶는다. ③ **콜백 `catch`가 `ApiError`만 접는다** — 그 밖의 예외는 500 스택으로 새어 로그인 화면 대신 에러 페이지가 뜬다. ④ **`error=` 분기가 state 검증보다 먼저 돌고 쿠키를 지운다** — `app/api/auth/callback/google/route.ts:34`의 `if (sp.get('error')) return fail('cancelled')`가 `fail()`을 타는데, `fail()`은 `state`·`redirect` 쿠키를 **만료**시킨다. 공격자가 피해자 브라우저를 `/api/auth/callback/google?error=x`로 보내면(이미지 태그·리다이렉트로 충분) 진행 중이던 로그인의 state 쿠키가 지워져 **정상 로그인이 "state 쿠키 없음"으로 실패**한다. 남의 콜백인지 먼저 가려낸 뒤 쿠키를 지운다.
**왜** — ①은 **계정 탈취 경로**다. Codex 교차 리뷰가 내 `email_verified` 판단을 명시적으로 반박했다([[log]] 2026-09-11) — Google 문서가 이메일은 바뀔 수 있으니 계정 식별자로 쓰지 말라고 하고, `upsertUser`는 로그인 시 이메일을 갱신하지도 않으므로 **불린 하나를 켜는 것으로는 못 막고 자동 연결 자체를 없애야 한다.** ④는 로그인을 외부에서 방해할 수 있는 경로다. BE-12가 "코드리뷰 반영"으로 5건을 닫을 때 **이 넷은 "BE-13에서 인가 경계를 손댈 때 함께"로 미뤄졌는데, BE-13의 `무엇`에 실제로 적히지 않아 사라질 뻔했다**(이번 위키 정리에서 발견). 인가 경계(BE-13)와 성격이 달라 따로 세운다 — 이건 **인증(누구인가) 계층**이지 인가(무엇을 할 수 있는가)가 아니다.
**완료 기준** — 같은 이메일을 가진 별개 Google 계정 두 개(또는 `users`에 수동으로 넣은 동일 이메일 행)로 로그인했을 때 **기존 계정에 자동으로 붙지 않는 것**을 실측. `upsertUser` 중간 실패를 주입해도 고아 `users` 행이 남지 않음. 콜백에서 `ApiError`가 아닌 예외를 던져도 `/console?auth=...`로 접힘. **진행 중인 로그인이 있는 상태에서** `?error=x`로 콜백을 때려도 원래 로그인이 정상 완료됨. `npm run test` 통과.

### BE-29. 업로드 남용 통제 — R2 증폭 차단
**무엇** — `PUT /api/events/[id]/documents/[docId]/upload`에 rate limit을 건다. 지금 **rate limit이 한 줄도 없다** — 적용된 라우트는 `logs`·`survey`·`questions` 셋뿐이다. 게다가 데모 이벤트는 `owner_id IS NULL`이라 `assertCanEdit`가 **누구든 통과시킨다**(게스트 체험이 여기 기대므로 의도된 설계다). 그래서 **아무나 20MB PDF를 무제한으로 올릴 수 있다.** `lib/rate-limit.ts`를 재사용하되 키를 정하고(익명이 정상 경로라 user_id를 못 쓴다 — `x-client-token` + IP 2층이 맞을 가능성이 높다, [[0006-rate-limit-key]]·[[0008-rate-limit-counter]]), **이벤트당 누적 바이트 상한**도 함께 판단한다. 파일당 20MB·이벤트당 자료 60개라는 기존 상한은 **한 번에 올릴 수 있는 양**만 막지 같은 문서에 반복해 덮어쓰는 것은 막지 않는다.
**왜** — **이 프로젝트는 "무료로 오래 유지"가 하드 제약이고 R2 때문에 결제 수단이 실제로 등록돼 있다**([[Context]]). 안전장치가 "카드 미등록"에서 "사용량 알람 + 코드 상한"으로 바뀐 순간부터 **코드 상한이 유일한 방어선**인데, 업로드 경로에 그 상한이 비어 있다. 자정 Cron의 고아 객체 정리는 **문서 행에 붙어 있는 파일은 고아가 아니라서 못 지운다** — 즉 지금은 상한도 회수 경로도 없다. Codex 교차 리뷰가 "R2 증폭"으로 지목했고 BE-13 범위로 미뤄졌으나 실제로는 등록되지 않았다([[log]] 2026-09-11).
**완료 기준** — 같은 문서에 연속 업로드 시 정해진 횟수에서 429와 **사유가 응답에 드러남**. 정상 현장 업로드 시나리오(자료 몇 개를 연달아 올림)는 막히지 않음 — 실무에서 연자가 늦게 도착해 행사 중에 올리는 것이 정상 경로다([[field-experience]]). 프로덕션에서 실측. README「알고 있는 한계」의 R2 서술 갱신.

서로 독립이라 순서 없이 착수할 수 있다.

### FE-27. PdfViewer 리소스 정리 — 언마운트 시 렌더 취소 + 재오픈 캐싱
**무엇** — 같은 컴포넌트의 같은 effect 근처를 건드리는 두 가지를 묶는다. ① 페이지 렌더 effect의 cleanup이 `cancelled = true`만 설정하고 `renderTaskRef.current?.cancel()`을 부르지 않아, 컴포넌트가 언마운트돼도 진행 중이던 pdf.js 렌더가 이미 분리된 canvas에 계속 그려진다 — cleanup에서 명시적으로 취소한다. ② 같은 문서를 닫았다 다시 열면(또는 스튜디오 미리보기의 두 `DEMO_DOCUMENTS`가 같은 데모 PDF를 가리키는 경우) `pdfjsLib.getDocument`가 매번 파일을 새로 내려받아 다시 파싱한다 — 마운트 간에 로드된 `PDFDocumentProxy`를 재사용할지 판단하고 구현(또는 재사용하지 않기로 한 근거를 남김).
**왜** — ①은 불필요한 CPU/GPU 낭비, ②는 불필요한 네트워크 요청·파싱 반복이다(PR #39 `/code-review` 발견).
**완료 기준** — 페이지 전환 직후 뷰어를 닫아도 진행 중이던 렌더가 실제로 취소됨을 확인(콘솔·프로파일러). 같은 문서를 닫았다 다시 열 때 네트워크 탭에 중복 다운로드가 없거나, 캐싱을 하지 않기로 했다면 그 판단 근거를 기록.

### FE-29. 자료 카드를 네이티브 `<button>`으로 리팩터
**무엇** — `Microsite.tsx`의 자료 카드가 `role="button"`·수동 `tabIndex`·직접 구현한 Enter/Space `onKeyDown`으로 버튼 의미를 재구현하고 있다. 네이티브 `<button disabled>`로 바꿔 pending·url 없음 상태를 플랫폼 차원에서 강제한다(기존 카드 룩은 스타일 리셋으로 유지).
**왜** — 지금은 `unavailable` 재확인을 `openDocument` 안에서 손으로 하고 있어, 앞으로 부모에 클릭 핸들러가 얹히거나 그 재확인을 빼먹으면 비활성 상태가 뚫릴 수 있다(PR #39 `/code-review` 발견) — 네이티브 `disabled`면 이런 실수가 구조적으로 불가능하다.
**완료 기준** — `<button>`으로 교체된 뒤에도 기존 시각 스타일 회귀 없음(교체 전후 스크린샷 대조). 키보드 Tab·Enter로 정상 동작. `disabled`일 때는 클릭 이벤트 자체가 발생하지 않음(핸들러 안의 재확인 없이).

### FE-17. 참가자 화면 탭바가 장식용이고 engage.chat·engage.cert가 어디서도 안 쓰임
**무엇** — `Microsite`의 상단 탭바(아젠다·자료·Q&A·설문)가 `onClick` 없는 순수 장식 요소라 실제 탭 전환이 없고(모든 섹션이 한 페이지에 죽 이어져 스크롤됨), 어떤 `engage` 토글을 꺼도 탭 4개가 그대로 보인다. `engage.chat`("현장 채팅")은 코드베이스 어디에도 소비하는 화면이 없고(채팅 기능 자체가 아직 없음), `engage.cert`("수료증 자동 발급")도 참가자 화면에 연결된 적이 없다(수료증 생성 자체는 FE-4에서 구현됐지만 지금은 스튜디오 미리보기 전용, FE-3/FE-4 로그 참고). 탭 전환 UI를 실제로 만들거나(토글 꺼진 탭 숨김 포함), 최소한 꺼진 토글의 탭은 안 보이게라도 하는 범위 결정 필요.
**왜** — PR #9 최종 코드리뷰(2026-09-02)가 발견. 다만 확인해보니 **이번 작업으로 생긴 회귀가 아니라 Microsite가 처음 만들어질 때부터 있던 특성**이다 — FE-3(Q&A)·FE-4(수료증)는 각자의 섹션 안 콘텐츠만 실제로 연결했을 뿐, 탭바 자체의 전환 기능은 손댄 적이 없다. 실제 채팅 기능 구현은 이 과제들과 별개의 큰 작업이라 지금 범위에 욱여넣지 않았다.
**완료 기준** — 범위 결정(탭 전환을 실제로 만들지, 꺼진 토글만 숨길지) 후 그에 맞는 완료 기준을 다시 씀. `engage.chat`은 실제 채팅 UI가 없는 한 토글 노출 자체를 재검토(만들 계획이 없다면 EngageSection에서 뺄지 결정).

### FE-13. 디자인 시스템 문서화 + 공용 컴포넌트 라이브러리
**무엇** — 두 갈래를 한 과제로 묶는다(서로 맞물려 있어 쪼개면 순서 의존이 생긴다). ① **디자인 시스템**: [[design]]을 컨셉 문서에서 실행 규격으로 승격 — `globals.css`의 CSS 변수 토큰(라이트/다크 페어 전체)을 이름·용도·대비비 기준과 함께 표로 정의하고, 타이포 스케일·간격·라운드·그림자 단계를 코드와 1:1로 맞춘다. 상태 의미색(진행중/검수대기 등)의 **다크 페어를 이번에 정의**한다(알려진 갭, [[log]] 2026-08-19). ② **공용 컴포넌트**: `lib/ui.ts`의 스타일 객체(`ghostBtn`/`primaryBtn`/`seg`/`pillStyle`)와 화면마다 반복되는 인라인 패턴(카드, 섹션 제목, 입력 필드, 상태 배지, 빈 상태)을 `components/ui/`의 실제 React 컴포넌트로 추출하고, 셸 화면 4곳이 이를 사용하도록 교체한다. **참가자 마이크로사이트는 범위 밖** — 행사 테마는 런타임 파생이라 도구 색 체계와 섞지 않는다([[design]] 색 분리 원칙). **BE 의존 없음.**
**왜** — 토큰은 CSS 변수로 체계화됐지만 컴포넌트 층이 없어서, 같은 카드·배지·버튼이 화면마다 인라인 스타일로 복제돼 있다. 다크모드 배지 갭이 정확히 이 구조의 비용이다 — 스타일이 한 곳에 있었다면 페어 하나 추가로 끝났을 일이 전 화면 수색이 됐다. FE 담당자와의 협업에서도 "어떤 색·컴포넌트를 쓰면 되는가"의 정본이 없으면 회신 왕복이 생긴다. README가 이미 인라인 스타일을 트레이드오프로 명시하고 정리 방향을 예고한 상태다.
**완료 기준** — [[design]]에 토큰 표(라이트/다크 전체)와 컴포넌트 목록·사용 규칙이 실림. `components/ui/`의 컴포넌트로 셸 4개 화면의 해당 패턴이 교체되고 시각 회귀 없음(교체 전후 스크린샷 대조). 상태 배지가 다크모드에서 튀지 않음. lint·build 통과.

### FE-14. FSD(Feature-Sliced Design) 아키텍처 적용
**무엇** — 평평한 `components/` + `lib/` 구조를 FSD 레이어(`app`/`pages`/`widgets`/`features`/`entities`/`shared`)로 재편한다. 먼저 **레이어 매핑 ADR**을 쓰고 나서 옮긴다 — 대략의 방향은: `lib/ui.ts`·`globals.css` 토큰·공용 컴포넌트(FE-13 산출물)→`shared/`, 이벤트·세션·테마 타입과 데이터 접근→`entities/`, Q&A·설문·테마 편집 같은 사용자 행동 단위→`features/`, 셸 화면 4개→`widgets/`+`pages/`. **주의**: Next.js App Router의 `app/` 디렉터리와 FSD의 `app` 레이어 이름 충돌, 그리고 `Microsite`(에디터 프리뷰와 참가자 뷰어가 같은 컴포넌트를 공유하는 이 프로젝트의 핵심 설계)가 어느 슬라이스에 속하는지를 ADR에서 반드시 결정한다. 이동은 **한 번에 전부가 아니라 레이어 단위로** 진행하고 각 단계마다 build를 통과시킨다. FE-2(라우트 분리)·FE-13(공용 컴포넌트)과 같은 파일을 건드리므로, **착수 시점에 그 둘이 진행 중이면 완료를 기다리거나 흡수 범위를 명시**한다. **BE 의존 없음.**
**왜** — 화면이 4개일 때는 평평한 구조가 싸지만, 열린 과제들(Q&A 연결, 설문 재설계, PDF 뷰어, 오프라인 대응)이 전부 "화면 조각 + 상태 + API 호출"을 한 덩어리씩 추가하는 성격이라 지금 구조로는 `components/`와 `lib/`이 기능 경계 없이 섞이며 자란다. FE 담당자와의 분업에서도 "이 기능은 이 폴더"라는 소유 경계가 있어야 충돌 없이 병렬 작업이 된다. 레이어의 단방향 의존 규칙은 프리뷰=실물 같은 구조적 보장을 지키는 데도 유리하다.
**완료 기준** — 레이어 매핑 ADR(`Decisions/`)이 있고 실제 구조가 그와 일치. import 방향이 FSD 규칙(상위→하위만)을 지키는지 eslint 규칙(예: `import/no-restricted-paths` 또는 steiger)으로 강제되고 위반 0건. 기존 화면 동작·시각 회귀 없음(스크린샷 대조). lint·build 통과.

### FE-25. 현장 업로드 UI — 자료를 실제 D1 이벤트에 연결
**무엇** — 운영자가 태블릿에서 강의자료 PDF를 올리는 화면. `PUT .../documents`(메타)·`PUT .../documents/[docId]/upload`(파일, BE-6) 둘 다 서버는 이미 동작한다 — FE-6 작업 중 curl로 직접 호출해 왕복까지 확인했다. **빠진 것은 그걸 호출하는 운영자 화면뿐**이다. `EditorScreen.tsx`의 `DocsSection`은 지금 완전히 정적 목업(`DOCS` 상수)이고, `app/(studio)/events/[id]/edit/page.tsx`도 로컬 `useStudio()` 목업을 참조할 뿐 실제 D1 이벤트에 연결된 적이 없다 — FE-5·FE-19·FE-23이 반복해서 부딪힌 것과 같은 구조적 원인. 착수 전 스튜디오↔D1 연결 범위(FE-15 ①④류 작업, 또는 FE-3/FE-5처럼 slug로 실제 이벤트 하나를 지목하는 별도 경로)부터 정해야 한다.
**왜** — 원래 FE-6("PDF.js 뷰어 + 현장 업로드")의 절반이었으나, 뷰어는 스튜디오 연결 없이 바로 만들 수 있었고 업로드는 그 연결이 선행돼야 해서 사용자와 상의해 분리했다([[log]] 2026-09-14). 실무에서 **연자가 늦게 도착해 자료가 행사 진행 중에 올라온다**([[field-experience]]) — 업로드는 사무실이 아니라 현장에서, 운영자가 직접 하는 동작이다.
**완료 기준** — 태블릿 화면에서 자료 등록(메타)→파일 업로드까지 완주 가능. 올린 즉시(새로고침 없이) 참가자 화면(`/[slug]`)에 반영. 실패 시 사유가 화면에 드러남.

### FE-23. 공개하기 버튼이 실제 공개 액션이 아님 — 상태 전환·공개 URL·비공개 되돌리기
**무엇** — 에디터 헤더의 `공개하기`(`StudioShell.tsx:243`)가 지금 하는 일은 `openViewer()` → `patch({ viewerOpen: true })`가 전부다. **미리보기 오버레이만 열릴 뿐 서버로 나가는 요청이 하나도 없고, 이벤트 상태도 그대로이며, 참가자에게 줄 주소가 화면 어디에도 나타나지 않는다.** 필요한 동작 세 가지:

| 순서 | 동작 |
|---|---|
| ① | 누르면 `PATCH /api/events/[id]`로 `status`를 `공개`로 올린다 |
| ② | 성공하면 공개 URL(`/{slug}`)을 화면에 띄운다 — 복사 버튼 포함 |
| ③ | 버튼이 `비공개`로 바뀌고, 다시 누르면 `status`를 비공개 상태(`초안`)로 되돌린다 |

**서버는 이미 준비돼 있다 — 새 BE 작업 불필요.** BE-23이 상태 모델을 발행 상태 4종(`초안`·`검수대기`·`공개`·`보관`)으로 재정의하고 쓰기 검증까지 넣었다([[0009-event-status-axes]]). 참가자 경로는 `PUBLIC_STATUSES = {공개}`로 게이트돼 나머지 셋이면 `/{slug}`가 **404**로 떨어진다(`assertPublicEvent`). 즉 FE가 `공개`·`초안`만 올바르게 보내면 공개/비공개가 그대로 작동하고, 목록 밖의 값은 서버가 400으로 막아준다.

**선행 판단 필요** — 스튜디오의 `ev`는 `useStudio()`가 들고 있는 로컬 목업(`SEEDED_EVENTS`)이라 **D1 이벤트 id가 아니다**(FE-5·FE-19·BE-20이 반복해서 부딪힌 그 원인). 목업 id를 그대로 `PATCH`에 실으면 남의 이벤트를 건드리거나 404가 난다. 범위를 ⓐ 스튜디오를 서버 워크스페이스에 연결한 뒤 착수(FE-15 ①④ 이후)할지, ⓑ FE-3·FE-5가 쓴 방식대로 **실제 공개 이벤트 하나를 slug로 지목하는 경로에서 먼저 성립**시킬지 결정하고 시작한다.
**왜** — 지금은 운영자가 "공개했다"고 믿을 근거가 화면에 없다. 버튼을 눌러도 미리보기만 뜨고, 참가자에게 보낼 주소를 어디서 얻는지 화면이 알려주지 않으며(콘솔 카드의 슬러그는 읽기 전용 텍스트다), 한번 공개한 뒤 내리는 경로는 콘솔 「선택 모드」의 일괄 상태 변경뿐인데 그마저 로컬 목업 상태만 바꾸고 D1에 닿지 않는다(`StudioShell.tsx:333`). **행사 당일 잘못 공개된 페이지를 즉시 내리지 못하는 것은 현장에서 되돌릴 수 없는 종류의 문제다** — 되돌리기가 없는 공개 버튼은 공개 기능이 아니다.
**완료 기준** — `공개하기`를 누르면 `PATCH`가 실제로 나가고(네트워크 탭), **새로고침 후에도 상태가 유지된다**(D1 반영 확인). 화면에 뜬 URL을 복사해 **다른 브라우저**로 열면 참가자 페이지가 열린다. 버튼이 `비공개`로 바뀌고, 누르면 같은 URL이 **404**로 바뀐다(없는 slug와 구분되지 않는 404여야 한다 — 존재를 흘리지 않는 기존 규칙 유지). 대비비 미달(`canPublish === false`)일 때 공개 전환이 막히는 기존 게이트는 그대로 유지된다. 실패 응답(404·400·네트워크 끊김)이 화면에 사유로 드러나고, 실패했는데 버튼만 `비공개`로 바뀌는 일이 없을 것.

### FE-24. 발행 상태를 화면에서 실제로 바꿀 수 있게 한다 (BE-23 재정의 후속)
**무엇** — BE-23이 상태 모델을 두 축으로 갈랐다([[0009-event-status-axes]]) — **발행 상태 4종은 저장·사람이 바꾸고, 행사 시점 3종은 `event_date`에서 파생된다.** 서버·목업·배지·필터 칩은 그 모델로 이미 정렬됐고, 응답에 파생 `phase`도 실려 온다. **남은 것은 "사람이 바꾸는 쪽"의 화면이다.**

| 상태 | 누가/무엇이 바꾸나 | 지금 |
|---|---|---|
| `초안` ↔ `공개` | 운영자 — **FE-23의 공개하기/비공개 버튼이 곧 이 전이다** | FE-23에서 닫힘 |
| `→ 보관` | 운영자 수동. 되돌릴 수 있어야 한다 | 콘솔 「선택 모드」에 있으나 **로컬 목업만 바꾸고 D1에 안 닿는다**(`StudioShell.tsx:333`) |
| `초안` → `검수대기` | **미정** — 검수 요청을 누가 받는가 | 검수자도 승인 동작도 코드에 없다 |
| 행사 시점 | 달력 (파생) | 완료 — 사람이 건드릴 것 없음 |

그래서 이 과제에 남은 것은 둘이다. ① **일괄 상태 변경을 실제 `PATCH`로 연결**한다(FE-23과 같은 선행 판단을 공유한다 — 스튜디오 `ev`가 D1 id가 아닌 로컬 목업이다). ② **`검수대기`의 존폐를 결정**한다 — 승인자를 정하려면 BE-12(계정 모델)가 먼저이므로, 그때까지 상태를 남겨둘지 지금 뺄지를 판단한다. **승인자가 필요 없다는 결론이면 빼는 것도 유효한 결과다** — 지키지 않는 상태를 화면에 남겨두는 것이 더 나쁘다.
**왜** — 재정의로 "달력이 정하는 것"은 전부 자동이 됐지만, **사람이 정하는 것을 사람이 바꿀 방법은 여전히 화면에 없다.** 콘솔의 일괄 변경은 새로고침하면 사라진다. `검수대기`는 아무도 지키지 않는 칸으로 남아 있고, 그게 이 과제가 처음 등록된 이유다(FE-17의 장식용 탭바와 같은 종류의 문제).
**완료 기준** — 일괄 상태 변경이 실제 `PATCH`로 나가고 새로고침 후에도 유지된다. `보관`으로 내린 이벤트의 공개 URL이 404가 되고, 되돌리면 다시 열린다. `검수대기` 결정을 [[design]] 또는 ADR에 근거와 함께 남기고, 빼기로 했다면 `EVENT_STATUSES`·배지·필터 칩에서 함께 사라진다(정본이 `lib/status.ts` 하나이므로 한 곳만 고치면 된다). **BE 의존 없음** — BE-23이 끝났다.

### FE-15. 로그인·계정 관리 화면 + 게스트/계정 이원화
**무엇** — ① **게스트 로컬 워크스페이스**: 비로그인 상태의 콘솔·에디터가 `localStorage`에 영속하는 워크스페이스에서 동작한다. 첫 진입 시 클라이언트 시드로 초기화하고, 이후 이벤트 생성·수정·삭제·테마 편집이 전부 로컬에서 완결되며 **새로고침·재방문에도 유지**된다. **서버 데모 이벤트의 id를 참조하는 오버레이로 만들지 않는다** — 자정 Cron 리셋 때 기준이 사라져 조용히 깨진다([[0007-sso-and-account-model]]). ② 헤더에 "Google로 시작하기" / 로그인 후 계정 메뉴(아바타·이름·로그아웃). ③ **게스트 상태를 화면에 드러낸다** — "체험 중 · 이 브라우저에만 저장됩니다" 배너, 공개 URL 발급처럼 서버가 필요한 동작에서만 로그인 유도. ④ **로그인 시 가져오기**: 로컬에 편집분이 있으면 "체험 중 만든 이벤트 N개를 계정으로 가져올까요?"를 묻고, 수락 시 BE-15의 `POST /api/events/import`에 이벤트+테마+아젠다를 묶어 보낸다. 로컬 이벤트는 생성 시점에 **로컬 UUID(`localRef`)를 갖고 있어야** 멱등성이 성립하므로 ①에서 함께 설계한다. 응답의 건별 결과를 받아 **성공한 항목만 로컬에서 제거**하고(남기면 재로그인 때 중복 제안), 실패분은 재시도 경로를 남기며, **slug가 바뀐 이벤트를 화면에 알린다**. 거절 시 로컬 보존. ⑤ 계정 설정 화면 — 프로필(이름·아바타·이메일), 연결된 제공자, 로그아웃, **계정 삭제**(삭제 범위 명시: 내 이벤트·아젠다·자료·질문·설문 응답 전부). ⑥ 로그인 후 원래 있던 화면으로 복귀. **①③은 BE 의존 없음, ②⑤는 BE-12·BE-13 의존, ④는 BE-15 의존.** PR #9(FE-1 이벤트별 상태 분리)가 이 워크스페이스의 상태 층이므로 머지 후 착수한다.
**왜** — 게스트에게 "저장이 안 된다"만 알리고 편집을 휘발시키면 **만져본 결과를 확인할 수 없어 체험 자체가 성립하지 않는다.** 반대로 로그인 벽이 먼저 보이면 ADR 0001이 지키려던 "30초 안에 판단"이 무너진다. 로컬 영속이 두 요구가 만나는 지점이고, **이 과제가 그 양립을 화면에서 판정한다.** 가져오기를 넣는 이유는 사용자 입장에서 **로그인이 잃는 행동이 되어서는 안 되기** 때문이다 — 공들여 만든 것이 로그인으로 사라지면 다시는 로그인하지 않는다.
**완료 기준** — 비로그인으로 이벤트를 만들고 테마를 바꾼 뒤 **브라우저를 닫았다 다시 열어도 그대로 있음**. 로그인 → 가져오기 수락 → **아젠다·테마까지** 서버에 `owner_id`와 함께 저장되고 성공분만 로컬에서 비워짐(가져오기 도중 새로고침해도 중복 생성 0) → 로그아웃 → 게스트 워크스페이스가 중복 없이 빈 상태. 다른 계정으로 로그인하면 남의 이벤트가 목록에 없음. 계정 삭제 후 재로그인 시 빈 상태. 게스트 데이터가 이 브라우저에만 있다는 사실이 화면에 드러남(조용히 사라지지 않게). 모든 운영자 화면에 대해 "게스트에게 어떻게 보이는가"를 확인한 기록을 남김. **`localStorage` 용량 판단 기록**: FE-8의 대표 이미지가 `key_visual`에 base64로 들어가면 5MB에 닿으므로, 이미지 제외·참조·IndexedDB 중 무엇을 골랐는지와 근거.

### FE-19. 키비주얼이 blob: URL이라 새로고침·서버 저장에서 살아남지 못함
**무엇** — `EditorScreen.tsx`가 업로드한 키 비주얼을 `URL.createObjectURL(f)`로만 저장한다(리뷰 후 revoke 누락은 이번에 고침, [[log]]). blob URL은 이 브라우저 탭에서만 유효해 새로고침하면 깨지고, 애초에 서버로 보낼 수 있는 값이 아니다.
**왜** — Claude 코드리뷰(2026-09-02)가 발견. 지금은 스튜디오가 BE-1 CRUD에 연결된 적이 없어(BE-20과 같은 이유) 잠복 상태지만, FE-15의 로그인 시 가져오기나 향후 BE PATCH 연결 시점에 그대로 보내면 참가자 페이지에 키 비주얼이 영영 안 뜬다. base64 인코딩(용량 문제, FE-15의 `localStorage` 5MB 논의와 연결) 또는 실제 파일 업로드(R2, BE-6 확장) 중 선택 필요.
**완료 기준** — BE-1 CRUD 연결 시점(FE-15 전후) 전에 방식 결정. 결정 전까지는 blob URL이 세션을 못 넘긴다는 한계를 알고 있는 상태로 유지.

### FE-18. 대비비 게이트가 실제 키비주얼 이미지 위 텍스트 대비는 검사하지 않음
**무엇** — `lib/theme.ts`의 "히어로 텍스트 / 키 비주얼" 대비비 행은 브랜드 프리셋 색으로 합성한 배경(`oklch(...)`)만 검사한다. 실제 렌더(`Microsite.tsx`)는 운영자가 올린 **임의의 이미지** 위에 반투명 그라디언트(라이트 모드는 검정 18~58%)를 얹고 그 위에 흰 라벨을 그린다 — 흰 배경 이미지를 올리면 실제 대비가 게이트 계산과 무관하게 크게 낮아질 수 있다.
**왜** — Codex CLI 교차 리뷰(2026-09-02)가 발견. "대비비 미달 조합은 만들 수 없다"가 이 제품의 핵심 주장(FE-7)인데, 게이트가 실제로 검사하는 범위와 사용자가 이해하는 범위(키 비주얼 포함 전체 화면)가 다르다는 게 문서화된 적이 없다.
**완료 기준** — 범위 결정 필요: ① 키 비주얼 위 텍스트도 실측하도록 게이트를 확장(캔버스로 이미지 픽셀 샘플링 + 오버레이 합성 후 대비 계산, 상당한 작업)하거나 ② 최소한 "이 게이트는 브랜드 색만 검사하고 업로드 이미지는 검사하지 않는다"는 한계를 UI 문구·README에 명시. 어느 쪽이든 결정 근거를 ADR 또는 [[design]]에 남김.

### FE-31. 추출한 브랜드 색을 참가자 화면이 실제로 쓰게 한다
**무엇** — `app/[slug]/page.tsx`가 서버 응답의 `theme.preset`(`{id, label, h, c}`)을 **버리고** `PRESETS.find((p) => p.id === data.theme.presetId) ?? PRESETS[0]`으로 **빌트인 5종에서만 찾는다**. 그래서 `origin='extracted'` 커스텀 프리셋이 걸린 이벤트는 참가자 화면이 엉뚱한 빌트인 색으로 그려진다. **서버는 이미 내려주고 있다** — BE-20이 `GET /api/public/[slug]`에 `LEFT JOIN brand_presets`를 걸어 `hue`·`chroma`·`label`을 실어 보내고, 응답의 주석도 "값이 있으면 클라이언트는 이걸로 derive하고, null이면 presetId로 빌트인을 찾으라"고 적어 뒀다. **FE가 그 분기를 구현하지 않았을 뿐이다.** `data.theme.preset`이 있으면 그걸로 `derive()`하고, 없을 때만 지금 경로로 폴백한다.
**왜** — **실무에서 넘어오는 건 색상 값이 아니라 이미지다**([[field-experience]]). 대표 이미지에서 색을 뽑아 프리셋으로 쌓는 흐름(FE-8)이 이 문제의 해법인데, **추출한 색이 정작 참가자 화면까지 도달하지 않으면 그 흐름 전체가 성립하지 않는다.** README가 이걸 「알고 있는 한계」의 "문제를 아직 못 푼 것"으로 적고 있으면서 **과제로는 등록되지 않아 아무도 자기 일로 잡지 않은 상태**였다(2026-09-14 발견). `app/[slug]/page.tsx:152` 주석은 "스튜디오가 CRUD API에 연결돼 있지 않아 이 경로로 실제 프리셋이 저장될 일이 아직 없다 — 빌트인 폴백은 안전하다"고 적어 뒀는데, **FE-30이 그 연결(id 지목, `presetId` 포함)을 이미 만들어놓아 이 가정은 더 이상 유효하지 않다** — 이제 스튜디오 에디터에서 실제 이벤트에 커스텀 프리셋 id를 저장하는 정상 경로가 있다([[0010-studio-d1-slug-designation]]).
**완료 기준** — `origin='extracted'` 프리셋이 걸린 이벤트의 참가자 페이지가 **추출된 hue·chroma로 렌더**되는 것을 실측(API로 커스텀 프리셋을 만들어 이벤트에 걸고 브라우저로 확인). `preset`이 null인 기존 이벤트는 빌트인 폴백으로 회귀 없이 동작. `app/[slug]/page.tsx:152`의 낡은 주석을 정리한다. README「알고 있는 한계」의 해당 항목을 지운다.

## 열린 과제 — 백엔드(BE)

번호가 곧 의존 순서다.

### BE-13. 인가 경계를 운영자 API에 적용 (이벤트 소유권 강제)
**무엇** — BE-12의 세션을 실제 권한 판정에 연결한다. ① `POST /api/events`는 로그인 필수(401), 생성 시 `owner_id = 현재 사용자`. ② `PATCH`/`DELETE /api/events/[id]`는 소유자만 — **남의 것이면 403이 아니라 404**로 존재 자체를 흘리지 않는다(BE-7이 이미 채택한 원칙과 일관). ③ `GET /api/events`는 로그인 시 내 이벤트, 게스트는 데모 이벤트(`owner_id IS NULL`)만. ④ 하위 리소스(아젠다·자료, 그리고 BE-10의 질문 숨김)는 상위 이벤트의 소유자 확인을 거친다. ⑤ 참가자 경로(`/api/public/[slug]`, Q&A·설문 POST)는 **무인증 유지** — 여기에 로그인을 요구하면 제품이 깨진다. ⑥ 세션 조회를 대상 조회와 D1 `batch`로 묶어 요청당 왕복을 늘리지 않는다. ⑦ **운영자 쓰기에 rate limit을 넣는다** — 지금 전혀 없고, FE-15의 "가져오기"가 로컬 이벤트 N개를 한 번에 올리는 대량 쓰기 경로가 된다. 계정당 이벤트 수 상한도 함께 판단한다(무료 티어 압박 방지). 판정은 `lib/rate-limit.ts`를 재사용하되 키가 IP·토큰이 아니라 **user_id**라는 점이 다르다. **BE-12 의존.**
**왜** — 스키마에 `owner_id`만 있고 라우트가 읽지 않으면 구멍은 그대로다. BE-12와 나눈 이유는 ①~④가 기존 라우트 전부를 건드려 회귀 위험이 다르기 때문이며, 특히 ⑤를 실수로 함께 잠그면 참가자 참여 기능이 통째로 죽는다.
**완료 기준** — 계정 A가 만든 이벤트를 계정 B가 `PATCH`/`DELETE` 시 404. 비로그인 `POST /api/events` 401. 이벤트 20개 연속 생성(가져오기 시뮬레이션)에서 상한이 사유와 함께 걸림. **참가자 경로는 무인증으로 그대로 동작**(공개 조회 200, Q&A·설문 POST 201) — 회귀 실측 필수. 요청당 D1 왕복이 BE-12 이전 대비 늘지 않았음을 확인. README「알고 있는 한계」의 무보호 서술 갱신.

### BE-15. 게스트 워크스페이스 가져오기 엔드포인트
**무엇** — `POST /api/events/import` — 이벤트 + 테마 + 아젠다를 묶어 받아 **이벤트 단위로 D1 `batch` 한 번**에 생성한다([[0007-sso-and-account-model]] §1-1). ① **멱등성**: `events.client_ref` 컬럼 + `UNIQUE(owner_id, client_ref)`로 받아 재요청 시 새로 만들지 않고 기존 행을 돌려준다 — 네트워크가 끊겨 다시 누르는 것을 정상 경로로 취급. ② **원자성 단위는 이벤트 하나** — A 성공·B 실패면 A는 커밋된 채 두고 건별 결과 배열을 돌려준다(전체 롤백은 "9개 성공했는데 10번째 때문에 처음부터"가 되어 더 나쁘다). ③ `ensureUniqueSlug`로 slug가 바뀐 항목을 응답에 실어 화면이 알릴 수 있게 한다. ④ 이벤트 수·이벤트당 아젠다 수 상한(초과 400) + BE-13의 쓰기 rate limit 적용. **BE-12·13·14 의존.**
**왜** — 이벤트마다 `POST` → 테마 `PATCH` → 아젠다 N회를 돌리면 왕복이 수십 회로 늘어 무료 티어 쓰기를 낭비하고, 중간에 끊기면 **테마 없는 이벤트·아젠다 없는 이벤트 같은 반쪽 상태**가 서버에 남으며, 재시도가 중복을 만든다. 가져오기는 사용자가 "로그인하면 잃는다"를 겪지 않게 하는 장치인데 그 과정이 데이터를 깨면 목적과 정반대가 된다.
**완료 기준** — 로컬 이벤트 3개(각 아젠다 6개·테마 포함)를 가져와 전부 `owner_id`와 함께 저장됨. **같은 요청을 두 번 보내도 중복 생성 0**(멱등성 실측). 중간 실패 주입 시 성공분은 남고 실패분만 재시도로 복구됨. slug 충돌 시 변경 사실이 응답에 실림. 상한 초과 400. 남의 `client_ref`로는 남의 이벤트에 닿지 못함.

### BE-22. 커스텀 도메인 + 엣지 rate limiting
**무엇** — 커스텀 도메인을 붙여 존(zone)을 만들고, Cloudflare의 WAF/Rate Limiting Rules로 **무효 요청을 워커 도달 전에** 끊는다. `sympo-studio.fomula91.workers.dev`(workers.dev)에는 이 규칙을 적용할 수 없다 — 존이 필요하다.
**왜** — [[0008-rate-limit-counter]]가 판정한 것: 무효 요청 플러드의 실제 피해는 "D1이 마른다"가 아니라 **"Workers 요청 한도(10만/일)가 소진돼 그날 사이트가 죽는다"**이고, 요청이 이미 워커에 도착한 뒤라 **애플리케이션 rate limit으로는 원리적으로 막을 수 없다.** 맞는 층은 엣지다. 커스텀 도메인은 BE-2가 "이번에 하지 않는 것"으로 미뤄 둔 항목이라 여기서 함께 판단한다.
**완료 기준** — 커스텀 도메인에서 앱이 뜨고, 엣지 규칙이 실제로 요청을 차단하는 것을 실측(차단된 요청이 Workers 지표에 안 잡히는지). 무료 플랜에서 쓸 수 있는 규칙 수 제약을 함께 기록.

### BE-24. 무인증 읽기 경로 차단 — 이벤트 상세·운영 지표
**무엇** — 운영자용 읽기 3종에 인가를 적용한다. 실측으로 확인한 현재 상태: `GET /api/events`(목록)는 **`owner_id` 필터 없이 전부 돌려주고**, `GET /api/events/[id]`(상세)와 `GET /api/events/[id]/ops`(운영 지표)는 **인증 호출이 아예 0건**이다(`_request`가 쓰이지도 않는다). 로그인 시 내 것 + 데모, 게스트는 데모(`owner_id IS NULL`)만 보이게 한다. **남의 것은 403이 아니라 404**(BE-7·BE-13이 채택한 원칙과 일관). `/ops`는 참가자 리포트(`/[slug]/report`)가 쓰는 경로이기도 하므로 **그 화면이 죽지 않는지 반드시 함께 확인**한다 — 공개 이벤트의 집계는 계속 열어 두거나, 참가자용 경로를 따로 가른다.
**왜** — BE-13의 `무엇` ③이 **목록만** 언급하고 상세·집계는 빠져 있다. `owner_id`가 채워지기 시작한 지금(BE-12 완료) **남의 이벤트 전체 상세와 방문자·열람 지표가 URL만 알면 열린다.** 데이터가 전부 가상이라 노출 피해 자체는 낮지만, 소유권 모델을 도입해 놓고 읽기가 뚫려 있으면 그 모델이 성립하지 않는다. Codex 교차 리뷰가 "무인증 목록/상세/집계 조회"로 지목했고 BE-13 범위로 미뤄졌으나 실제로는 등록되지 않았다([[log]] 2026-09-11).
**완료 기준** — 계정 A의 이벤트를 계정 B가 `GET /api/events/[id]`·`/ops` 하면 404. 게스트는 데모 이벤트만 목록에 보임. **참가자 공개 리포트(`/[slug]/report`)가 그대로 동작** — 회귀 실측 필수. 요청당 D1 왕복이 늘지 않음(세션 조회를 `batch`로 묶는다). **BE-13과 같은 파일을 건드리므로 순서를 맞춘다.**

### BE-25. 프리셋 쓰기 경로 보호 — 무인증 + id 덮어쓰기
**무엇** — `POST /api/presets`에 인가를 건다. 지금 **인증 호출이 0건**이고, 쿼리가 `INSERT … ON CONFLICT(id) DO UPDATE SET label, hue, chroma, source_key`라 **id만 알면 남이 만든 프리셋(내장 프리셋 포함)을 아무나 덮어쓴다.** `migrations/0006_seed_builtin_presets.sql`이 넣은 내장 프리셋도 같은 테이블이라 함께 뚫려 있다. 최소한 ① 로그인 필수, ② 내장 프리셋(`origin`으로 구분) 수정 금지, ③ 남의 프리셋 덮어쓰기 금지 셋을 판단한다. `brand_presets`에 소유자 개념이 없으므로 **컬럼을 추가할지부터 정해야 한다**(추가하면 마이그레이션).
**왜** — 프리셋은 **이 제품의 핵심 컨셉**이다 — 실무에서 넘어오는 건 색상 값이 아니라 이미지라, 추출해 프리셋으로 쌓는 흐름이 있어야 실제 문제를 푼다([[Context]] 핵심 판단). 그 축적물이 아무나 덮어쓸 수 있으면 축적이 성립하지 않는다. 게다가 프리셋 색은 참가자 화면에 그대로 렌더되므로 **덮어쓰기가 곧 남의 행사 페이지 색을 바꾸는 것**이다. Codex 교차 리뷰가 "프리셋 덮어쓰기"로 지목했고 BE-13 범위로 미뤄졌으나 실제로는 등록되지 않았다([[log]] 2026-09-11).
**완료 기준** — 비로그인 `POST /api/presets` 401. 내장 프리셋 id로 덮어쓰기 시도가 거절되고 원래 값이 유지됨. 계정 A의 프리셋을 계정 B가 덮어쓰지 못함. **FE-8이 만든 추출→저장 흐름과 참가자 화면 색 렌더가 회귀 없이 동작** — 실측 필수. 소유자 컬럼을 추가했다면 기존 행의 마이그레이션 경로가 있을 것.

### BE-27. 자료 status와 파일 존재를 일치시킨다
**무엇** — `PUT /api/events/[id]/documents`가 **파일 없는 기존 문서를 `status: 'ready'`로 바꾸는 것을 막는다.** `lib/agenda.ts`는 **신규 생성만** 검사한다(`id === null && status === 'ready'` → 400). 기존 항목 수정 경로(`UPDATE documents SET … status = ?`)에는 검사가 없어서, `r2_key`가 NULL인 문서를 메타 저장 한 번으로 `ready`로 올릴 수 있다. `r2_key IS NULL`이면 `ready`를 거절하거나, 아예 `status`를 **입력이 아니라 `r2_key` 유무에서 파생**시키는 것을 검토한다(후자가 근본적이다 — 두 값이 어긋날 수 없게 된다).
**왜** — 참가자 화면에 **열 수 없는 자료가 "준비됨"으로 뜬다.** FE-6 작업 중 이 상태를 실제로 만들어 재현했고, FE 쪽은 `unavailable = pending || !url` 게이트로 방어했지만 **그건 증상을 가린 것이지 원인을 고친 게 아니다**([[log]] 2026-09-14). 서버가 일관성을 보장하지 않으면 다른 소비자(운영자 화면, 리포트)가 같은 함정을 각자 다시 밟는다. `status='pending'`은 "연자가 늦어 자료가 행사 중에 올라온다"는 실무 관찰을 담은 이 테이블의 요점이라([[field-experience]], `0001_init.sql` 주석) 그 의미가 어긋나면 안 된다.
**완료 기준** — `r2_key`가 NULL인 문서를 `ready`로 바꾸려는 `PUT`이 거절되고 사유가 응답에 드러남(또는 파생 방식을 택했다면 애초에 입력받지 않음). 업로드가 끝나면 `ready`가 되는 기존 흐름은 회귀 없음. 파생 방식을 택했다면 **기존 행 중 어긋난 것이 있는지 확인하고 정리**. `npm run test`에 회귀 테스트 추가.

### BE-28. 데모 리셋이 테마를 되돌리지 않는다
**무엇** — `lib/seed.ts`의 `resetDemoData`가 데모 이벤트를 제자리 `UPDATE`할 때 **테마 6컬럼을 되돌리지 않는다.** 지금 되돌리는 건 `owner_id`·`brand`·`title`·`venue`·`event_date`·`host`·`capacity`·`status`·`engage_*`뿐이고, `preset_id`·`mode`·`icon_set`·`density`·`key_visual`·`kv_pattern`은 손대지 않는다(`migrations/0001_init.sql:42-47`). `UPDATE` 목록에 추가한다.
**왜** — **데모 이벤트는 누구나 편집할 수 있는 게스트 체험 경로**다(`owner_id IS NULL` → `assertCanEdit` 통과). 방문자가 테마를 바꾸면 **자정 리셋이 그걸 되돌리지 못해 다음 방문자에게 그대로 남는다.** 데모가 매일 같은 상태로 시작한다는 전제가 깨지고, 채용담당자가 30초 안에 판단하는 화면이 남이 망가뜨린 상태일 수 있다. 리셋의 존재 이유가 바로 이 전제다. Codex 교차 리뷰가 "리셋이 테마를 안 되돌리는 것"으로 지목했고 BE-13 범위로 미뤄졌으나 실제로는 등록되지 않았다([[log]] 2026-09-11).
**완료 기준** — 데모 이벤트의 테마를 바꾼 뒤 `resetDemoData`를 돌리면 6컬럼이 전부 초기값으로 돌아옴(`key_visual`은 NULL). `lib/seed.test.ts`에 회귀 테스트 추가 — **가짜 D1이 SQL 문자열만 본다는 기존 한계**를 감안해 단언을 짜고, 그 한계를 파일 주석에 이미 적어 둔 방식을 따른다. R2에 올라간 키비주얼이 있다면 고아 정리 경로와 어긋나지 않는지 확인.
