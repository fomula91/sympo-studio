# sympo-studio — 다음 과제

> **형식 계약 (훅이 파싱한다)**: 열린 과제 제목은 `### FE-N. 제목` / `### BE-N. 제목`.
> 코드 repo의 SessionStart 훅이 `### FE-`·`### BE-`로 시작하는 줄만 추출해 세션에 주입한다. 섹션 헤더는 주입되지 않으므로 **제목의 `FE-`/`BE-` 접두사가 유일한 구분자**다.
> 계약은 접두사뿐이라 아래 섹션 제목은 자유롭게 바꿔도 되고, 추출이 0건이면 훅이 형식 오류 문구를 대신 주입한다.
> 새 과제는 `무엇 → 왜 → 완료 기준`으로 추가하고, 종료되면 아래 종료 기록 표로 옮긴 뒤 지운다. 남은 번호를 다시 매기지 않는다.
> 분리 규칙의 근거는 [[0003-next-tasks-fe-be-split]], 작성 규칙 본문은 `CLAUDE.md`의 「Next-Tasks 작성 규칙」.

**FE는 서로 독립**이라 순서 없이 아무거나 착수할 수 있다(단, 대부분 대응하는 BE에 의존한다 — 각 과제의 `무엇`에 명시).
**BE는 번호가 곧 의존 순서**다. 근거는 [[0001-backend-for-working-demo]], [[0002-cloudflare-free-tier-stack]].

현황(2026-08-31): **FE-1·2·7·8·9는 [PR #9](https://github.com/fomula91/sympo-studio/pull/9), BE-4는 [PR #12](https://github.com/fomula91/sympo-studio/pull/12)로 리뷰 대기 중** — 양쪽 다 머지 전 수정 권고가 남아 있다. 지금 새로 착수 가능한 FE: **FE-3**(BE 준비 완료 — [[API-Guide-FE]]가 계약), FE-4의 수료증 부분. BE 다음 추천은 **BE-12**(인증 기반) — 운영자 CRUD가 인가 검사도 rate limit도 없이 열려 있고, BE-10이 그 위에 무인증 엔드포인트를 하나 더 얹기 전에 놓아야 한다([[0007-sso-and-account-model]]). 읽기 비용 쪽이 급하면 BE-8을 먼저.

문제 정의의 정본은 [[field-experience]]다. 과제의 `왜`를 쓸 때 **거기 없는 내용을 근거로 삼지 않는다** — 기존 README가 그렇게 무너졌다([[0004-problem-redefinition]]).

## 열린 과제 — 프론트엔드(FE)

### FE-1. 이벤트별 편집 상태 분리
**무엇** — `StudioState`에 평평하게 녹아 있는 편집 대상(title/venue/date/sessions/theme…)을 이벤트 단위로 내린다. 현재는 콘솔에서 어떤 카드를 눌러도 `title`/`venue`만 패치되어 같은 아젠다를 편집한다(`ConsoleScreen.tsx:119`). **BE-1의 스키마 확정 후 착수** — 먼저 고치면 스키마가 정해질 때 두 번 고치게 된다.
**왜** — 데모를 클릭해 보는 사람이 가장 먼저 발견할 결함이다. 카드가 여러 개인데 편집 결과가 하나뿐인 것은 제품의 기본 전제가 깨진 상태다.
**완료 기준** — 서로 다른 이벤트가 각자의 아젠다·테마를 유지. 이벤트 전환 시 편집 중인 내용이 섞이지 않음.
**진행** — [PR #9](https://github.com/fomula91/sympo-studio/pull/9)에 완료로 포함, 리뷰 대기.

### FE-2. 라우트 분리 + 폰트 자체 호스팅
**무엇** — 화면 4개를 App Router 라우트로 분리(`/console`, `/events/[id]/edit`, `/[slug]`, `/report`). Pretendard를 `next/font/local`로 자체 호스팅해 외부 CDN 의존을 제거한다. **BE 의존 없음 — 로컬에서 완결된다.**
**왜** — 데모 링크를 특정 화면으로 공유할 수 있게 된다. 외부 CDN은 몇 달 뒤 링크가 열렸을 때 죽어 있을 수 있는 유일한 런타임 의존성이다.
**완료 기준** — 4개 화면이 딥링크로 열림. 외부 네트워크 의존 0(네트워크 탭에서 자사 도메인 외 요청 없음). 이번에 하지 않는 것: 커스텀 도메인.
**진행** — [PR #9](https://github.com/fomula91/sympo-studio/pull/9)에 완료로 포함, 리뷰 대기.

### FE-3. Q&A 화면 연결
**무엇** — 참가자 화면의 "질문 남기기"를 BE-3 API에 연결. 목록 갱신은 3~5초 폴링. 전송 중·실패·rate limit 초과 상태를 화면에 드러낸다. **브라우저 익명 토큰(`crypto.randomUUID()`)을 `localStorage`에 보관하고 POST에 `x-client-token` 헤더로 실어 보낸다**([[0006-rate-limit-key]] — 안 보내면 행사장 Wi-Fi 전체가 분당 3건을 공유). 입력 영역은 **고령 사용자 기준**으로 잡는다(글자 크기, 터치 타깃 44px 이상, 안내 문구를 화면에 상시 노출). 구현 계약은 [[API-Guide-FE]]. **BE 준비 완료** — BE-3·BE-9 종료(프로덕션 반영), BE-7 공개 API 배포됨. 지금 착수 가능.
**왜** — 방문자가 남긴 것이 실제로 목록에 뜨는 순간이 이 데모의 하이라이트다. 실무에서 Q&A는 **반복 노출로 익숙해지며 사용률이 올랐으므로**([[field-experience]]), 처음 보는 사람도 설명 없이 쓸 수 있는지가 관건이다.
**완료 기준** — 다른 브라우저에서 남긴 질문이 폴링으로 나타남. rate limit 초과 시 사용자가 이유를 알 수 있음(조용히 실패하지 않음). 확대 없이 읽고 누를 수 있음.

### FE-4. 설문 흐름 재설계 + 수료증 클라이언트 생성
**무엇** — **현재의 2단 설문 구조부터 재검토한다.** 실무에서 이탈 지점을 없앴는데도 설문 응답률이 오르지 않았고 원인은 고령 사용자였다([[field-experience]]) — 끝나고 몰아 받는 2단 폼이 그 자체로 장벽일 수 있다. **세션이 끝날 때마다 1문항씩 즉시** 받는 안을 우선 검토하고, 정한 구조로 BE-4에 연결한다. 응답 완료 시 수료증을 `pdf-lib`로 **브라우저에서 생성**해 다운로드시킨다. **폼은 BE-4 의존, 수료증 생성은 독립.**
**왜** — **이 프로젝트가 도전하는 지점이 정확히 여기다**([[0004-problem-redefinition]]). 플랫폼 교체로는 실패했고 UI 접근은 시도된 적이 없다. "현장에서 사람이 하던 안내를 UI가 대신할 수 있는가"에 답하는 과제다. 서버 PDF 생성은 무료 티어에서 막히므로 수료증은 클라이언트 생성이 전제다([[0002-cloudflare-free-tier-stack]]).
**완료 기준** — 구조 선택의 근거를 ADR 또는 [[field-experience]] 갱신으로 남김(직관만으로 정하지 말 것). 응답이 저장되고 수료증 PDF가 브라우저에서 생성·다운로드됨. **응답률 가설은 검증되지 않았음을 README에 계속 명시.** 이번에 하지 않는 것: 이메일 발송 — 다운로드로 대체.

### FE-5. 리포트를 실측 데이터로 교체
**무엇** — `ReportScreen`의 하드코딩 샘플(`METRICS`/`OPS`)을 BE-5의 집계 응답으로 교체한다. **BE-5 의존.**
**왜** — 도구가 스스로를 측정하지 않으면 개선됐는지 알 수 없다는 것이 리포트 층을 넣은 이유다.
**완료 기준** — 실제 방문 데이터로 열람률이 그려짐. 실측으로 바뀐 지표에서 `샘플 데이터` 배지 제거, 남은 가상 수치는 배지 유지(README 고지와 UI 배지가 어긋나지 않을 것).

### FE-6. PDF.js 뷰어 + 현장 업로드 + 가상 강의자료 제작
**무엇** — PDF 렌더링을 **PDF.js 클라이언트**로 구현하고 페이지 이동·확대 UI를 만든다. 함께 **현장 업로드 경로**를 넣는다 — 자료 도착 전의 "준비 중" 상태 표시, 태블릿에서 올릴 수 있는 업로드 UI, 올린 즉시 참가자 화면 반영. 데모용 가상 강의자료 PDF 제작 포함. **업로드는 BE-6 의존**이나, 로컬 PDF로 뷰어 개발까지는 먼저 할 수 있다.
**왜** — 실무에서 **연자가 늦게 도착해 자료가 행사 진행 중에 올라왔다**([[field-experience]]). 자료를 올리는 곳은 사무실 책상이 아니라 현장이었고, 그때까지 빈 목록이 그냥 결함처럼 보였다. 뷰어만으로는 이 상황을 다루지 못한다.
**완료 기준** — **모바일·태블릿에서 페이지 이동·확대가 동작**(`<iframe>` 방식은 iOS Safari에서 깨져 기각). 자료 없는 상태가 "준비 중"으로 읽힘. 태블릿 화면에서 업로드 완주 가능. 번들은 lazy load로 초기 로딩에 포함되지 않음.

### FE-7. 대비비 저장 게이트 실장
**무엇** — `lib/theme.ts:40`의 `lum(L) = L³` 근사를 culori 기반 실제 OKLCH→sRGB 변환으로 교체하고, `allPass`가 거짓일 때 "공개하기"를 실제로 차단한다(`StudioApp.tsx:245`). **BE 의존 없음.**
**왜** — "대비비 미달 조합은 만들 수 없다"가 이 제품의 주장인데 지금은 배지만 그리고 저장을 막지 않는다. **보여주려는 것 자체가 구현돼 있지 않다.** 실무에서 대비비로 사고가 난 적은 없지만, 색을 눈으로 맞추던 상황에서는 **안 났다는 보장도 없었다**([[field-experience]]). FE-8이 이미지에서 뽑은 색을 검증 없이 쓰면 위험하므로 그쪽의 전제이기도 하다.
**완료 기준** — 미달 조합에서 공개 버튼 비활성 + 사유 노출. WCAG 수치가 실제 sRGB 변환 기준. Vitest로 프리셋별 대비비 회귀 테스트.
**진행** — [PR #9](https://github.com/fomula91/sympo-studio/pull/9)에 완료로 포함, 리뷰 대기.

### FE-8. 브랜드 컬러를 대표 이미지에서 추출 + 프리셋 축적
**무엇** — 브랜드 대표 이미지를 올리면 주조색을 추출해 `{hue, chroma}`로 변환하고, 기존 `derive` 파이프라인에 태운다. 추출 결과는 **프리셋으로 저장해 다음 회차에 재사용**한다. 추출값은 그대로 쓰지 않고 대비비 게이트(FE-7)를 통과시킨다. **BE 의존 없음** — 이미지 처리는 전부 클라이언트에서 가능하다.
**왜** — 실무에서 대행사가 **정확한 색상 값을 주지 않아 이미지를 보고 눈으로 맞춰 입력**했다([[field-experience]]). 현재의 "브랜드 프리셋 선택"은 프리셋 목록에 그 브랜드가 이미 있을 때만 동작하는데, 회차마다 다른 브랜드가 오고 넘어오는 건 이미지 한 장이다. **즉 지금 구현은 실제 문제를 절반만 푼다.** 프리셋은 미리 준비된 목록이 아니라 **쌓이는 것**이어야 했다.
**완료 기준** — 이미지 업로드 → 팔레트 파생 → 대비비 검증 → 프리셋 저장까지 왕복. 저장한 프리셋이 다음 이벤트에서 선택 가능. 추출이 실패하거나 대비비 미달일 때 수동 조정 경로가 있음.
**진행** — [PR #9](https://github.com/fomula91/sympo-studio/pull/9)에 완료로 포함, 리뷰 대기.

### FE-9. 네트워크 단절 대응
**무엇** — 폴링·서버 요청 실패를 화면에서 다루고, 마지막으로 받은 아젠다·자료 목록을 캐시해 오프라인에서도 표시한다. 참여 기능은 오프라인일 때 **명시적으로 비활성**하고 이유를 알린다(조용히 실패하지 않기). **BE 의존 없음** — 클라이언트 캐싱과 실패 처리다.
**왜** — 현장에서 **인터넷이 끊기는 일이 실제로 있었고**([[field-experience]]), 참가자 수십·수백 명이 같은 행사장 와이파이를 쓴다. **네트워크가 가장 느려지는 시점이 참여 기능을 써야 하는 시점**이다. [[0002-cloudflare-free-tier-stack]]이 3~5초 폴링을 전제하므로 이 대응 없이는 현장에서 화면이 비는 것으로 끝난다.
**완료 기준** — 네트워크를 끊은 상태에서 아젠다·자료가 계속 보임. 참여 기능이 비활성 상태와 사유를 노출. 복구 시 자동 재개.
**진행** — [PR #9](https://github.com/fomula91/sympo-studio/pull/9)에 완료로 포함, 리뷰 대기.

### FE-13. 디자인 시스템 문서화 + 공용 컴포넌트 라이브러리
**무엇** — 두 갈래를 한 과제로 묶는다(서로 맞물려 있어 쪼개면 순서 의존이 생긴다). ① **디자인 시스템**: [[design]]을 컨셉 문서에서 실행 규격으로 승격 — `globals.css`의 CSS 변수 토큰(라이트/다크 페어 전체)을 이름·용도·대비비 기준과 함께 표로 정의하고, 타이포 스케일·간격·라운드·그림자 단계를 코드와 1:1로 맞춘다. 상태 의미색(진행중/검수대기 등)의 **다크 페어를 이번에 정의**한다(알려진 갭, [[log]] 2026-08-19). ② **공용 컴포넌트**: `lib/ui.ts`의 스타일 객체(`ghostBtn`/`primaryBtn`/`seg`/`pillStyle`)와 화면마다 반복되는 인라인 패턴(카드, 섹션 제목, 입력 필드, 상태 배지, 빈 상태)을 `components/ui/`의 실제 React 컴포넌트로 추출하고, 셸 화면 4곳이 이를 사용하도록 교체한다. **참가자 마이크로사이트는 범위 밖** — 행사 테마는 런타임 파생이라 도구 색 체계와 섞지 않는다([[design]] 색 분리 원칙). **BE 의존 없음.**
**왜** — 토큰은 CSS 변수로 체계화됐지만 컴포넌트 층이 없어서, 같은 카드·배지·버튼이 화면마다 인라인 스타일로 복제돼 있다. 다크모드 배지 갭이 정확히 이 구조의 비용이다 — 스타일이 한 곳에 있었다면 페어 하나 추가로 끝났을 일이 전 화면 수색이 됐다. FE 담당자와의 협업에서도 "어떤 색·컴포넌트를 쓰면 되는가"의 정본이 없으면 회신 왕복이 생긴다. README가 이미 인라인 스타일을 트레이드오프로 명시하고 정리 방향을 예고한 상태다.
**완료 기준** — [[design]]에 토큰 표(라이트/다크 전체)와 컴포넌트 목록·사용 규칙이 실림. `components/ui/`의 컴포넌트로 셸 4개 화면의 해당 패턴이 교체되고 시각 회귀 없음(교체 전후 스크린샷 대조). 상태 배지가 다크모드에서 튀지 않음. lint·build 통과.

### FE-14. FSD(Feature-Sliced Design) 아키텍처 적용
**무엇** — 평평한 `components/` + `lib/` 구조를 FSD 레이어(`app`/`pages`/`widgets`/`features`/`entities`/`shared`)로 재편한다. 먼저 **레이어 매핑 ADR**을 쓰고 나서 옮긴다 — 대략의 방향은: `lib/ui.ts`·`globals.css` 토큰·공용 컴포넌트(FE-13 산출물)→`shared/`, 이벤트·세션·테마 타입과 데이터 접근→`entities/`, Q&A·설문·테마 편집 같은 사용자 행동 단위→`features/`, 셸 화면 4개→`widgets/`+`pages/`. **주의**: Next.js App Router의 `app/` 디렉터리와 FSD의 `app` 레이어 이름 충돌, 그리고 `Microsite`(에디터 프리뷰와 참가자 뷰어가 같은 컴포넌트를 공유하는 이 프로젝트의 핵심 설계)가 어느 슬라이스에 속하는지를 ADR에서 반드시 결정한다. 이동은 **한 번에 전부가 아니라 레이어 단위로** 진행하고 각 단계마다 build를 통과시킨다. FE-2(라우트 분리)·FE-13(공용 컴포넌트)과 같은 파일을 건드리므로, **착수 시점에 그 둘이 진행 중이면 완료를 기다리거나 흡수 범위를 명시**한다. **BE 의존 없음.**
**왜** — 화면이 4개일 때는 평평한 구조가 싸지만, 열린 과제들(Q&A 연결, 설문 재설계, PDF 뷰어, 오프라인 대응)이 전부 "화면 조각 + 상태 + API 호출"을 한 덩어리씩 추가하는 성격이라 지금 구조로는 `components/`와 `lib/`이 기능 경계 없이 섞이며 자란다. FE 담당자와의 분업에서도 "이 기능은 이 폴더"라는 소유 경계가 있어야 충돌 없이 병렬 작업이 된다. 레이어의 단방향 의존 규칙은 프리뷰=실물 같은 구조적 보장을 지키는 데도 유리하다.
**완료 기준** — 레이어 매핑 ADR(`Decisions/`)이 있고 실제 구조가 그와 일치. import 방향이 FSD 규칙(상위→하위만)을 지키는지 eslint 규칙(예: `import/no-restricted-paths` 또는 steiger)으로 강제되고 위반 0건. 기존 화면 동작·시각 회귀 없음(스크린샷 대조). lint·build 통과.

### FE-15. 로그인·계정 관리 화면 + 게스트/계정 이원화
**무엇** — ① **게스트 로컬 워크스페이스**: 비로그인 상태의 콘솔·에디터가 `localStorage`에 영속하는 워크스페이스에서 동작한다. 첫 진입 시 클라이언트 시드로 초기화하고, 이후 이벤트 생성·수정·삭제·테마 편집이 전부 로컬에서 완결되며 **새로고침·재방문에도 유지**된다. **서버 데모 이벤트의 id를 참조하는 오버레이로 만들지 않는다** — 자정 Cron 리셋 때 기준이 사라져 조용히 깨진다([[0007-sso-and-account-model]]). ② 헤더에 "Google로 시작하기" / 로그인 후 계정 메뉴(아바타·이름·로그아웃). ③ **게스트 상태를 화면에 드러낸다** — "체험 중 · 이 브라우저에만 저장됩니다" 배너, 공개 URL 발급처럼 서버가 필요한 동작에서만 로그인 유도. ④ **로그인 시 가져오기**: 로컬에 편집분이 있으면 "체험 중 만든 이벤트 N개를 계정으로 가져올까요?"를 묻고, 수락 시 BE-15의 `POST /api/events/import`에 이벤트+테마+아젠다를 묶어 보낸다. 로컬 이벤트는 생성 시점에 **로컬 UUID(`localRef`)를 갖고 있어야** 멱등성이 성립하므로 ①에서 함께 설계한다. 응답의 건별 결과를 받아 **성공한 항목만 로컬에서 제거**하고(남기면 재로그인 때 중복 제안), 실패분은 재시도 경로를 남기며, **slug가 바뀐 이벤트를 화면에 알린다**. 거절 시 로컬 보존. ⑤ 계정 설정 화면 — 프로필(이름·아바타·이메일), 연결된 제공자, 로그아웃, **계정 삭제**(삭제 범위 명시: 내 이벤트·아젠다·자료·질문·설문 응답 전부). ⑥ 로그인 후 원래 있던 화면으로 복귀. **①③은 BE 의존 없음, ②⑤는 BE-12·BE-13 의존, ④는 BE-15 의존.** PR #9(FE-1 이벤트별 상태 분리)가 이 워크스페이스의 상태 층이므로 머지 후 착수한다.
**왜** — 게스트에게 "저장이 안 된다"만 알리고 편집을 휘발시키면 **만져본 결과를 확인할 수 없어 체험 자체가 성립하지 않는다.** 반대로 로그인 벽이 먼저 보이면 ADR 0001이 지키려던 "30초 안에 판단"이 무너진다. 로컬 영속이 두 요구가 만나는 지점이고, **이 과제가 그 양립을 화면에서 판정한다.** 가져오기를 넣는 이유는 사용자 입장에서 **로그인이 잃는 행동이 되어서는 안 되기** 때문이다 — 공들여 만든 것이 로그인으로 사라지면 다시는 로그인하지 않는다.
**완료 기준** — 비로그인으로 이벤트를 만들고 테마를 바꾼 뒤 **브라우저를 닫았다 다시 열어도 그대로 있음**. 로그인 → 가져오기 수락 → **아젠다·테마까지** 서버에 `owner_id`와 함께 저장되고 성공분만 로컬에서 비워짐(가져오기 도중 새로고침해도 중복 생성 0) → 로그아웃 → 게스트 워크스페이스가 중복 없이 빈 상태. 다른 계정으로 로그인하면 남의 이벤트가 목록에 없음. 계정 삭제 후 재로그인 시 빈 상태. 게스트 데이터가 이 브라우저에만 있다는 사실이 화면에 드러남(조용히 사라지지 않게). 모든 운영자 화면에 대해 "게스트에게 어떻게 보이는가"를 확인한 기록을 남김. **`localStorage` 용량 판단 기록**: FE-8의 대표 이미지가 `key_visual`에 base64로 들어가면 5MB에 닿으므로, 이미지 제외·참조·IndexedDB 중 무엇을 골랐는지와 근거.

### BE-2. Cloudflare 배포 — 살아있는 링크 확보
**무엇** — `@opennextjs/cloudflare` 어댑터로 Workers/Pages 배포, D1·R2 바인딩, GitHub 연동 자동 배포.
**왜** — **링크 없는 완벽한 계획보다 링크 있는 절반이 낫다.** 포트폴리오에서 가장 먼저 읽히는 요소가 살아있는 URL이고, 이후 기능은 여기에 증분 배포하면 된다.
**완료 기준** — 공개 URL에서 앱이 뜨고 D1·R2 바인딩이 동작. push → 자동 배포. **결제 수단 미등록 상태 확인**(카드가 있으면 봇 트래픽에 청구서가 날아온다). 딥링크 확인은 FE-2 소관.
**진행** — 배포 완료: https://sympo-studio.fomula91.workers.dev (`/`·`/intro`·`/api/events` 200, D1 쓰기 왕복 실측, [[log]] 2026-08-24). R2 바인딩은 BE-6으로 이관. 남은 것: ① GitHub push→자동 배포(Workers Builds 연결) ② 결제 수단 미등록 확인 — 둘 다 대시보드 작업.

### BE-5. 이벤트 로그 적재 + OPS 집계
**무엇** — 세션별 열람·자료 열람·설문 완료를 이벤트 로그로 적재하고 집계 엔드포인트를 제공한다.
**왜** — BE-3·4에서 데이터가 쌓여야 의미가 생기므로 순서상 여기다.
**완료 기준** — 실제 방문 데이터가 적재되고 집계로 조회됨. **이벤트 로그 30일 보존 후 삭제 Cron 등록**(방치하면 무한 증가한다).

### BE-6. R2 자료 저장 + 업로드 + 서명 URL
**무엇** — 강의자료를 R2에 두고 서명 URL로 내준다. **업로드 엔드포인트도 여기 포함** — 행사 진행 중 현장에서 올리는 경로다(FE-6). 서버는 URL 발급과 저장만 하고 렌더링·변환에는 관여하지 않는다.
**왜** — 서버 PDF 파싱은 무료 티어에서 막히므로 "저장·조회는 서버, 렌더링은 클라이언트" 원칙을 그대로 적용한다([[0002-cloudflare-free-tier-stack]]). R2는 이그레스가 무료라 전송량 계산이 불필요하다.
**완료 기준** — 서명 URL로 PDF를 받을 수 있고 만료가 동작. **서버 CPU 사용 0**(파싱·변환 없음).

### BE-7. 참가자 화면용 공개 조회 API (slug 기반)
**무엇** — 참가자 마이크로사이트가 쓸 공개 읽기 엔드포인트. `GET /api/public/[slug]` 하나로 이벤트 + 아젠다 + 자료 목록(`pending`="준비 중" 포함) + 테마 + engage 토글을 돌려준다. **공개 가능한 상태(공개예정·진행중·완료)만 노출**하고 초안·검수대기·보관은 404 — 존재 여부도 흘리지 않는다. 관리자 전용 필드(전체 목록·상태 필터 등)는 제외. Q&A·설문은 BE-3/4 엔드포인트를 재사용하되, 이 응답에 이벤트 id를 실어 slug→id 재해석 없이 붙을 수 있게 한다. **의존은 BE-1뿐** — 번호는 7이지만 BE-4~6과 독립이라 BE-3 다음에 바로 착수해도 된다. FE-2(라우트 분리)의 `/[slug]` 화면과 FE-3이 이 API의 소비자다.
**왜** — FE-2가 참가자 화면을 `/[slug]` 라우트로 분리하는 순간 데이터를 받아올 곳이 없다. 지금의 `/api/events`는 운영자 콘솔용 CRUD라 id 기반이고 초안까지 다 보인다. 참가자는 **회차별 고유 slug로 접근**하는 것이 이 제품의 핵심 제약(공유 캐시 오염 방지, [[0005-d1-schema]])이므로, 공개 API의 키도 slug여야 한다.
**완료 기준** — slug 하나로 참가자 화면 렌더에 필요한 전부가 단일 응답으로 옴(뷰어/`Microsite`가 실제로 그려지는지로 확인). 비공개 상태 404. 폴링 대상이므로 rate limit 정책 판단을 함께 기록(읽기 전용이라 BE-3보다 완화한다면 그 근거).
**진행** — 구현·로컬 실측 완료([[log]] 2026-08-26): `GET /api/public/[slug]` 단일 응답(이벤트+아젠다+자료+테마+engage, 이벤트 id 포함), 공개 상태 3종만 노출하고 초안·없는 slug 모두 동일한 404(존재 비노출), `r2_key`는 경계 밖. rate limit 정책 기록: D1 판정형 읽기 제한은 역효과라 미적용, `Cache-Control: public, max-age=10`으로 흡수(근거는 라우트 주석) — D1을 안 거치는 통제는 BE-8에서 판단. 배포 후 프로덕션 실측 완료(2026-08-26): 공개 slug 200+캐시 헤더, 초안 전환 시 404, 없는 slug 404. 남은 것: `Microsite` 실제 렌더 확인(FE-2/FE-3 연결 시).

### BE-10. 질문 숨김(모더레이션) 경로
**무엇** — `questions.status`를 `hidden`으로 바꾸는 운영자 엔드포인트를 만들고, `engage_qa=0`일 때 GET 피드를 계속 서빙할지 정책을 정해 반영한다.
**왜** — 코드리뷰(2026-08-25)에서 확인: 스키마와 주석은 `status='hidden'` 숨김 처리를 전제하는데 그것을 수행하는 코드가 어디에도 없다. 부적절한 질문이 올라오면 제거 경로가 이벤트 전체 삭제(CASCADE) 또는 자정 리셋 대기뿐이고, Q&A 토글을 꺼도 GET은 계속 서빙된다.
**완료 기준** — 숨김 처리한 질문이 폴링 피드에서 즉시 사라짐. `engage_qa` off 시 GET 동작이 정책으로 문서화되고 구현과 일치.

### BE-11. 2차 코드리뷰 지적 10건 반영
**무엇** — 2차 코드리뷰(2026-08-25, 후보 12건 전건 CONFIRMED, 상위 10건 채택)의 지적을 반영한다: ① POST 본문 JSON `null`이 500으로 터짐 → 객체 검사, ② `createdAt`이 존 표기 없는 UTC 문자열이라 클라이언트에서 9시간 어긋남 → ISO-8601+`Z`, ③ 시드 리셋마다 세션 id가 +6씩 밀려(AUTOINCREMENT) `SESSIONS0`의 id 1~6과 어긋남 → 시드에서 id 고정, ④ 일일 캡 쿼리에 날짜 조건 없음(해시 소금에만 의존) → KST 하루 시작 조건 추가, ⑤ 자정 리셋과 경합하는 POST의 FK 위반 500 → 404, ⑥ `ORDER BY id DESC`가 인덱스를 못 타 전체 행 임시 정렬(EXPLAIN 실측) → `created_at DESC` + JS 동점 안정화, ⑦ 워커 엔트리가 `fetch`만 골라 담아 산출물 드리프트에 취약 → `...handler` 스프레드, ⑧ 에러→상태코드 try/catch 6중 복제 → `ApiError` 계층 + `withRoute` 래퍼로 공통화, ⑨ 시드가 `autoSlug` 파생값을 손 전사 → 파생으로 교체, ⑩ 핫 쿼리 `SELECT *`가 미사용 컬럼 3개(client_hash 포함) 전송 → 컬럼 명시.
**왜** — ①~⑤는 FE-3(Q&A 화면 연결)이 붙는 순간 실사용자가 밟는 결함이고, ⑥·⑩은 가장 바쁜 폴링 경로의 비용, ⑦~⑨는 다음 과제(BE-4~10)가 같은 패턴을 복제하기 전에 잡아야 하는 구조 문제다.
**완료 기준** — lint·build 통과. 배포 후 원격 재검증(BE-3의 원격 Cron 확인과 함께): 질문 저장·조회 왕복, 429 사유 노출, 리셋 후 세션 id 1~6 유지.
**진행** — 전 항목 구현 완료 + PR #8 머지 + 배포·원격 재검증 완료(2026-08-26, [[log]]): 403→(qa on)→201 왕복, `null` 본문 400, `createdAt` ISO(`…T…Z`), 60초 4건째 429 사유 노출 — 전부 프로덕션 URL 실측. 남은 것: 첫 자정 리셋(00:00 KST) 후 시드 세션 id가 1~6으로 유지되는지 확인.

### BE-12. 인증 기반 — Google SSO + D1 세션 + 이벤트 소유권 컬럼
**무엇** — [[0007-sso-and-account-model]]대로 구현한다. ① 마이그레이션 0004: `users`·`oauth_accounts`·`auth_sessions`(**이름 주의** — 기존 `sessions`는 아젠다 세션이다) + `events.owner_id`(NULL = 데모 이벤트). ② OAuth 라우트 4개 — `GET /api/auth/google`(state + PKCE 발급), `GET /api/auth/callback/google`(state 대조 → 토큰 교환 → `iss`/`aud`/`exp` 확인 → 사용자 upsert → 세션 발급), `POST /api/auth/logout`, `GET /api/auth/me`(게스트는 200 + `null`). ③ 세션은 랜덤 토큰을 httpOnly 쿠키로 주고 D1에는 SHA-256 해시만 저장, 쿠키는 `SameSite=Lax`·`Secure`·`Path=/`이며 `__Host-` 접두사는 **환경별로 분기**(로컬 dev는 http라 동작하지 않음). ④ **같은 커밋에서** `lib/seed.ts:22`의 `DELETE FROM events`를 `WHERE owner_id IS NULL`로 한정한다. ⑤ 만료 세션 정리를 기존 자정 Cron에 추가. **의존은 BE-1뿐.** 사람 손 작업이 하나 있다: Google Cloud Console에서 OAuth 클라이언트 생성 + redirect URI 등록, `wrangler secret put`으로 `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` 주입.
**왜** — 운영자 CRUD가 인가 검사도 rate limit도 없이 열려 있어 **누구나 남의 이벤트를 수정·삭제(CASCADE)** 할 수 있다. BE-10(질문 숨김)이 여기 얹히면 무인증 운영자 엔드포인트가 하나 더 늘어나므로 그 전에 기반을 놓아야 한다. ④는 미루면 안 되는 종류다 — `owner_id`가 생긴 시점부터 자정 Cron이 매일 사용자 데이터를 통째로 지운다.
**완료 기준** — 로그인 → 이벤트 생성 시 `owner_id`가 채워짐. 로그아웃 후 쿠키·세션 행 모두 소멸. 만료 세션으로 요청 시 게스트로 취급(500 아님). `state` 불일치·`code` 재사용·만료 `id_token`을 각각 거부하는 것을 실측. **자정 리셋 시 `owner_id IS NOT NULL` 이벤트가 살아남는 것을 실측**(시각을 앞당겨 Cron 핸들러 직접 호출). 직접 구현한 흐름이므로 **코드리뷰 통과를 완료 기준에 포함**한다. 로컬·프로덕션 양쪽 실측.

### BE-13. 인가 경계를 운영자 API에 적용 (이벤트 소유권 강제)
**무엇** — BE-12의 세션을 실제 권한 판정에 연결한다. ① `POST /api/events`는 로그인 필수(401), 생성 시 `owner_id = 현재 사용자`. ② `PATCH`/`DELETE /api/events/[id]`는 소유자만 — **남의 것이면 403이 아니라 404**로 존재 자체를 흘리지 않는다(BE-7이 이미 채택한 원칙과 일관). ③ `GET /api/events`는 로그인 시 내 이벤트, 게스트는 데모 이벤트(`owner_id IS NULL`)만. ④ 하위 리소스(아젠다·자료, 그리고 BE-10의 질문 숨김)는 상위 이벤트의 소유자 확인을 거친다. ⑤ 참가자 경로(`/api/public/[slug]`, Q&A·설문 POST)는 **무인증 유지** — 여기에 로그인을 요구하면 제품이 깨진다. ⑥ 세션 조회를 대상 조회와 D1 `batch`로 묶어 요청당 왕복을 늘리지 않는다. ⑦ **운영자 쓰기에 rate limit을 넣는다** — 지금 전혀 없고, FE-15의 "가져오기"가 로컬 이벤트 N개를 한 번에 올리는 대량 쓰기 경로가 된다. 계정당 이벤트 수 상한도 함께 판단한다(무료 티어 압박 방지). 판정은 `lib/rate-limit.ts`를 재사용하되 키가 IP·토큰이 아니라 **user_id**라는 점이 다르다. **BE-12 의존.**
**왜** — 스키마에 `owner_id`만 있고 라우트가 읽지 않으면 구멍은 그대로다. BE-12와 나눈 이유는 ①~④가 기존 라우트 전부를 건드려 회귀 위험이 다르기 때문이며, 특히 ⑤를 실수로 함께 잠그면 참가자 참여 기능이 통째로 죽는다.
**완료 기준** — 계정 A가 만든 이벤트를 계정 B가 `PATCH`/`DELETE` 시 404. 비로그인 `POST /api/events` 401. 이벤트 20개 연속 생성(가져오기 시뮬레이션)에서 상한이 사유와 함께 걸림. **참가자 경로는 무인증으로 그대로 동작**(공개 조회 200, Q&A·설문 POST 201) — 회귀 실측 필수. 요청당 D1 왕복이 BE-12 이전 대비 늘지 않았음을 확인. README「알고 있는 한계」의 무보호 서술 갱신.


### BE-14. 아젠다·자료 쓰기 API (지금 아예 없다)
**무엇** — `sessions`(아젠다)와 `documents`(자료 메타)를 쓰는 라우트를 만든다. 목록 교체(순서 포함)와 개별 수정·삭제를 지원하고, 드래그 정렬 결과를 한 번에 반영할 수 있어야 한다(FE의 아젠다 편집은 순서가 곧 데이터다). 상위 이벤트 소유자만 쓸 수 있다(BE-13의 판정 재사용). 자료 **파일**은 BE-6(R2) 소관이고 여기서는 메타(제목·상태·순서)만 다룬다. **번호는 14지만 BE-12·13과 독립**이라 인증보다 먼저 착수해도 된다(그 경우 소유권 검사만 나중에 얹는다).
**왜** — `app/api/events/[id]/`에 `questions`·`survey`뿐이고 **아젠다를 서버에 저장할 방법이 없다.** GET·시드로 읽히기만 해서 지금까지 드러나지 않았을 뿐, FE-1(이벤트별 편집 상태 분리)이 붙는 순간 "에디터에서 아젠다를 고쳤는데 서버에 안 남는다"로 나타난다. FE-15의 가져오기도 이것 없이는 이벤트 껍데기만 옮기게 된다.
**완료 기준** — 아젠다 추가·수정·삭제·순서 변경이 왕복으로 확인됨. 순서 변경이 한 번의 요청으로 반영됨(N개 개별 PATCH 아님). 남의 이벤트의 아젠다는 404. **세션 삭제 시 `survey_responses`의 UNIQUE 위반**(PR #12 리뷰가 재현한 `FK SET NULL` × `idx_survey_once`)이 여기서 실제로 터지므로 함께 해결하고 실측한다.
**진행** — 구현·로컬 실측 완료(2026-08-31, [[log]]): `PUT /api/events/[id]/sessions`·`PUT …/documents`(둘 다 목록 전체를 받는 id 기준 diff), `GET /api/events/[id]`에 `documents` 추가 + 3쿼리 batch. UNIQUE 위반은 **로컬 D1에서 생 SQL로 먼저 재현**한 뒤(`DELETE FROM sessions WHERE id=4` → `SQLITE_CONSTRAINT_UNIQUE`) 세션 삭제 전에 그 세션의 설문 응답을 함께 지우는 것으로 해결 — 스키마 `ON DELETE CASCADE`가 정석이나 SQLite는 FK를 ALTER할 수 없어 테이블 재생성이 필요하고 그 마이그레이션이 미머지 상태인 BE-4의 0003(같은 테이블 컬럼 추가)과 적용 순서로 얽힌다. 계약은 [[API-Guide-FE]]. **남은 것**: ① BE-4 머지 후 스키마 CASCADE로 이관 ② 소유권 검사(BE-13에서 얹음 — 지금은 누구나 호출 가능) ③ 배포·프로덕션 실측.

### BE-15. 게스트 워크스페이스 가져오기 엔드포인트
**무엇** — `POST /api/events/import` — 이벤트 + 테마 + 아젠다를 묶어 받아 **이벤트 단위로 D1 `batch` 한 번**에 생성한다([[0007-sso-and-account-model]] §1-1). ① **멱등성**: `events.client_ref` 컬럼 + `UNIQUE(owner_id, client_ref)`로 받아 재요청 시 새로 만들지 않고 기존 행을 돌려준다 — 네트워크가 끊겨 다시 누르는 것을 정상 경로로 취급. ② **원자성 단위는 이벤트 하나** — A 성공·B 실패면 A는 커밋된 채 두고 건별 결과 배열을 돌려준다(전체 롤백은 "9개 성공했는데 10번째 때문에 처음부터"가 되어 더 나쁘다). ③ `ensureUniqueSlug`로 slug가 바뀐 항목을 응답에 실어 화면이 알릴 수 있게 한다. ④ 이벤트 수·이벤트당 아젠다 수 상한(초과 400) + BE-13의 쓰기 rate limit 적용. **BE-12·13·14 의존.**
**왜** — 이벤트마다 `POST` → 테마 `PATCH` → 아젠다 N회를 돌리면 왕복이 수십 회로 늘어 무료 티어 쓰기를 낭비하고, 중간에 끊기면 **테마 없는 이벤트·아젠다 없는 이벤트 같은 반쪽 상태**가 서버에 남으며, 재시도가 중복을 만든다. 가져오기는 사용자가 "로그인하면 잃는다"를 겪지 않게 하는 장치인데 그 과정이 데이터를 깨면 목적과 정반대가 된다.
**완료 기준** — 로컬 이벤트 3개(각 아젠다 6개·테마 포함)를 가져와 전부 `owner_id`와 함께 저장됨. **같은 요청을 두 번 보내도 중복 생성 0**(멱등성 실측). 중간 실패 주입 시 성공분은 남고 실패분만 재시도로 복구됨. slug 충돌 시 변경 사실이 응답에 실림. 상한 초과 400. 남의 `client_ref`로는 남의 이벤트에 닿지 못함.
