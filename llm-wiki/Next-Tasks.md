## 열린 과제 — 프론트엔드(FE)

### FE-20. 참가자 화면에서 이벤트 로그 적재
**무엇** — 참가자 화면이 열람 흔적을 `POST /api/events/[id]/logs`로 보낸다. **BE-5가 만든 엔드포인트를 지금 아무도 호출하지 않아**, 집계(`/ops`)가 시드 로그 13건만 그린다(2026-09-03 프로덕션 실측: `visitors=3 pageViews=3 sessions=3` = 시드 값 그대로). 보낼 것 네 가지:

| 시점 | 본문 |
|---|---|
| 참가자 페이지 진입 | `{ kind: 'page_view' }` |
| 아젠다 세션이 화면에 보일 때 | `{ kind: 'session_view', sessionId }` |
| 자료를 열 때 | `{ kind: 'doc_view', documentId }` |
| 설문 완료 시 | `{ kind: 'survey_complete' }` |

**건별로 보내지 말 것** — 아젠다를 훑으면 열람이 순식간에 쌓여 D1 쓰기보다 **요청 수가 먼저 부담**이 된다. 배열로 모아 한 번에(최대 30개). `x-client-token`을 실어야 **같은 사람의 열람이 하나로 세어진다**(없어도 저장은 되지만 `visitors`에서 빠지고 `hits`에만 남는다). rate limit은 60초 60행·하루 300행으로 Q&A보다 넉넉하다. 계약은 [[API-Guide-FE]]의 「이벤트 로그·운영 지표」. **BE-5 완료 — 서버는 준비됐다.**
**왜** — FE-5(리포트)의 완료 기준이 *"**실제 방문 데이터로** 열람률이 그려짐"*인데, 읽는 쪽만 만들어져 **계약의 절반이 주인 없이 떠 있었다.** 원인은 과제 분할이다 — BE-5는 "리포트의 원자료"로, FE-5는 "집계 응답으로 교체"로만 서술돼 **적재를 아무도 자기 일로 적지 않았다**(PR #20 리뷰에서 발견). 리포트가 그리는 수치가 실측이 아니면 "도구가 스스로를 측정한다"는 리포트 층의 존재 이유가 성립하지 않는다.
**완료 기준** — 참가자 페이지를 서로 다른 브라우저로 열면 `/ops`의 `visitors`가 그만큼 늘어남(시드 값과 구분되게 확인). 같은 브라우저로 여러 번 열면 `visitors`는 그대로고 `pageViews`만 늘어남(토큰이 사람을 하나로 세는지). 세션·자료 열람이 `/ops`의 `sessions`·`documents`에 반영됨. 요청이 건별이 아니라 배치인 것을 네트워크 탭에서 확인. **로그 전송 실패가 화면 동작을 막지 않을 것** — 계측이지 참여 기능이 아니다.
**진행** — `page_view`·`session_view` 두 종만 우선 구현(2026-09-06, [[log]]). `lib/api.ts`에 `sendEventLogs()` 신설(배치 전송, 실패 시 조용히 무시). `app/[slug]/page.tsx`가 로드 성공 시 1회 `page_view`를 보내고, `Microsite.tsx`는 아젠다 `<li>`마다 `IntersectionObserver`로 화면 노출을 감지해 1.5초 디바운스로 모아 `session_view`를 배치 전송(같은 세션 중복 방지, 스튜디오 미리보기에서는 미전송). **`doc_view`·`survey_complete`는 보류** — 참가자 화면에 자료를 "여는" 동작(FE-6 PDF 뷰어)과 설문 "제출" 동작(FE-4 설문 UI)이 아직 없어 로그를 붙일 트리거 자체가 없다(백엔드 `/logs`는 이미 4종 다 받는다, BE 요청 아님). **FE-6·FE-4 각각 완료 후 이어서 두 kind를 추가한다.** → `survey_complete`는 FE-4 종료와 함께 연결 완료([[log]] 2026-09-09), 남은 건 `doc_view`(FE-6 의존). curl로 `POST /api/events/1/logs` 왕복 확인 중 로컬 D1에 마이그레이션 미적용(`token_hash` 컬럼 없음) 발견 — `npm run db:migrate`로 해결(코드 문제 아님). `npm run lint`·`test`(12건)·`build` 통과. 브라우저 확장 미연결로 실제 스크롤 시나리오는 미검증.

### FE-6. PDF.js 뷰어 + 현장 업로드 + 가상 강의자료 제작
**무엇** — PDF 렌더링을 **PDF.js 클라이언트**로 구현하고 페이지 이동·확대 UI를 만든다. 함께 **현장 업로드 경로**를 넣는다 — 자료 도착 전의 "준비 중" 상태 표시, 태블릿에서 올릴 수 있는 업로드 UI, 올린 즉시 참가자 화면 반영. 데모용 가상 강의자료 PDF 제작 포함. **업로드는 BE-6 의존**이나, 로컬 PDF로 뷰어 개발까지는 먼저 할 수 있다.
**왜** — 실무에서 **연자가 늦게 도착해 자료가 행사 진행 중에 올라왔다**([[field-experience]]). 자료를 올리는 곳은 사무실 책상이 아니라 현장이었고, 그때까지 빈 목록이 그냥 결함처럼 보였다. 뷰어만으로는 이 상황을 다루지 못한다.
**완료 기준** — **모바일·태블릿에서 페이지 이동·확대가 동작**(`<iframe>` 방식은 iOS Safari에서 깨져 기각). 자료 없는 상태가 "준비 중"으로 읽힘. 태블릿 화면에서 업로드 완주 가능. 번들은 lazy load로 초기 로딩에 포함되지 않음.

### FE-13. 디자인 시스템 문서화 + 공용 컴포넌트 라이브러리
**무엇** — 두 갈래를 한 과제로 묶는다(서로 맞물려 있어 쪼개면 순서 의존이 생긴다). ① **디자인 시스템**: [[design]]을 컨셉 문서에서 실행 규격으로 승격 — `globals.css`의 CSS 변수 토큰(라이트/다크 페어 전체)을 이름·용도·대비비 기준과 함께 표로 정의하고, 타이포 스케일·간격·라운드·그림자 단계를 코드와 1:1로 맞춘다. 상태 의미색(진행중/검수대기 등)의 **다크 페어를 이번에 정의**한다(알려진 갭, [[log]] 2026-08-19). ② **공용 컴포넌트**: `lib/ui.ts`의 스타일 객체(`ghostBtn`/`primaryBtn`/`seg`/`pillStyle`)와 화면마다 반복되는 인라인 패턴(카드, 섹션 제목, 입력 필드, 상태 배지, 빈 상태)을 `components/ui/`의 실제 React 컴포넌트로 추출하고, 셸 화면 4곳이 이를 사용하도록 교체한다. **참가자 마이크로사이트는 범위 밖** — 행사 테마는 런타임 파생이라 도구 색 체계와 섞지 않는다([[design]] 색 분리 원칙). **BE 의존 없음.**
**왜** — 토큰은 CSS 변수로 체계화됐지만 컴포넌트 층이 없어서, 같은 카드·배지·버튼이 화면마다 인라인 스타일로 복제돼 있다. 다크모드 배지 갭이 정확히 이 구조의 비용이다 — 스타일이 한 곳에 있었다면 페어 하나 추가로 끝났을 일이 전 화면 수색이 됐다. FE 담당자와의 협업에서도 "어떤 색·컴포넌트를 쓰면 되는가"의 정본이 없으면 회신 왕복이 생긴다. README가 이미 인라인 스타일을 트레이드오프로 명시하고 정리 방향을 예고한 상태다.
**완료 기준** — [[design]]에 토큰 표(라이트/다크 전체)와 컴포넌트 목록·사용 규칙이 실림. `components/ui/`의 컴포넌트로 셸 4개 화면의 해당 패턴이 교체되고 시각 회귀 없음(교체 전후 스크린샷 대조). 상태 배지가 다크모드에서 튀지 않음. lint·build 통과.

### FE-14. FSD(Feature-Sliced Design) 아키텍처 적용
**무엇** — 평평한 `components/` + `lib/` 구조를 FSD 레이어(`app`/`pages`/`widgets`/`features`/`entities`/`shared`)로 재편한다. 먼저 **레이어 매핑 ADR**을 쓰고 나서 옮긴다 — 대략의 방향은: `lib/ui.ts`·`globals.css` 토큰·공용 컴포넌트(FE-13 산출물)→`shared/`, 이벤트·세션·테마 타입과 데이터 접근→`entities/`, Q&A·설문·테마 편집 같은 사용자 행동 단위→`features/`, 셸 화면 4개→`widgets/`+`pages/`. **주의**: Next.js App Router의 `app/` 디렉터리와 FSD의 `app` 레이어 이름 충돌, 그리고 `Microsite`(에디터 프리뷰와 참가자 뷰어가 같은 컴포넌트를 공유하는 이 프로젝트의 핵심 설계)가 어느 슬라이스에 속하는지를 ADR에서 반드시 결정한다. 이동은 **한 번에 전부가 아니라 레이어 단위로** 진행하고 각 단계마다 build를 통과시킨다. FE-2(라우트 분리)·FE-13(공용 컴포넌트)과 같은 파일을 건드리므로, **착수 시점에 그 둘이 진행 중이면 완료를 기다리거나 흡수 범위를 명시**한다. **BE 의존 없음.**
**왜** — 화면이 4개일 때는 평평한 구조가 싸지만, 열린 과제들(Q&A 연결, 설문 재설계, PDF 뷰어, 오프라인 대응)이 전부 "화면 조각 + 상태 + API 호출"을 한 덩어리씩 추가하는 성격이라 지금 구조로는 `components/`와 `lib/`이 기능 경계 없이 섞이며 자란다. FE 담당자와의 분업에서도 "이 기능은 이 폴더"라는 소유 경계가 있어야 충돌 없이 병렬 작업이 된다. 레이어의 단방향 의존 규칙은 프리뷰=실물 같은 구조적 보장을 지키는 데도 유리하다.
**완료 기준** — 레이어 매핑 ADR(`Decisions/`)이 있고 실제 구조가 그와 일치. import 방향이 FSD 규칙(상위→하위만)을 지키는지 eslint 규칙(예: `import/no-restricted-paths` 또는 steiger)으로 강제되고 위반 0건. 기존 화면 동작·시각 회귀 없음(스크린샷 대조). lint·build 통과.

### FE-15. 로그인·계정 관리 화면 + 게스트/계정 이원화
**무엇** — ① **게스트 로컬 워크스페이스**: 비로그인 상태의 콘솔·에디터가 `localStorage`에 영속하는 워크스페이스에서 동작한다. 첫 진입 시 클라이언트 시드로 초기화하고, 이후 이벤트 생성·수정·삭제·테마 편집이 전부 로컬에서 완결되며 **새로고침·재방문에도 유지**된다. **서버 데모 이벤트의 id를 참조하는 오버레이로 만들지 않는다** — 자정 Cron 리셋 때 기준이 사라져 조용히 깨진다([[0007-sso-and-account-model]]). ② 헤더에 "Google로 시작하기" / 로그인 후 계정 메뉴(아바타·이름·로그아웃). ③ **게스트 상태를 화면에 드러낸다** — "체험 중 · 이 브라우저에만 저장됩니다" 배너, 공개 URL 발급처럼 서버가 필요한 동작에서만 로그인 유도. ④ **로그인 시 가져오기**: 로컬에 편집분이 있으면 "체험 중 만든 이벤트 N개를 계정으로 가져올까요?"를 묻고, 수락 시 BE-15의 `POST /api/events/import`에 이벤트+테마+아젠다를 묶어 보낸다. 로컬 이벤트는 생성 시점에 **로컬 UUID(`localRef`)를 갖고 있어야** 멱등성이 성립하므로 ①에서 함께 설계한다. 응답의 건별 결과를 받아 **성공한 항목만 로컬에서 제거**하고(남기면 재로그인 때 중복 제안), 실패분은 재시도 경로를 남기며, **slug가 바뀐 이벤트를 화면에 알린다**. 거절 시 로컬 보존. ⑤ 계정 설정 화면 — 프로필(이름·아바타·이메일), 연결된 제공자, 로그아웃, **계정 삭제**(삭제 범위 명시: 내 이벤트·아젠다·자료·질문·설문 응답 전부). ⑥ 로그인 후 원래 있던 화면으로 복귀. **①③은 BE 의존 없음, ②⑤는 BE-12·BE-13 의존, ④는 BE-15 의존.** PR #9(FE-1 이벤트별 상태 분리)가 이 워크스페이스의 상태 층이므로 머지 후 착수한다.
**왜** — 게스트에게 "저장이 안 된다"만 알리고 편집을 휘발시키면 **만져본 결과를 확인할 수 없어 체험 자체가 성립하지 않는다.** 반대로 로그인 벽이 먼저 보이면 ADR 0001이 지키려던 "30초 안에 판단"이 무너진다. 로컬 영속이 두 요구가 만나는 지점이고, **이 과제가 그 양립을 화면에서 판정한다.** 가져오기를 넣는 이유는 사용자 입장에서 **로그인이 잃는 행동이 되어서는 안 되기** 때문이다 — 공들여 만든 것이 로그인으로 사라지면 다시는 로그인하지 않는다.
**완료 기준** — 비로그인으로 이벤트를 만들고 테마를 바꾼 뒤 **브라우저를 닫았다 다시 열어도 그대로 있음**. 로그인 → 가져오기 수락 → **아젠다·테마까지** 서버에 `owner_id`와 함께 저장되고 성공분만 로컬에서 비워짐(가져오기 도중 새로고침해도 중복 생성 0) → 로그아웃 → 게스트 워크스페이스가 중복 없이 빈 상태. 다른 계정으로 로그인하면 남의 이벤트가 목록에 없음. 계정 삭제 후 재로그인 시 빈 상태. 게스트 데이터가 이 브라우저에만 있다는 사실이 화면에 드러남(조용히 사라지지 않게). 모든 운영자 화면에 대해 "게스트에게 어떻게 보이는가"를 확인한 기록을 남김. **`localStorage` 용량 판단 기록**: FE-8의 대표 이미지가 `key_visual`에 base64로 들어가면 5MB에 닿으므로, 이미지 제외·참조·IndexedDB 중 무엇을 골랐는지와 근거.

### FE-17. 참가자 화면 탭바가 장식용이고 engage.chat·engage.cert가 어디서도 안 쓰임
**무엇** — `Microsite`의 상단 탭바(아젠다·자료·Q&A·설문)가 `onClick` 없는 순수 장식 요소라 실제 탭 전환이 없고(모든 섹션이 한 페이지에 죽 이어져 스크롤됨), 어떤 `engage` 토글을 꺼도 탭 4개가 그대로 보인다. `engage.chat`("현장 채팅")은 코드베이스 어디에도 소비하는 화면이 없고(채팅 기능 자체가 아직 없음), `engage.cert`("수료증 자동 발급")도 참가자 화면에 연결된 적이 없다(수료증 생성 자체는 FE-4에서 구현됐지만 지금은 스튜디오 미리보기 전용, FE-3/FE-4 로그 참고). 탭 전환 UI를 실제로 만들거나(토글 꺼진 탭 숨김 포함), 최소한 꺼진 토글의 탭은 안 보이게라도 하는 범위 결정 필요.
**왜** — PR #9 최종 코드리뷰(2026-09-02)가 발견. 다만 확인해보니 **이번 작업으로 생긴 회귀가 아니라 Microsite가 처음 만들어질 때부터 있던 특성**이다 — FE-3(Q&A)·FE-4(수료증)는 각자의 섹션 안 콘텐츠만 실제로 연결했을 뿐, 탭바 자체의 전환 기능은 손댄 적이 없다. 실제 채팅 기능 구현은 이 과제들과 별개의 큰 작업이라 지금 범위에 욱여넣지 않았다.
**완료 기준** — 범위 결정(탭 전환을 실제로 만들지, 꺼진 토글만 숨길지) 후 그에 맞는 완료 기준을 다시 씀. `engage.chat`은 실제 채팅 UI가 없는 한 토글 노출 자체를 재검토(만들 계획이 없다면 EngageSection에서 뺄지 결정).

### FE-23. 공개하기 버튼이 실제 공개 액션이 아님 — 상태 전환·공개 URL·비공개 되돌리기
**무엇** — 에디터 헤더의 `공개하기`(`StudioShell.tsx:243`)가 지금 하는 일은 `openViewer()` → `patch({ viewerOpen: true })`가 전부다. **미리보기 오버레이만 열릴 뿐 서버로 나가는 요청이 하나도 없고, 이벤트 상태도 그대로이며, 참가자에게 줄 주소가 화면 어디에도 나타나지 않는다.** 필요한 동작 세 가지:

| 순서 | 동작 |
|---|---|
| ① | 누르면 `PATCH /api/events/[id]`로 `status`를 `공개`로 올린다 |
| ② | 성공하면 공개 URL(`/{slug}`)을 화면에 띄운다 — 복사 버튼 포함 |
| ③ | 버튼이 `비공개`로 바뀌고, 다시 누르면 `status`를 비공개 상태(`초안`)로 되돌린다 |

**서버는 이미 준비돼 있다 — 새 BE 작업 불필요.** BE-23이 상태 모델을 발행 상태 4종(`초안`·`검수대기`·`공개`·`보관`)으로 재정의하고 쓰기 검증까지 넣었다([[0009-event-status-axes]]). 참가자 경로는 `PUBLIC_STATUSES = {공개}`로 게이트돼 나머지 셋이면 `/{slug}`가 **404**로 떨어진다(`assertPublicEvent`). 즉 FE가 `공개`·`초안`만 올바르게 보내면 공개/비공개가 그대로 작동하고, 목록 밖의 값은 서버가 400으로 막아준다.

**선행 판단 필요** — 스튜디오의 `ev`는 `useStudio()`가 들고 있는 로컬 목업(`SEEDED_EVENTS`)이라 **D1 이벤트 id가 아니다**(FE-5·FE-19·BE-20이 반복해서 부딪힌 그 원인). 목업 id를 그대로 `PATCH`에 실으면 남의 이벤트를 건드리거나 404가 난다. 범위를 ⓐ 스튜디오를 서버 워크스페이스에 연결한 뒤 착수(FE-15 ①④ 이후)할지, ⓑ FE-3·FE-5가 쓴 방식대로 **실제 공개 이벤트 하나를 slug로 지목하는 경로에서 먼저 성립**시킬지 결정하고 시작한다.
**왜** — 지금은 운영자가 "공개했다"고 믿을 근거가 화면에 없다. 버튼을 눌러도 미리보기만 뜨고, 참가자에게 보낼 주소를 어디서 얻는지 화면이 알려주지 않으며(콘솔 카드의 슬러그는 읽기 전용 텍스트다), 한번 공개한 뒤 내리는 경로는 콘솔 「선택 모드」의 일괄 상태 변경뿐인데 그마저 로컬 목업 상태만 바꾸고 D1에 닿지 않는다(`StudioShell.tsx:333`). **행사 당일 잘못 공개된 페이지를 즉시 내리지 못하는 것은 현장에서 되돌릴 수 없는 종류의 문제다** — 되돌리기가 없는 공개 버튼은 공개 기능이 아니다.
**완료 기준** — `공개하기`를 누르면 `PATCH`가 실제로 나가고(네트워크 탭), **새로고침 후에도 상태가 유지된다**(D1 반영 확인). 화면에 뜬 URL을 복사해 **다른 브라우저**로 열면 참가자 페이지가 열린다. 버튼이 `비공개`로 바뀌고, 누르면 같은 URL이 **404**로 바뀐다(없는 slug와 구분되지 않는 404여야 한다 — 존재를 흘리지 않는 기존 규칙 유지). 대비비 미달(`canPublish === false`)일 때 공개 전환이 막히는 기존 게이트는 그대로 유지된다. 실패 응답(404·400·네트워크 끊김)이 화면에 사유로 드러나고, 실패했는데 버튼만 `비공개`로 바뀌는 일이 없을 것.

### FE-24. 발행 상태를 화면에서 실제로 바꿀 수 있게 한다 (BE-23 재정의 후속)
**무엇** — BE-23이 상태 모델을 두 축으로 갈랐다([[0009-event-status-axes]]) — **발행 상태 4종은 저장·사람이 바꾸고, 행사 시점 3종은 `event_date`에서 파생된다.** 서버·목업·배지·필터 칩은 그 모델로 이미 정렬됐고, 응답에 파생 `phase`도 실려 온다. **남은 것은 "사람이 바꾸는 쪽"의 화면이다.**

| 상태 | 누가/무엇이 바꾸나 | 지금 |
|---|---|---|
| `초안` ↔ `공개` | 운영자 — **FE-23의 공개하기/비공개 버튼이 곧 이 전이다** | FE-23에서 닫힘 |
| `→ 보관` | 운영자 수동. 되돌릴 수 있어야 한다 | 콘솔 「선택 모드」에 있으나 **로컬 목업만 바꾸고 D1에 안 닿는다**(`StudioShell.tsx:333`) |
| `초안` → `검수대기` | **미정** — 검수 요청을 누가 받는가 | 검수자도 승인 동작도 코드에 없다 |
| 행사 시점 | 달력 (파생) | 완료 — 사람이 건드릴 것 없음 |

그래서 이 과제에 남은 것은 둘이다. ① **일괄 상태 변경을 실제 `PATCH`로 연결**한다(FE-23과 같은 선행 판단을 공유한다 — 스튜디오 `ev`가 D1 id가 아닌 로컬 목업이다). ② **`검수대기`의 존폐를 결정**한다 — 승인자를 정하려면 BE-12(계정 모델)가 먼저이므로, 그때까지 상태를 남겨둘지 지금 뺄지를 판단한다. **승인자가 필요 없다는 결론이면 빼는 것도 유효한 결과다** — 지키지 않는 상태를 화면에 남겨두는 것이 더 나쁘다.
**왜** — 재정의로 "달력이 정하는 것"은 전부 자동이 됐지만, **사람이 정하는 것을 사람이 바꿀 방법은 여전히 화면에 없다.** 콘솔의 일괄 변경은 새로고침하면 사라진다. `검수대기`는 아무도 지키지 않는 칸으로 남아 있고, 그게 이 과제가 처음 등록된 이유다(FE-17의 장식용 탭바와 같은 종류의 문제).
**완료 기준** — 일괄 상태 변경이 실제 `PATCH`로 나가고 새로고침 후에도 유지된다. `보관`으로 내린 이벤트의 공개 URL이 404가 되고, 되돌리면 다시 열린다. `검수대기` 결정을 [[design]] 또는 ADR에 근거와 함께 남기고, 빼기로 했다면 `EVENT_STATUSES`·배지·필터 칩에서 함께 사라진다(정본이 `lib/status.ts` 하나이므로 한 곳만 고치면 된다). **BE 의존 없음** — BE-23이 끝났다.

## 열린 과제 — 백엔드(BE)

### BE-12. 인증 기반 — Google SSO + D1 세션 + 이벤트 소유권 컬럼
**무엇** — [[0007-sso-and-account-model]]대로 구현한다. ① 마이그레이션 0004: `users`·`oauth_accounts`·`auth_sessions`(**이름 주의** — 기존 `sessions`는 아젠다 세션이다) + `events.owner_id`(NULL = 데모 이벤트). ② OAuth 라우트 4개 — `GET /api/auth/google`(state + PKCE 발급), `GET /api/auth/callback/google`(state 대조 → 토큰 교환 → `iss`/`aud`/`exp` 확인 → 사용자 upsert → 세션 발급), `POST /api/auth/logout`, `GET /api/auth/me`(게스트는 200 + `null`). ③ 세션은 랜덤 토큰을 httpOnly 쿠키로 주고 D1에는 SHA-256 해시만 저장, 쿠키는 `SameSite=Lax`·`Secure`·`Path=/`이며 `__Host-` 접두사는 **환경별로 분기**(로컬 dev는 http라 동작하지 않음). ④ **같은 커밋에서** `lib/seed.ts:22`의 `DELETE FROM events`를 `WHERE owner_id IS NULL`로 한정한다. ⑤ 만료 세션 정리를 기존 자정 Cron에 추가. **의존은 BE-1뿐.** 사람 손 작업이 하나 있다: Google Cloud Console에서 OAuth 클라이언트 생성 + redirect URI 등록, `wrangler secret put`으로 `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET` 주입.
**왜** — 운영자 CRUD가 인가 검사도 rate limit도 없이 열려 있어 **누구나 남의 이벤트를 수정·삭제(CASCADE)** 할 수 있다. BE-10(질문 숨김)이 여기 얹히면 무인증 운영자 엔드포인트가 하나 더 늘어나므로 그 전에 기반을 놓아야 한다. ④는 미루면 안 되는 종류다 — `owner_id`가 생긴 시점부터 자정 Cron이 매일 사용자 데이터를 통째로 지운다.
**완료 기준** — 로그인 → 이벤트 생성 시 `owner_id`가 채워짐. 로그아웃 후 쿠키·세션 행 모두 소멸. 만료 세션으로 요청 시 게스트로 취급(500 아님). `state` 불일치·`code` 재사용·만료 `id_token`을 각각 거부하는 것을 실측. **자정 리셋 시 `owner_id IS NOT NULL` 이벤트가 살아남는 것을 실측**(시각을 앞당겨 Cron 핸들러 직접 호출). 직접 구현한 흐름이므로 **코드리뷰 통과를 완료 기준에 포함**한다. 로컬·프로덕션 양쪽 실측.

### BE-13. 인가 경계를 운영자 API에 적용 (이벤트 소유권 강제)
**무엇** — BE-12의 세션을 실제 권한 판정에 연결한다. ① `POST /api/events`는 로그인 필수(401), 생성 시 `owner_id = 현재 사용자`. ② `PATCH`/`DELETE /api/events/[id]`는 소유자만 — **남의 것이면 403이 아니라 404**로 존재 자체를 흘리지 않는다(BE-7이 이미 채택한 원칙과 일관). ③ `GET /api/events`는 로그인 시 내 이벤트, 게스트는 데모 이벤트(`owner_id IS NULL`)만. ④ 하위 리소스(아젠다·자료, 그리고 BE-10의 질문 숨김)는 상위 이벤트의 소유자 확인을 거친다. ⑤ 참가자 경로(`/api/public/[slug]`, Q&A·설문 POST)는 **무인증 유지** — 여기에 로그인을 요구하면 제품이 깨진다. ⑥ 세션 조회를 대상 조회와 D1 `batch`로 묶어 요청당 왕복을 늘리지 않는다. ⑦ **운영자 쓰기에 rate limit을 넣는다** — 지금 전혀 없고, FE-15의 "가져오기"가 로컬 이벤트 N개를 한 번에 올리는 대량 쓰기 경로가 된다. 계정당 이벤트 수 상한도 함께 판단한다(무료 티어 압박 방지). 판정은 `lib/rate-limit.ts`를 재사용하되 키가 IP·토큰이 아니라 **user_id**라는 점이 다르다. **BE-12 의존.**
**왜** — 스키마에 `owner_id`만 있고 라우트가 읽지 않으면 구멍은 그대로다. BE-12와 나눈 이유는 ①~④가 기존 라우트 전부를 건드려 회귀 위험이 다르기 때문이며, 특히 ⑤를 실수로 함께 잠그면 참가자 참여 기능이 통째로 죽는다.
**완료 기준** — 계정 A가 만든 이벤트를 계정 B가 `PATCH`/`DELETE` 시 404. 비로그인 `POST /api/events` 401. 이벤트 20개 연속 생성(가져오기 시뮬레이션)에서 상한이 사유와 함께 걸림. **참가자 경로는 무인증으로 그대로 동작**(공개 조회 200, Q&A·설문 POST 201) — 회귀 실측 필수. 요청당 D1 왕복이 BE-12 이전 대비 늘지 않았음을 확인. README「알고 있는 한계」의 무보호 서술 갱신.


### BE-15. 게스트 워크스페이스 가져오기 엔드포인트
**무엇** — `POST /api/events/import` — 이벤트 + 테마 + 아젠다를 묶어 받아 **이벤트 단위로 D1 `batch` 한 번**에 생성한다([[0007-sso-and-account-model]] §1-1). ① **멱등성**: `events.client_ref` 컬럼 + `UNIQUE(owner_id, client_ref)`로 받아 재요청 시 새로 만들지 않고 기존 행을 돌려준다 — 네트워크가 끊겨 다시 누르는 것을 정상 경로로 취급. ② **원자성 단위는 이벤트 하나** — A 성공·B 실패면 A는 커밋된 채 두고 건별 결과 배열을 돌려준다(전체 롤백은 "9개 성공했는데 10번째 때문에 처음부터"가 되어 더 나쁘다). ③ `ensureUniqueSlug`로 slug가 바뀐 항목을 응답에 실어 화면이 알릴 수 있게 한다. ④ 이벤트 수·이벤트당 아젠다 수 상한(초과 400) + BE-13의 쓰기 rate limit 적용. **BE-12·13·14 의존.**
**왜** — 이벤트마다 `POST` → 테마 `PATCH` → 아젠다 N회를 돌리면 왕복이 수십 회로 늘어 무료 티어 쓰기를 낭비하고, 중간에 끊기면 **테마 없는 이벤트·아젠다 없는 이벤트 같은 반쪽 상태**가 서버에 남으며, 재시도가 중복을 만든다. 가져오기는 사용자가 "로그인하면 잃는다"를 겪지 않게 하는 장치인데 그 과정이 데이터를 깨면 목적과 정반대가 된다.
**완료 기준** — 로컬 이벤트 3개(각 아젠다 6개·테마 포함)를 가져와 전부 `owner_id`와 함께 저장됨. **같은 요청을 두 번 보내도 중복 생성 0**(멱등성 실측). 중간 실패 주입 시 성공분은 남고 실패분만 재시도로 복구됨. slug 충돌 시 변경 사실이 응답에 실림. 상한 초과 400. 남의 `client_ref`로는 남의 이벤트에 닿지 못함.

### BE-22. 커스텀 도메인 + 엣지 rate limiting
**무엇** — 커스텀 도메인을 붙여 존(zone)을 만들고, Cloudflare의 WAF/Rate Limiting Rules로 **무효 요청을 워커 도달 전에** 끊는다. `sympo-studio.fomula91.workers.dev`(workers.dev)에는 이 규칙을 적용할 수 없다 — 존이 필요하다.
**왜** — [[0008-rate-limit-counter]]가 판정한 것: 무효 요청 플러드의 실제 피해는 "D1이 마른다"가 아니라 **"Workers 요청 한도(10만/일)가 소진돼 그날 사이트가 죽는다"**이고, 요청이 이미 워커에 도착한 뒤라 **애플리케이션 rate limit으로는 원리적으로 막을 수 없다.** 맞는 층은 엣지다. 커스텀 도메인은 BE-2가 "이번에 하지 않는 것"으로 미뤄 둔 항목이라 여기서 함께 판단한다.
**완료 기준** — 커스텀 도메인에서 앱이 뜨고, 엣지 규칙이 실제로 요청을 차단하는 것을 실측(차단된 요청이 Workers 지표에 안 잡히는지). 무료 플랜에서 쓸 수 있는 규칙 수 제약을 함께 기록.

### FE-18. 대비비 게이트가 실제 키비주얼 이미지 위 텍스트 대비는 검사하지 않음
**무엇** — `lib/theme.ts`의 "히어로 텍스트 / 키 비주얼" 대비비 행은 브랜드 프리셋 색으로 합성한 배경(`oklch(...)`)만 검사한다. 실제 렌더(`Microsite.tsx`)는 운영자가 올린 **임의의 이미지** 위에 반투명 그라디언트(라이트 모드는 검정 18~58%)를 얹고 그 위에 흰 라벨을 그린다 — 흰 배경 이미지를 올리면 실제 대비가 게이트 계산과 무관하게 크게 낮아질 수 있다.
**왜** — Codex CLI 교차 리뷰(2026-09-02)가 발견. "대비비 미달 조합은 만들 수 없다"가 이 제품의 핵심 주장(FE-7)인데, 게이트가 실제로 검사하는 범위와 사용자가 이해하는 범위(키 비주얼 포함 전체 화면)가 다르다는 게 문서화된 적이 없다.
**완료 기준** — 범위 결정 필요: ① 키 비주얼 위 텍스트도 실측하도록 게이트를 확장(캔버스로 이미지 픽셀 샘플링 + 오버레이 합성 후 대비 계산, 상당한 작업)하거나 ② 최소한 "이 게이트는 브랜드 색만 검사하고 업로드 이미지는 검사하지 않는다"는 한계를 UI 문구·README에 명시. 어느 쪽이든 결정 근거를 ADR 또는 [[design]]에 남김.

### FE-19. 키비주얼이 blob: URL이라 새로고침·서버 저장에서 살아남지 못함
**무엇** — `EditorScreen.tsx`가 업로드한 키 비주얼을 `URL.createObjectURL(f)`로만 저장한다(리뷰 후 revoke 누락은 이번에 고침, [[log]]). blob URL은 이 브라우저 탭에서만 유효해 새로고침하면 깨지고, 애초에 서버로 보낼 수 있는 값이 아니다.
**왜** — Claude 코드리뷰(2026-09-02)가 발견. 지금은 스튜디오가 BE-1 CRUD에 연결된 적이 없어(BE-20과 같은 이유) 잠복 상태지만, FE-15의 로그인 시 가져오기나 향후 BE PATCH 연결 시점에 그대로 보내면 참가자 페이지에 키 비주얼이 영영 안 뜬다. base64 인코딩(용량 문제, FE-15의 `localStorage` 5MB 논의와 연결) 또는 실제 파일 업로드(R2, BE-6 확장) 중 선택 필요.
**완료 기준** — BE-1 CRUD 연결 시점(FE-15 전후) 전에 방식 결정. 결정 전까지는 blob URL이 세션을 못 넘긴다는 한계를 알고 있는 상태로 유지.
