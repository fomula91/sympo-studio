# sympo-studio — 과제

앞으로 할 일 전체의 정본. **에이전트용 고밀도 문서**이고, 사람이 읽고 바로 착수할 판단은 → **[[Summaries/Next]]**

## 과제와 Next-Task의 관계

```
과제 (이 문서 전체)
├── Next-Task ······· 핫픽스 · 긴급 · 꼭 필요한 것.  먼저 처리한다
├── 열린 과제 — FE ·· 나머지 프론트엔드 백로그
└── 열린 과제 — BE ·· 나머지 백엔드 백로그
```

- **과제**는 총칭이다. 아래 세 섹션에 있는 것이 전부 과제다.
- **Next-Task**는 과제 중 **지금 먼저 해야 할 것**만 골라 담는 자리다. 아래 셋 중 하나에 해당하면 여기 적는다.

| 넣는 기준 | 뜻 |
|---|---|
| **핫픽스** | 배포된 것이 실제로 깨져 있다 |
| **차단** | 이게 정해지지 않으면 다른 과제를 착수할 수 없다 |
| **필수** | 이미 완료 기준을 어기고 있거나, 사용자에게 드러나는 결함이다 |

- **새 과제는 기본적으로 FE/BE 백로그에 넣는다.** 위 기준에 맞을 때만 Next-Task로 올린다 — 전부 급하면 아무것도 급하지 않다.
- Next-Task도 **똑같은 과제**라 번호 체계(`FE-N`/`BE-N`)를 공유한다. 급한 상태가 풀리면 백로그로 내리고, 끝나면 [[Archive/Closed-Tasks]]로 옮긴다.

> **형식 계약 (훅이 파싱한다)** — 과제 제목은 `### FE-N. 제목` / `### BE-N. 제목`.
> SessionStart 훅은 **`## 열린 과제`로 시작하는 섹션**의 `### FE-`·`### BE-` 줄만 추출해 주입한다. 그래서 세 섹션 제목이 전부 `## 열린 과제`로 시작한다 — **바꾸면 그 섹션이 통째로 주입에서 빠진다.** 파일명 `Next-Tasks.md`도 훅이 하드코딩해 읽으므로 바꾸지 않는다.
> 섹션 헤더는 주입되지 않아 **제목의 `FE-`/`BE-` 접두사가 유일한 구분자**다. 추출이 0건이면 형식 오류 문구가 대신 주입된다.
> 새 과제는 `무엇 → 왜 → 완료 기준`으로 쓴다. **남은 번호를 다시 매기지 않는다**(로그·ADR 참조가 깨진다).
> 근거 [[0003-next-tasks-fe-be-split]] · 작성 규칙 본문은 `CLAUDE.md`의 「Next-Tasks 작성 규칙」.

문제 정의의 정본은 [[field-experience]]다. 과제의 `왜`를 쓸 때 **거기 없는 내용을 근거로 삼지 않는다** — 기존 README가 그렇게 무너졌다([[0004-problem-redefinition]]).

핫픽스·차단·필수에 해당하는 것만 여기 둔다. 급한 상태가 풀리면 아래 백로그로 내린다.

FE-49·51·52는 2026-10-13 전체 리뷰(PR #77, 브라우저 실측 + 코드 대조)에서 나왔다 — 셋 다 **화면에 드러나는 결함**이라 「필수」로 올렸다. FE-50은 2026-10-26 버튼을 숨기는 쪽으로 닫았다([[Archive/Closed-Tasks]]).
경로는 현재 `main` 기준이다. FE-14(PR #79)가 머지되면 `components/`가 `src/frontend/` 아래로 옮겨지니 **함수·심볼 이름으로 찾는다.**

### FE-49. 아젠다 세션의 시간·제목·연자·종류를 편집하는 UI
**무엇** — `components/screens/EditorScreen.tsx`의 `AgendaSection` 세션 행은 시간(`x.time`)·제목(`x.title`)·연자(`x.speaker`)·종류(`x.kind`)가 전부 정적 `<div>`다. `input`·`contentEditable`·모달이 어디에도 없어, 가능한 조작은 `SESSION_LIB`(고정 3개 템플릿) 추가·순서 변경·삭제뿐이다. 행마다 입력칸(종류는 `select`)을 두고 기존 `patchEvent` → 세션 저장 큐(`flushSessionSave`)로 연결한다. 서버 `PUT /api/events/[id]/sessions`는 이미 네 필드를 자유 텍스트로 받으므로 **FE만 하면 된다.**
**왜** — 운영자가 세션 내용을 직접 입력할 방법이 없다. FE-55(템플릿 반복 시 완전 중복)와 겹치면, 세션이 3개를 넘는 실제 행사는 원하는 아젠다를 아예 만들 수 없다.
**완료 기준** — 에디터에서 세션 네 필드를 고침 → "방금 저장됨" → 새로고침해도 유지 → 참가자 화면(`/{slug}`)에 같은 값. 게스트 이벤트는 로컬 저장으로 같은 흐름. lint·build 통과.

### FE-51. 아젠다 순서 핸들을 클릭만 해도 "변경 저장 중…"에서 멈춘다
**무엇** — `EditorScreen.tsx` `startDrag`의 `up`(`pointerup`)이 실제로 이동했는지와 상관없이 `patch({ dragIdx: -1, saved: savingMessage(isServerEvent) })`를 부른다(146~149행). 이동이 없으면 `patchEvent`가 불리지 않아 저장 큐가 비어 있고, 문구를 "방금 저장됨"으로 되돌릴 타이머도 없다. 이동이 있었을 때만 저장 문구로 바꾼다.
**왜** — 요청도 콘솔 로그도 없는 거짓 "저장 중"이 영구히 남는다(새로고침 직후 클릭 한 번으로 100% 재현). 터치로 핸들을 스치기만 해도 생긴다.
**완료 기준** — 핸들 클릭(이동 없음) → 저장 문구가 바뀌지 않음. 드래그로 실제 이동 → "저장 중" → "방금 저장됨". 키보드 재정렬(ArrowUp/Down)도 그대로 동작.

### FE-52. 하드 리로드 직후 사이드바를 누르면 엉뚱한 이벤트로 이동한다
**무엇** — `StudioShell.tsx:294` `goTo()`가 `effectiveId`가 아니라 `ev.id`로 `router.push`한다. 서버 전용 id(시드 0~14 밖)는 상세 조회가 끝나기 전엔 `s.events`에 없어 `ev = s.events.find(...) ?? s.events[0]`가 시드 이벤트로 폴백하고, 그 id(0)로 이동한다. 이동 대상은 URL의 이벤트 id(`effectiveId`)를 쓴다.
**왜** — `/events/27/edit`를 새로고침하고 1초 안에 「에디터」·「테마」를 누르면 `/events/0/edit`로 가서 "이벤트를 불러오지 못했습니다"가 뜬다(재현됨). 다른 이벤트로 가는 실제 오작동이다.
**완료 기준** — 서버 이벤트 편집 화면을 하드 리로드한 직후 사이드바를 눌러도 같은 id에 머문다. 콘솔에서 다른 이벤트를 고른 뒤의 이동은 그대로.


## 열린 과제 — 프론트엔드(FE)

**전체 조망의 흐름 묶음 순서를 따른다** — 대부분은 여전히 서로 독립이라 자유롭게 고를 수 있지만, 묶음 1~4는 순서대로 착수해야 화면으로 끝까지 검증할 수 있다(위 표 참조). 각 항목의 `무엇`에도 어느 묶음 소속인지 적어둔다.

### FE-14. FSD(Feature-Sliced Design) 아키텍처 적용 — 단계별 적용 [묶음 6]
**진행 상태(2026-10-19)** — [[0015-frontend-fsd-boundaries]] 기준 1~4단계 코드 구현과 ESLint 경계 검사를 같은 `fe-14-architecture-adr` 브랜치/PR #79에 반영했다. build·앱 소스 lint·테스트 171건 통과, 게스트 편집/복원 및 미리보기 화면 확인. 로그인 서버 저장·업로드·실패 알림 E2E와 동일 데이터 전후 시각 대조가 남아 FE-14는 열린 상태, PR은 draft로 유지한다.
**무엇** — 평평한 `components/` + `lib/` 구조를 FSD 레이어(`app`/`pages`/`widgets`/`features`/`entities`/`shared`)로 재편한다. **한 번에 전부가 아니라 5단계로 나누고, 하나의 브랜치에서 단계별 커밋으로 진행한다. 0단계는 ADR을 검토하고, 코드 변경 단계(1~4단계)는 lint·build 통과·기존 화면 동작·시각 회귀 없음(스크린샷 대조)을 확인한다**(2026-10-14 범위 재정의, 근거는 「왜」).
- **0단계 — ADR**: 레이어 매핑을 정하면서 ① Next.js App Router의 `app/` 디렉터리와 FSD `app` 레이어의 이름 충돌 처리 방법 ② `Microsite`(에디터 프리뷰와 참가자 뷰어가 같은 컴포넌트를 공유하는 이 프로젝트의 핵심 설계)가 속할 슬라이스 ③ 서버 전용 코드(`lib/db.ts`·`auth.ts`·`rate-limit.ts` 등)를 FSD 대상에서 뺄지를 함께 결정한다.
- **1단계 — shared + 대형 파일 분리**: `lib/ui.ts`·`globals.css` 토큰·공용 컴포넌트(FE-13 산출물, `components/ui/`)를 `shared/`로 옮기고, `EditorScreen.tsx`(기본정보·아젠다·테마·자료·참여 5개 섹션이 한 파일, 1,700줄)를 섹션별 파일로 나눈다. 뒤따르는 FE 수정(아젠다 세션 편집 UI 등)보다 먼저 해두면 그 작업들의 충돌·리뷰 비용이 줄어든다.
- **2단계 — entities**: 이벤트·세션·자료·테마의 타입과 데이터 접근(`lib/studio-api.ts` 등)을 옮긴다.
- **3단계 — features**: Q&A, 설문, slug 편집, 테마 추출 같은 사용자 행동 단위를 옮긴다.
- **4단계 — widgets/pages + import 방향 강제**: 셸 화면을 `widgets/`+`pages/`로 옮기고, import 방향이 FSD 규칙(상위→하위만)을 지키는지 eslint 규칙(`import/no-restricted-paths` 또는 steiger)으로 강제해 위반 0건을 만든다.
**왜** — 등록 당시(2026-08) 근거였던 "열린 과제들이 계속 쌓이며 구조가 섞인다"의 그 과제들(Q&A 연결·설문 재설계·PDF 뷰어·오프라인 대응)은 전부 닫혔지만, 그 근거는 이미 다른 것으로 대체됐다 — PR #77 리뷰에서 아젠다 세션 편집 UI·Q&A 모더레이션 화면·프리셋 삭제·템플릿 복제 구현·not-found 페이지 같은 새 FE 작업이 나왔고, `EditorScreen.tsx`(1,700줄)·`StudioProvider.tsx`(1,166줄: 상태·서버 동기화·저장 큐)·`StudioShell.tsx`(704줄: 셸·라우팅·일괄 작업)에 이미 여러 책임이 한 파일에 몰려 있다. #77이 찾은 실제 오작동(드래그 핸들 "저장 중" 멈춤, 복제 버튼 무동작, 사이드바 내비게이션 레이스)도 전부 이 세 파일에서 나왔다. 분업할 때도 "이 기능은 이 폴더"라는 소유 경계가 있어야 같은 파일을 동시에 고치는 충돌이 줄어든다.
**완료 기준** — 0단계는 목표 레이어·슬라이스, 현재 파일의 이동 계획, 예외와 적용 제외 범위를 레이어 매핑 ADR(`Decisions/`)로 확정한다. 아직 파일을 이동하지 않으므로 이 단계에서 실제 구조와의 일치를 요구하지 않는다. 코드 변경 단계(1~4단계)마다 lint·build 통과, 기존 화면 동작·시각 회귀 없음(스크린샷 대조)을 확인한다. 4단계 완료 시 실제 구조가 ADR과 일치하고, import 방향이 eslint 규칙으로 강제되며 위반 0건이어야 한다.

### FE-57. 「예상 참여 인원 — 리포트 분모로 사용」 안내가 사실이 아니다

그 앞의 **BE-40**은 PR #70(가져오기)이 등록한 과제를 그 PR보다 먼저 닫았다 — 가져오기가 참여 설정을

그보다 앞의 **BE-38**은 등록 당일 닫혔다 — PR #68이 콘솔에 삭제 버튼을 붙이자, 고치기와 같은 가드를
쓰던 `DELETE`가 공용 데모를 누구에게나 지우게 두던 구멍이 드러났다. 삭제 전용 가드 `assertCanDelete`로
데모만 403으로 막았다(편집은 그대로 열림). **파괴적인 버튼을 붙이는 FE PR은 그 경로의 서버 가드를 같이 본다.**

그보다 앞의 **BE-36**은 목록 응답에서 키 비주얼 원문을 빼고 세션·자료 개수를 실었다. 서버만 바꾸면
목록 병합이 키 비주얼을 빈 값으로 덮는 FE 회귀가 생겨, 같은 브랜치에서 FE 병합·콘솔 카드를 함께 고쳤다 —
**응답 모양을 바꾸는 BE 과제는 그 응답을 병합하는 FE 코드를 같이 본다.**

그보다 앞의 **BE-35**는 등록 전제("R2 삭제 코드가 없다")가 틀렸던 경우다 — 자정 Cron이 이미 고아
객체를 지우고 있었고, 실제 문제는 하루 지연과 리셋 실패 시 정리 누락이었다. 과제를 쓰기 전에 **같은 일을 하는
기존 코드(Cron·retention)가 있는지 먼저 찾는다.**

그 이전의 **BE-34**는 이벤트 텍스트·인원 상한을 `lib/event-limits.ts` 한 벌로 모아
POST·PATCH·가져오기·에디터가 함께 보게 했다 — 운영 D1에 초과 값은 없었다.

더 앞의 **BE-33은 코드가 아니라 설정이 비어 있던 경우**다 — 정본 도메인이 Google
콘솔의 승인된 리디렉션 URI에 없어 그 주소에서 로그인이 시작조차 못 했다. **BE-22(커스텀
도메인)의 완료 기준에 리디렉션 URI 등록이 빠져 있던 것이 원인**이라, 다음에 호스트를
추가·변경하면 그 등록을 같은 과제 안에서 함께 본다.

그보다 더 앞의 둘은 **구현이 아니라 판단으로** 닫혔다 — BE-22는 커스텀 도메인까지만 하고
엣지 rate limiting을 기각했고([[0013-edge-rate-limiting-rejected]]), BE-32는 제공자별
별개 계정을 채택된 모델로 확정하며 기각했다([[0011-account-link-key]] 「개정」).
새 BE 과제는 실제 사용에서 문제가 드러나거나 발굴할 때 생긴다.

### BE-42. 추출 브랜드 프리셋 삭제 API
**무엇** — `app/api/presets/route.ts`에 GET·POST만 있고 삭제 경로가 없다. `DELETE /api/presets/[id]`를 만든다 — `WHERE owner_id = 나`를 함께 둬 본인 추출 프리셋만 지우게 한다(공용 내장 `owner_id IS NULL`은 대상 아님, BE-25의 소유권 모델 그대로). 참조하던 이벤트는 스키마가 이미 `events.preset_id … ON DELETE SET NULL`이라 참조가 풀린다 — 그때 참가자 화면이 무엇으로 폴백하는지 확인한다. 추출 원본 이미지(`source_key`, R2)도 BE-35처럼 같이 지운다. 화면은 FE-62.
**왜** — 저장은 매끄러운데 되돌릴 수단이 서버에도 없다. 2026-10-13 리뷰 중 만든 `logo-mark` 프리셋이 지금 남아 있다 — 로컬 D1인지 운영 D1인지 확인하고, 운영이면 이 과제로 정리한다.
**완료 기준** — 본인 프리셋 삭제 200, 남의 것·내장 프리셋 404(또는 403), 비로그인 401. 참조하던 이벤트의 `preset_id`가 NULL이 되고 화면이 깨지지 않음, R2 원본 삭제. 단위 테스트 포함. `logo-mark` 정리 여부를 [[log]]에 기록.
