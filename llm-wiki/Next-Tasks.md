> 코드 repo의 SessionStart 훅이 `### FE-`·`### BE-`로 시작하는 줄만 추출해 세션에 주입한다. 섹션 헤더는 주입되지 않으므로 **제목의 `FE-`/`BE-` 접두사가 유일한 구분자**다.

**FE는 서로 독립**이라 순서 없이 아무거나 착수할 수 있다(단, 대부분 대응하는 BE에 의존한다 — 각 과제의 `무엇`에 명시).
**BE는 번호가 곧 의존 순서**다. 근거는 [[0001-backend-for-working-demo]], [[0002-cloudflare-free-tier-stack]].

현황(2026-08-26): **FE-1·2·7·8·9는 [PR #9](https://github.com/fomula91/sympo-studio/pull/9)로 올라와 리뷰 대기 중.** 지금 새로 착수 가능한 것: **FE-3**(BE 준비 완료 — [[API-Guide-FE]]가 계약), FE-4의 수료증 부분. BE 다음 추천은 **BE-8**(FE-3의 폴링이 시작되기 전에).

## 열린 과제 — 프론트엔드(FE)

### FE-3. Q&A 화면 연결
**무엇** — 참가자 화면의 "질문 남기기"를 BE-3 API에 연결. 목록 갱신은 3~5초 폴링. 전송 중·실패·rate limit 초과 상태를 화면에 드러낸다. **브라우저 익명 토큰(`crypto.randomUUID()`)을 `localStorage`에 보관하고 POST에 `x-client-token` 헤더로 실어 보낸다**([[0006-rate-limit-key]] — 안 보내면 행사장 Wi-Fi 전체가 분당 3건을 공유). 입력 영역은 **고령 사용자 기준**으로 잡는다(글자 크기, 터치 타깃 44px 이상, 안내 문구를 화면에 상시 노출). 구현 계약은 [[API-Guide-FE]]. **BE 준비 완료** — BE-3·BE-9 종료(프로덕션 반영), BE-7 공개 API 배포됨. 지금 착수 가능.
**왜** — 방문자가 남긴 것이 실제로 목록에 뜨는 순간이 이 데모의 하이라이트다. 실무에서 Q&A는 **반복 노출로 익숙해지며 사용률이 올랐으므로**([[field-experience]]), 처음 보는 사람도 설명 없이 쓸 수 있는지가 관건이다.
**완료 기준** — 다른 브라우저에서 남긴 질문이 폴링으로 나타남. rate limit 초과 시 사용자가 이유를 알 수 있음(조용히 실패하지 않음). 확대 없이 읽고 누를 수 있음.

### FE-4. 설문 흐름 재설계 + 수료증 클라이언트 생성
**무엇** — **현재의 2단 설문 구조부터 재검토한다.** 실무에서 이탈 지점을 없앴는데도 설문 응답률이 오르지 않았고 원인은 고령 사용자였다([[field-experience]]) — 끝나고 몰아 받는 2단 폼이 그 자체로 장벽일 수 있다. **세션이 끝날 때마다 1문항씩 즉시** 받는 안을 우선 검토하고, 정한 구조로 BE-4에 연결한다. 응답 완료 시 수료증을 `pdf-lib`로 **브라우저에서 생성**해 다운로드시킨다. **폼은 BE-4 의존, 수료증 생성은 독립.**
**왜** — **이 프로젝트가 도전하는 지점이 정확히 여기다**([[0004-problem-redefinition]]). 플랫폼 교체로는 실패했고 UI 접근은 시도된 적이 없다. "현장에서 사람이 하던 안내를 UI가 대신할 수 있는가"에 답하는 과제다. 서버 PDF 생성은 무료 티어에서 막히므로 수료증은 클라이언트 생성이 전제다([[0002-cloudflare-free-tier-stack]]).
**완료 기준** — 구조 선택의 근거를 ADR 또는 [[field-experience]] 갱신으로 남김(직관만으로 정하지 말 것). 응답이 저장되고 수료증 PDF가 브라우저에서 생성·다운로드됨. **응답률 가설은 검증되지 않았음을 README에 계속 명시.** 이번에 하지 않는 것: 이메일 발송 — 다운로드로 대체.

### FE-5. 리포트를 실측 데이터로 교체
**무엇** — `ReportScreen`의 하드코딩 샘플(`METRICS`/`OPS`)을 BE-5의 집계 응답으로 교체한다. **BE-5 의존.**
**왜** — 도구가 스스로를 측정하지 않으면 개선됐는지 알 수 없다는 것이 리포트 층을 넣은 이유다.
**완료 기준** — 실제 방문 데이터로 열람률이 그려짐. 실측으로 바뀐 지표에서 `샘플 데이터` 배지 제거, 남은 가상 수치는 배지 유지(README 고지와 UI 배지가 어긋나지 않을 것).

### FE-6. PDF.js 뷰어 + 현장 업로드 + 가상 강의자료 제작
**무엇** — PDF 렌더링을 **PDF.js 클라이언트**로 구현하고 페이지 이동·확대 UI를 만든다. 함께 **현장 업로드 경로**를 넣는다 — 자료 도착 전의 "준비 중" 상태 표시, 태블릿에서 올릴 수 있는 업로드 UI, 올린 즉시 참가자 화면 반영. 데모용 가상 강의자료 PDF 제작 포함. **업로드는 BE-6 의존**이나, 로컬 PDF로 뷰어 개발까지는 먼저 할 수 있다.
**왜** — 실무에서 **연자가 늦게 도착해 자료가 행사 진행 중에 올라왔다**([[field-experience]]). 자료를 올리는 곳은 사무실 책상이 아니라 현장이었고, 그때까지 빈 목록이 그냥 결함처럼 보였다. 뷰어만으로는 이 상황을 다루지 못한다.
**완료 기준** — **모바일·태블릿에서 페이지 이동·확대가 동작**(`<iframe>` 방식은 iOS Safari에서 깨져 기각). 자료 없는 상태가 "준비 중"으로 읽힘. 태블릿 화면에서 업로드 완주 가능. 번들은 lazy load로 초기 로딩에 포함되지 않음.

### FE-13. 디자인 시스템 문서화 + 공용 컴포넌트 라이브러리
**무엇** — 두 갈래를 한 과제로 묶는다(서로 맞물려 있어 쪼개면 순서 의존이 생긴다). ① **디자인 시스템**: [[design]]을 컨셉 문서에서 실행 규격으로 승격 — `globals.css`의 CSS 변수 토큰(라이트/다크 페어 전체)을 이름·용도·대비비 기준과 함께 표로 정의하고, 타이포 스케일·간격·라운드·그림자 단계를 코드와 1:1로 맞춘다. 상태 의미색(진행중/검수대기 등)의 **다크 페어를 이번에 정의**한다(알려진 갭, [[log]] 2026-08-19). ② **공용 컴포넌트**: `lib/ui.ts`의 스타일 객체(`ghostBtn`/`primaryBtn`/`seg`/`pillStyle`)와 화면마다 반복되는 인라인 패턴(카드, 섹션 제목, 입력 필드, 상태 배지, 빈 상태)을 `components/ui/`의 실제 React 컴포넌트로 추출하고, 셸 화면 4곳이 이를 사용하도록 교체한다. **참가자 마이크로사이트는 범위 밖** — 행사 테마는 런타임 파생이라 도구 색 체계와 섞지 않는다([[design]] 색 분리 원칙). **BE 의존 없음.**
**왜** — 토큰은 CSS 변수로 체계화됐지만 컴포넌트 층이 없어서, 같은 카드·배지·버튼이 화면마다 인라인 스타일로 복제돼 있다. 다크모드 배지 갭이 정확히 이 구조의 비용이다 — 스타일이 한 곳에 있었다면 페어 하나 추가로 끝났을 일이 전 화면 수색이 됐다. FE 담당자와의 협업에서도 "어떤 색·컴포넌트를 쓰면 되는가"의 정본이 없으면 회신 왕복이 생긴다. README가 이미 인라인 스타일을 트레이드오프로 명시하고 정리 방향을 예고한 상태다.
**완료 기준** — [[design]]에 토큰 표(라이트/다크 전체)와 컴포넌트 목록·사용 규칙이 실림. `components/ui/`의 컴포넌트로 셸 4개 화면의 해당 패턴이 교체되고 시각 회귀 없음(교체 전후 스크린샷 대조). 상태 배지가 다크모드에서 튀지 않음. lint·build 통과.

### FE-14. FSD(Feature-Sliced Design) 아키텍처 적용
**무엇** — 평평한 `components/` + `lib/` 구조를 FSD 레이어(`app`/`pages`/`widgets`/`features`/`entities`/`shared`)로 재편한다. 먼저 **레이어 매핑 ADR**을 쓰고 나서 옮긴다 — 대략의 방향은: `lib/ui.ts`·`globals.css` 토큰·공용 컴포넌트(FE-13 산출물)→`shared/`, 이벤트·세션·테마 타입과 데이터 접근→`entities/`, Q&A·설문·테마 편집 같은 사용자 행동 단위→`features/`, 셸 화면 4개→`widgets/`+`pages/`. **주의**: Next.js App Router의 `app/` 디렉터리와 FSD의 `app` 레이어 이름 충돌, 그리고 `Microsite`(에디터 프리뷰와 참가자 뷰어가 같은 컴포넌트를 공유하는 이 프로젝트의 핵심 설계)가 어느 슬라이스에 속하는지를 ADR에서 반드시 결정한다. 이동은 **한 번에 전부가 아니라 레이어 단위로** 진행하고 각 단계마다 build를 통과시킨다. FE-2(라우트 분리)·FE-13(공용 컴포넌트)과 같은 파일을 건드리므로, **착수 시점에 그 둘이 진행 중이면 완료를 기다리거나 흡수 범위를 명시**한다. **BE 의존 없음.**
**왜** — 화면이 4개일 때는 평평한 구조가 싸지만, 열린 과제들(Q&A 연결, 설문 재설계, PDF 뷰어, 오프라인 대응)이 전부 "화면 조각 + 상태 + API 호출"을 한 덩어리씩 추가하는 성격이라 지금 구조로는 `components/`와 `lib/`이 기능 경계 없이 섞이며 자란다. FE 담당자와의 분업에서도 "이 기능은 이 폴더"라는 소유 경계가 있어야 충돌 없이 병렬 작업이 된다. 레이어의 단방향 의존 규칙은 프리뷰=실물 같은 구조적 보장을 지키는 데도 유리하다.
**완료 기준** — 레이어 매핑 ADR(`Decisions/`)이 있고 실제 구조가 그와 일치. import 방향이 FSD 규칙(상위→하위만)을 지키는지 eslint 규칙(예: `import/no-restricted-paths` 또는 steiger)으로 강제되고 위반 0건. 기존 화면 동작·시각 회귀 없음(스크린샷 대조). lint·build 통과.

## 열린 과제 — 백엔드(BE)

### BE-2. Cloudflare 배포 — 살아있는 링크 확보
**무엇** — `@opennextjs/cloudflare` 어댑터로 Workers/Pages 배포, D1·R2 바인딩, GitHub 연동 자동 배포.
**왜** — **링크 없는 완벽한 계획보다 링크 있는 절반이 낫다.** 포트폴리오에서 가장 먼저 읽히는 요소가 살아있는 URL이고, 이후 기능은 여기에 증분 배포하면 된다.
**완료 기준** — 공개 URL에서 앱이 뜨고 D1·R2 바인딩이 동작. push → 자동 배포. **결제 수단 미등록 상태 확인**(카드가 있으면 봇 트래픽에 청구서가 날아온다). 딥링크 확인은 FE-2 소관.
**진행** — 배포 완료: https://sympo-studio.fomula91.workers.dev (`/`·`/intro`·`/api/events` 200, D1 쓰기 왕복 실측, [[log]] 2026-08-24). R2 바인딩은 BE-6으로 이관. 남은 것: ① GitHub push→자동 배포(Workers Builds 연결) ② 결제 수단 미등록 확인 — 둘 다 대시보드 작업.

### BE-4. 설문 응답 수집 + 집계
**무엇** — 2단 설문 응답 저장과 `GROUP BY` 집계 엔드포인트.
**왜** — BE-3과 구조가 거의 같아 코드가 재사용된다. 설문 응답률은 리포트의 핵심 지표라 BE-5의 입력이기도 하다.
**완료 기준** — 응답이 저장되고 집계 수치가 조회됨. 남용 통제는 BE-3과 동일 정책 적용.

### BE-5. 이벤트 로그 적재 + OPS 집계
**무엇** — 세션별 열람·자료 열람·설문 완료를 이벤트 로그로 적재하고 집계 엔드포인트를 제공한다.
**왜** — BE-3·4에서 데이터가 쌓여야 의미가 생기므로 순서상 여기다.
**완료 기준** — 실제 방문 데이터가 적재되고 집계로 조회됨. **이벤트 로그 30일 보존 후 삭제 Cron 등록**(방치하면 무한 증가한다).

### BE-6. R2 자료 저장 + 업로드 + 서명 URL
**무엇** — 강의자료를 R2에 두고 서명 URL로 내준다. **업로드 엔드포인트도 여기 포함** — 행사 진행 중 현장에서 올리는 경로다(FE-6). 서버는 URL 발급과 저장만 하고 렌더링·변환에는 관여하지 않는다.
**왜** — 서버 PDF 파싱은 무료 티어에서 막히므로 "저장·조회는 서버, 렌더링은 클라이언트" 원칙을 그대로 적용한다([[0002-cloudflare-free-tier-stack]]). R2는 이그레스가 무료라 전송량 계산이 불필요하다.
**완료 기준** — 서명 URL로 PDF를 받을 수 있고 만료가 동작. **서버 CPU 사용 0**(파싱·변환 없음).

### BE-7. 참가자 화면용 공개 조회 API (slug 기반)
**무엇** — 참가자 마이크로사이트가 쓸 공개 읽기 엔드포인트. `GET /api/public/[slug]` 하나로 이벤트 + 아젠다 + 자료 목록(`pending`="준비 중" 포함) + 테마 + engage 토글을 돌려준다. **공개 가능한 상태(공개예정·진행중·완료)만 노출**하고 초안·검수대기·보관은 404 — 존재 여부도 흘리지 않는다. 관리자 전용 필드(전체 목록·상태 필터 등)는 제외. Q&A·설문은 BE-3/4 엔드포인트를 재사용하되, 이 응답에 이벤트 id를 실어 slug→id 재해석 없이 붙을 수 있게 한다. **의존은 BE-1뿐** — 번호는 7이지만 BE-4~6과 독립이라 BE-3 다음에 바로 착수해도 된다. FE-2(라우트 분리)의 `/[slug]` 화면과 FE-3이 이 API의 소비자다.
**왜** — FE-2가 참가자 화면을 `/[slug]` 라우트로 분리하는 순간 데이터를 받아올 곳이 없다. 지금의 `/api/events`는 운영자 콘솔용 CRUD라 id 기반이고 초안까지 다 보인다. 참가자는 **회차별 고유 slug로 접근**하는 것이 이 제품의 핵심 제약(공유 캐시 오염 방지, [[0005-d1-schema]])이므로, 공개 API의 키도 slug여야 한다.
**완료 기준** — slug 하나로 참가자 화면 렌더에 필요한 전부가 단일 응답으로 옴(뷰어/`Microsite`가 실제로 그려지는지로 확인). 비공개 상태 404. 폴링 대상이므로 rate limit 정책 판단을 함께 기록(읽기 전용이라 BE-3보다 완화한다면 그 근거).
**진행** — 구현·로컬 실측 완료([[log]] 2026-08-26): `GET /api/public/[slug]` 단일 응답(이벤트+아젠다+자료+테마+engage, 이벤트 id 포함), 공개 상태 3종만 노출하고 초안·없는 slug 모두 동일한 404(존재 비노출), `r2_key`는 경계 밖. rate limit 정책 기록: D1 판정형 읽기 제한은 역효과라 미적용, `Cache-Control: public, max-age=10`으로 흡수(근거는 라우트 주석) — D1을 안 거치는 통제는 BE-8에서 판단. 배포 후 프로덕션 실측 완료(2026-08-26): 공개 slug 200+캐시 헤더, 초안 전환 시 404, 없는 slug 404. 남은 것: `Microsite` 실제 렌더 확인(FE-2/FE-3 연결 시).

### BE-8. Q&A 폴링 GET 남용 통제 (읽기 쪽)
**무엇** — `GET /api/events/[id]/questions`에 읽기 쪽 통제를 넣는다: ① `Cache-Control`/ETag로 3~5초 폴링의 반복 응답을 재사용, ② `since`(keyset) 커서로 응답을 증분으로 축소, ③ 이벤트 존재 확인과 질문 SELECT를 `batch`로 묶어 요청당 D1 왕복 1회, ④ POST도 `clientHash`(순수 연산)를 먼저 계산하고 rate limit 카운트를 이벤트 조회와 batch — 무효 POST가 통제 없이 읽기만 소모하는 비용을 줄인다. **BE-7의 공개 조회 rate limit 정책 판단과 함께 정한다.**
**왜** — 코드리뷰(2026-08-25)에서 확인: 현재 남용 통제는 POST에만 있고, BE-3의 존재 이유였던 "폴링이 무료 티어를 소진" 시나리오가 GET에 그대로 열려 있다. curl 루프 10 req/s(또는 참가자 ~100명의 3초 폴링)면 D1 일일 읽기 한도가 1시간 내에 소진되고 이후 모든 D1 라우트가 그날 내내 500이다.
**완료 기준** — 폴링 루프 실측으로 요청당 D1 읽기 횟수와 캐시 적중이 확인됨. 무효 POST 플러드가 요청당 최대 1회 읽기로 제한됨.

### BE-10. 질문 숨김(모더레이션) 경로
**무엇** — `questions.status`를 `hidden`으로 바꾸는 운영자 엔드포인트를 만들고, `engage_qa=0`일 때 GET 피드를 계속 서빙할지 정책을 정해 반영한다.
**왜** — 코드리뷰(2026-08-25)에서 확인: 스키마와 주석은 `status='hidden'` 숨김 처리를 전제하는데 그것을 수행하는 코드가 어디에도 없다. 부적절한 질문이 올라오면 제거 경로가 이벤트 전체 삭제(CASCADE) 또는 자정 리셋 대기뿐이고, Q&A 토글을 꺼도 GET은 계속 서빙된다.
**완료 기준** — 숨김 처리한 질문이 폴링 피드에서 즉시 사라짐. `engage_qa` off 시 GET 동작이 정책으로 문서화되고 구현과 일치.

### BE-11. 2차 코드리뷰 지적 10건 반영
**무엇** — 2차 코드리뷰(2026-08-25, 후보 12건 전건 CONFIRMED, 상위 10건 채택)의 지적을 반영한다: ① POST 본문 JSON `null`이 500으로 터짐 → 객체 검사, ② `createdAt`이 존 표기 없는 UTC 문자열이라 클라이언트에서 9시간 어긋남 → ISO-8601+`Z`, ③ 시드 리셋마다 세션 id가 +6씩 밀려(AUTOINCREMENT) `SESSIONS0`의 id 1~6과 어긋남 → 시드에서 id 고정, ④ 일일 캡 쿼리에 날짜 조건 없음(해시 소금에만 의존) → KST 하루 시작 조건 추가, ⑤ 자정 리셋과 경합하는 POST의 FK 위반 500 → 404, ⑥ `ORDER BY id DESC`가 인덱스를 못 타 전체 행 임시 정렬(EXPLAIN 실측) → `created_at DESC` + JS 동점 안정화, ⑦ 워커 엔트리가 `fetch`만 골라 담아 산출물 드리프트에 취약 → `...handler` 스프레드, ⑧ 에러→상태코드 try/catch 6중 복제 → `ApiError` 계층 + `withRoute` 래퍼로 공통화, ⑨ 시드가 `autoSlug` 파생값을 손 전사 → 파생으로 교체, ⑩ 핫 쿼리 `SELECT *`가 미사용 컬럼 3개(client_hash 포함) 전송 → 컬럼 명시.
**왜** — ①~⑤는 FE-3(Q&A 화면 연결)이 붙는 순간 실사용자가 밟는 결함이고, ⑥·⑩은 가장 바쁜 폴링 경로의 비용, ⑦~⑨는 다음 과제(BE-4~10)가 같은 패턴을 복제하기 전에 잡아야 하는 구조 문제다.
**완료 기준** — lint·build 통과. 배포 후 원격 재검증(BE-3의 원격 Cron 확인과 함께): 질문 저장·조회 왕복, 429 사유 노출, 리셋 후 세션 id 1~6 유지.
**진행** — 전 항목 구현 완료 + PR #8 머지 + 배포·원격 재검증 완료(2026-08-26, [[log]]): 403→(qa on)→201 왕복, `null` 본문 400, `createdAt` ISO(`…T…Z`), 60초 4건째 429 사유 노출 — 전부 프로덕션 URL 실측. 남은 것: 첫 자정 리셋(00:00 KST) 후 시드 세션 id가 1~6으로 유지되는지 확인.
