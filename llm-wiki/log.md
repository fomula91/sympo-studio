[[0007-sso-and-account-model]] 신설 + ADR 0001 결정 1번에 개정 주석(폐기 아님 — "채용담당자는 가입하지 않는다"는 유지되고, 가입이 강제가 아닌 선택지가 됐을 뿐), [[index]] 링크, Next-Tasks에 BE-12(인증 기반)·BE-13(인가 경계 적용, 참가자 경로 무인증 유지가 완료 기준)·FE-15(로그인·계정 화면 + 게스트 모드 명시) 등록, 착수 가이드 현행화. **코드 변경 없음 — 설계·문서까지.**
- **[PROJ] ADR 0007 보정 — 게스트 편집을 localStorage에 영속시키는 로컬 워크스페이스로**: 초안이 게스트 모드를 "서버에 저장하지 않는 로컬 편집"까지만 적어 **편집이 휘발되는 것처럼 읽혔고**, 사용자가 "확인은 해야 되니까 로컬에 저장했으면 좋겠다"고 정정 — 만져본 결과를 확인할 수 없으면 체험 자체가 성립하지 않는다. 세 가지를 결정에 반영: ① 게스트는 `localStorage`에 **영속하는 워크스페이스**를 갖고 새로고침·재방문에도 유지되며 이벤트 생성·삭제까지 로컬에서 완결한다. ② **서버 데모 이벤트 id를 참조하는 오버레이 방식은 명시적으로 기각** — 매일 자정 Cron이 데모를 리셋할 때 로컬 편집분의 기준이 사라져 조용히 깨진다. 대신 클라이언트 시드로 초기화하는 독립 워크스페이스. 서버 데모 이벤트(`owner_id IS NULL`)는 없어지지 않고 역할이 갈린다 — 운영자 도구 체험은 로컬, 참가자 참여(Q&A·설문이 실제 저장되는 증명)는 서버. ③ **로그인 시 가져오기**(0007 §1-1 신설) — 로컬 편집분이 있으면 "계정으로 가져올까요?"를 묻고 수락 시 순차 생성 후 로컬 제거(남기면 재로그인 때 중복 생성), 거절 시 보존. 묻지 않고 버리면 **로그인이 잃는 행동**이 되어 다시는 로그인하지 않는다는 것이 근거. 결과적으로 0001이 기각했던 A안(정적 + localStorage)이 폐기되지 않고 게스트 모드로 살아남는 구조. 파생 트레이드오프 3건 기록: 로컬 데이터는 그 브라우저에만 존재(사파리 7일 스토리지 만료 포함 — 문구로 드러내 로그인의 이유가 되게), `localStorage` 5MB 한계에 FE-8의 `key_visual` base64가 닿을 수 있음(이미지 제외·참조·IndexedDB 중 선택을 FE-15 완료 기준에 포함), 가져오기가 대량 쓰기 경로가 되므로 **지금 전혀 없는 운영자 쓰기 rate limit을 BE-13에 추가**(키가 IP·토큰이 아닌 user_id라는 점만 다르고 `lib/rate-limit.ts` 재사용) + 계정당 이벤트 수 상한 판단. FE-15를 6개 항목으로 재작성하고 ①③은 BE 의존 없음·②④⑤는 BE-12·13 의존으로 갈랐으며, PR #9(FE-1 상태 분리)가 워크스페이스의 상태 층이라 머지 후 착수 조건을 명시.
- **[PROJ] 가져오기 프로세스 구체화 (0007 §1-1) + BE-14·BE-15 등록 — 아젠다 쓰기 API 부재 발견**: 사용자가 "로그인하면 게스트 데이터를 가져오는 프로세스"를 요청(직전 수정에 의도는 이미 들어가 있었으나 "묻고→순차 생성→로컬 제거" 수준이라 구현 명세가 없었다). 구체화하려 API를 확인하다 **전제가 깨져 있는 것을 발견**: `POST /api/events`는 이벤트 헤더 필드만 받고, 테마는 `PATCH`로만 들어가며, **아젠다(`sessions`)를 쓰는 라우트가 아예 없다**(`app/api/events/[id]/`에 `questions`·`survey`뿐). 이벤트 껍데기만 가져오면 게스트가 짠 아젠다가 버려져 "로그인은 잃는 행동이 아니다"라는 취지 자체가 무너진다. 이 결손은 가져오기만의 문제가 아니라 **FE-1(이벤트별 편집 상태 분리)이 붙는 순간 "에디터에서 아젠다를 고쳤는데 서버에 안 남는다"로 드러날 구멍** — GET·시드로 읽히기만 해서 지금까지 안 보였을 뿐이다. **BE-14**(아젠다·자료 쓰기 API, 번호는 14지만 BE-12·13과 독립 / 순서 변경을 요청 1회로 / PR #12 리뷰가 재현한 세션 삭제 시 `FK SET NULL` × `idx_survey_once` UNIQUE 위반을 여기서 함께 해결)와 **BE-15**(`POST /api/events/import`)를 등록. 가져오기 설계 4가지를 확정: ① 이벤트+테마+아젠다를 **묶어 받아 이벤트 단위 D1 `batch` 1회** — 개별 POST/PATCH 반복은 왕복이 수십 회로 늘고 중간에 끊기면 테마 없는 이벤트 같은 **반쪽 상태**가 서버에 남는다. ② **멱등성** — 로컬 워크스페이스가 생성 시점에 부여하는 `localRef`(UUID)를 `events.client_ref` + `UNIQUE(owner_id, client_ref)`로 받아, 네트워크가 끊겨 다시 누르는 것을 정상 경로로 취급. ③ **원자성 단위는 이벤트 하나** — A 성공·B 실패면 A는 커밋된 채 두고 건별 결과 배열 반환, 로컬 제거는 성공분만(전체 롤백은 "9개 성공했는데 10번째 때문에 처음부터"가 되어 더 나쁘다). ④ `ensureUniqueSlug`로 **slug가 바뀐 항목을 응답에 실어** 조용히 바꾸지 않는다. FE-15 ④를 이 계약에 맞춰 정정하고 의존을 다시 갈랐다(①③ BE 의존 없음 / ②⑤ BE-12·13 / ④ BE-15). **코드 변경 없음 — 설계·문서까지.**

- **[PROJ] GitHub → Discord 웹훅 연동 절차 정리**: 푸시·PR 알림을 Discord 채널에서 받기 위한 설정 절차를 확정. 방식은 **Discord 채널 웹훅 + `/github` 접미사** — Discord 채널 설정 → 연동 → 새 웹후크로 URL을 발급받고, 그 URL 끝에 `/github`를 붙여 GitHub 리포 Settings → Webhooks의 Payload URL로 등록한다. 이 접미사가 GitHub의 push/PR JSON을 Discord가 임베드로 렌더링하게 하는 스위치이며, 빠뜨리면 Discord가 일반 메시지 payload로 해석해 400대 오류를 반환한다(구체 코드는 미검증). 함께 걸리는 함정 둘: **Content type을 `application/json`으로 바꿔야 한다**(GitHub 기본값 `x-www-form-urlencoded`면 실패), **Secret은 비워둔다**(Discord는 GitHub의 `X-Hub-Signature` 검증을 지원하지 않아 넣어도 무의미). 이벤트는 `Send me everything` 대신 개별 선택(Pushes·Pull requests·Issues·Releases, 배포 붙인 뒤엔 Deployment statuses) — 렌더링 못 하는 타입이 섞이면 조용한 실패가 쌓이고 채널도 시끄럽다. 검증은 Recent Deliveries의 응답이 `204`인지로 보되, 등록 직후 오는 `ping`은 Discord가 렌더링하지 않아 채널에 안 뜨므로 **실제 push로 확인**해야 한다. 대안인 Discord GitHub 앱(`/github subscribe`)은 채널별 구독 관리가 편하지만 서버에 봇 추가 + 리포 권한 부여가 필요해 리포 1개에는 과하다고 판단해 채택하지 않음. **repo 코드 변경 없음**이며, 웹훅 URL은 아는 사람이면 누구나 그 채널에 글을 쓸 수 있는 비밀값이라 위키·코드 어디에도 기록하지 않는다(유출 시 Discord에서 웹훅 삭제 후 재발급). 실제 등록·배달 확인은 GitHub·Discord 콘솔에서 수행하는 작업이라 이 로그로는 검증되지 않는다.
