## 2026-09-16
- **[BE] BE-31 — 업로드 한도를 예약(admission)으로 바꿨다. 착수는 측정으로 시작했고, 그 측정이 과제 문서보다 나쁜 수치를 냈다**: 과제는 "동시 요청이 카운터를 0으로 읽고 전부 통과한다"고만 적혀 있었는데, 실제로 재보니 **같은 토큰으로 20MB 16개를 동시에 시작했을 때 15건이 통과해 300MB가 들어갔다**(정책은 5분 200MB). 그마저도 rate limit이 멈춘 게 아니라 **이벤트 총량 300MB**가 16번째를 400으로 막은 것이었다 — 즉 업로드 rate limit은 그 시나리오에서 **천장 역할을 전혀 못 하고 있었다.** 설계는 후보 둘 중 ①(조건부 upsert)을 골랐다. 다만 **과제가 적어둔 형태 그대로는 쓰지 않았다**: 버킷(토큰 창·일, IP 창·일) 넷에 조건부 upsert를 따로 보내면 일부만 통과해 **보상 쓰기**가 생기고, 플러드에서 그게 요청마다 반복되면 거절된 요청이 D1 쓰기를 태운다 — [[0008-rate-limit-counter]]가 *"무효 요청이 쓰기 티어를 태우면 Q&A·설문·로그가 전부 죽는다"*며 명시적으로 기각한 바로 그 구조다. 그래서 **게이트를 SELECT의 WHERE 한 곳에 모으고 버킷 행들을 그 SELECT가 만들게 했다** — 조건이 거짓이면 0행이라 어떤 버킷도 오르지 않는다. **SQL 의미를 추측하지 않고 로컬 D1에 걸어 넷을 쟀다**: ① 거절 시 `changes=0`·네 버킷 값 불변 ② 통과 시 `changes=4`·각 버킷 정확히 cost — **자기 관찰이 없다**(SQLite가 대상 테이블을 읽는 `INSERT…SELECT`를 먼저 물질화한다). 되읽었다면 첫 행이 오른 뒤 조건이 거짓이 돼 나머지가 누락됐을 것이라 `195+5<=200`이라는 **경계를 일부러 만들어 갈랐다** ③ upsert에서 `RETURNING`이 동작해 실제로 오른 버킷을 돌려준다 ④ **거절 12건 뒤 카운터가 1도 안 움직였다.** ②는 엔진 구현 세부라 **거기 기대지 않는다** — `RETURNING`이 돌려준 버킷이 전부가 아니면 오른 것만 정확히 되돌리고 거절하므로, 물질화가 달라져도 카운터가 어긋난 채 남지 않는다. 되돌리는 기준은 **R2 `put`이 실제로 일어났는가** 하나다(put이 던지면 되돌리고, put 뒤의 실패는 안 되돌린다 — Class A 연산은 이미 썼고 이 정책이 지키는 게 그것이다). 거절 사유 문구는 게이트가 알려주지 않아 **거절 경로에서만 읽기 1회**를 더 써서 고른다(0008이 피하려던 건 쓰기지 읽기가 아니다). **수정 후 재측정: 10건 통과·6건 429·카운터 정확히 200·저장 200MB**, 정상 현장 시나리오(4MB×5 연속)는 안 막힘. **다른 정책은 건드리지 않았다** — 질문·설문·로그·이벤트 생성이 지키는 건 D1 행이고 쓰기 술어가 이미 천장이다. `lint`·`test`(77건, 예약 6건 신설)·`build` 통과.
- **[PROJ] ADR 0011 신설 + BE-15 종료 누락 정리**: [[0011-upload-admission]]에 0008의 "성공한 쓰기에만 증가"를 **업로드에 한해** 개정한 근거와 실측 4건, 감수하는 것(사전 판정이 최적화로 남는다·워커가 죽으면 예약이 창 만료까지 남는다·분 단위 근사는 그대로다)을 남겼다. 그리고 **BE-15가 [[Archive/Closed-Tasks]]와 열린 과제 양쪽에 있었다** — 종료 처리하며 `Next-Tasks`에서 빼는 걸 빠뜨린 것이라, 끝난 과제가 세션 시작 훅에 계속 주입되고 있었다. 지웠다.

BE-29에서 이벤트 총량에 쓴 것과 같은 수법이다. **남긴 한계 하나**: 같은 사용자가 가져오기를 동시에 두 번 보내면 두 번째가 첫 번째가 방금 차지한 slug를 모른 채 같은 후보를 배정해 그 이벤트가 `failed`가 된다. **중복은 안 생기고 그대로 다시 보내면 성공한다**(`client_ref` 멱등성 + 새 스냅샷). 한 브라우저에서 로그인 한 번에 한 번 도는 경로라 자동 재시도를 넣는 대신 라우트 주석에 적어 뒀다 — 실제로 이 경합을 재현해 확인했다. 부수로 Codex 하드닝 하나: 토큰이 없을 때 `''` 대신 **NULL을 바인딩**한다(`s.id = NULL`은 어떤 행과도 같지 않아, 실수로 빈 id 행이 생겨도 뚫리지 않는다). Codex가 확인해 준 것: `sessionUserIdSql()`의 자리번호 전부 정확, 만료 세션 차단 동작, `users`를 참조하는 FK가 정확히 넷이고 모두 대피 대상, 프리셋 UPSERT의 `NULL = excluded.owner_id`가 내장 수정을 실제로 막음, `last_insert_rowid()`가 D1 batch에서 안전함. 최종 확인은 **종료 코드로**: `lint 0` · `test 0`(71건) · `build 0`.

END`). 그냥 덮어썼다면 표시용 값 하나 때문에 **이미 링크된 사람의 로그인이 UNIQUE 위반으로 실패**했을 것이다 — 로컬 D1에서 충돌/비충돌 두 경우를 실제로 돌려 확인했다. ② **신규 생성을 `batch` 하나로.** `SELECT`→`INSERT users`→`INSERT oauth_accounts`가 따로 돌아 중간 실패 시 oauth 링크 없는 고아 `users` 행이 남았고, **그 행이 다음 로그인에서 다시 ①의 이메일 매칭을 불렀다** — 비원자성이 ①을 스스로 재생산하는 구조였다. batch는 바인딩이 먼저 끝나 첫 문의 `RETURNING id`를 둘째 문에 못 넣으므로 둘째 문이 `VALUES ((SELECT id FROM users WHERE email = ?), …)`로 방금 넣은 행을 집는다(바로 앞에서 충돌 없음을 확인했고 `email`이 UNIQUE라 한 행만 가리킨다). `last_insert_rowid()`는 **D1 batch가 문 사이에 그 값을 보존한다는 보장을 문서로 확인할 수 없어** 쓰지 않았다. ③ 콜백 `catch`가 `ApiError`만 접어 그 밖의 예외가 **500 스택 페이지**로 새던 것을 전부 접도록 바꿨다(`console.error`로 남기고 응답엔 안 실림). ④ **`?error=` 분기를 state 대조 뒤로 옮겼다** — `fail()`이 state·redirect 쿠키를 만료시키는데 이 분기가 대조보다 먼저 돌아, 공격자가 피해자 브라우저를 `/api/auth/callback/google?error=x`로 보내기만 하면(이미지 태그 한 줄) **진행 중이던 정상 로그인이 'state 쿠키 없음'으로 실패**했다. `matchOAuthState()`를 신설해 판정을 맨 앞에 두고, 통과 전 실패는 **쿠키를 건드리지 않는** `ignore()`로 갈랐다(OAuth 2.0은 오류 응답에도 state를 실으므로 정상 취소는 그대로 `cancelled`로 접힌다). **실측**: 로컬 D1에 batch 2문을 실제로 실행해 ㉮ 서브쿼리가 방금 삽입한 id로 해석되는 것, ㉯ 둘째 문이 UNIQUE로 실패하면 **첫 문까지 롤백돼 고아 행이 0건**인 것을 확인했다(`SELECT … WHERE email LIKE 'be26-%'` 조회 후 프로브 행 정리). `lib/auth.test.ts` 신설 7건 — 이메일 연결 금지·거절 시 INSERT 0건·두 INSERT가 같은 batch·`matchOAuthState` 경계. `npm run lint`·`test`(28건)·`build` 통과. **미실측**: 실제 Google 왕복(취소·`?error=` 주입·이메일 충돌 로그인)은 배포 후 확인이 남았다.

Domain=evil.example`은 **쿠키 속성 주입**이 됐다(실측). `serializeCookie`에 `encodeURIComponent`, `readCookie`에 짝이 되는 디코딩을 넣었다. 콜백이 쿠키 값을 재검증 없이 `Location`으로 쓰던 것도 `safeNextPath`를 한 번 더 태우게 했다 — 쿠키를 쓸 수 있는 경로가 생기면 ①이 그대로 다시 열린다. **④ 시드의 고정 id 재삽입이 시한폭탄이었다** — 예전엔 `DELETE FROM events`가 테이블을 비워 `VALUES (1, ...)`가 항상 성공했는데, 이번 PR이 삭제를 `owner_id IS NULL`로 한정하면서 그 보장이 사라졌다. 새 DB에서 첫 이벤트를 로그인 사용자가 만들면 id 1을 차지하고, 삭제는 건너뛰고, 재삽입이 `UNIQUE constraint failed: events.id`로 터진다(실측). **batch가 원자적이라 리셋 전체가 롤백되고, worker가 이어서 부르는 R2 고아 정리 — 그 주석이 스스로 "유일한 상한"이라 부르는 것 — 까지 영영 멈춘다.** 증상이 "리셋이 안 된다"가 아니라 "R2가 계속 찬다"로 나타나는 종류다. 데모 이벤트를 **지웠다 다시 만들지 않고 slug로 찾아 제자리에서 UPDATE**하도록 재작성했고(지웠다 만들면 AUTOINCREMENT가 매일 새 id를 준다), 세션 id 고정도 없앤 뒤 `RETURNING id`로 받아 설문·로그가 그 값을 쓰게 했다. **⑤ 소유권을 가드보다 먼저 배포할 뻔했다** — `owner_id`를 채우기 시작했는데 `PATCH`/`DELETE`에 검사가 없었다. 이 PR 전에는 모든 이벤트가 매일 밤 지워져 무보호의 대가가 최대 하루치였지만, 이제 로그인 사용자 이벤트는 영속하므로 **일시적 구멍이 영구적 데이터 손실로 넓어진다.** BE-13의 범위지만 `assertCanEdit`를 앞당겼다 — 소유자가 없는 데모 이벤트는 지금처럼 열어 두고(게스트 체험이 여기 기댄다), 소유자가 있으면 세션이 일치해야 하며 불일치는 **403이 아니라 404**다(BE-7과 같은 규칙). 실측: 비로그인 PATCH·DELETE → 404이고 제목이 안 바뀜, 데모 PATCH → 200(회귀 없음), 브라우저에서 소유자 PATCH → 200. **⑧ 시드 테스트의 항진명제도 고쳤다** — 두 번째 단언이 첫 단언 뒤에는 절대 매치될 수 없는 형태였다. `owner_id IS NULL` 한정과 **고정 id 재삽입 금지**(④의 회귀 가드)를 검사하도록 다시 썼고, 가짜 D1이 SQL 문자열만 본다는 한계를 파일 주석에 명시했다. 남긴 것: ③(`email_verified` 미검사 + upsert 비원자성)과 ⑥(콜백 catch가 `ApiError`만 접음)은 BE-13에서 인가 경계를 손댈 때 함께. `npm run lint`·`test`(23건)·`build` 통과.
