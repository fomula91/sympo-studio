Domain=evil.example`은 **쿠키 속성 주입**이 됐다(실측). `serializeCookie`에 `encodeURIComponent`, `readCookie`에 짝이 되는 디코딩을 넣었다. 콜백이 쿠키 값을 재검증 없이 `Location`으로 쓰던 것도 `safeNextPath`를 한 번 더 태우게 했다 — 쿠키를 쓸 수 있는 경로가 생기면 ①이 그대로 다시 열린다. **④ 시드의 고정 id 재삽입이 시한폭탄이었다** — 예전엔 `DELETE FROM events`가 테이블을 비워 `VALUES (1, ...)`가 항상 성공했는데, 이번 PR이 삭제를 `owner_id IS NULL`로 한정하면서 그 보장이 사라졌다. 새 DB에서 첫 이벤트를 로그인 사용자가 만들면 id 1을 차지하고, 삭제는 건너뛰고, 재삽입이 `UNIQUE constraint failed: events.id`로 터진다(실측). **batch가 원자적이라 리셋 전체가 롤백되고, worker가 이어서 부르는 R2 고아 정리 — 그 주석이 스스로 "유일한 상한"이라 부르는 것 — 까지 영영 멈춘다.** 증상이 "리셋이 안 된다"가 아니라 "R2가 계속 찬다"로 나타나는 종류다. 데모 이벤트를 **지웠다 다시 만들지 않고 slug로 찾아 제자리에서 UPDATE**하도록 재작성했고(지웠다 만들면 AUTOINCREMENT가 매일 새 id를 준다), 세션 id 고정도 없앤 뒤 `RETURNING id`로 받아 설문·로그가 그 값을 쓰게 했다. **⑤ 소유권을 가드보다 먼저 배포할 뻔했다** — `owner_id`를 채우기 시작했는데 `PATCH`/`DELETE`에 검사가 없었다. 이 PR 전에는 모든 이벤트가 매일 밤 지워져 무보호의 대가가 최대 하루치였지만, 이제 로그인 사용자 이벤트는 영속하므로 **일시적 구멍이 영구적 데이터 손실로 넓어진다.** BE-13의 범위지만 `assertCanEdit`를 앞당겼다 — 소유자가 없는 데모 이벤트는 지금처럼 열어 두고(게스트 체험이 여기 기댄다), 소유자가 있으면 세션이 일치해야 하며 불일치는 **403이 아니라 404**다(BE-7과 같은 규칙). 실측: 비로그인 PATCH·DELETE → 404이고 제목이 안 바뀜, 데모 PATCH → 200(회귀 없음), 브라우저에서 소유자 PATCH → 200. **⑧ 시드 테스트의 항진명제도 고쳤다** — 두 번째 단언이 첫 단언 뒤에는 절대 매치될 수 없는 형태였다. `owner_id IS NULL` 한정과 **고정 id 재삽입 금지**(④의 회귀 가드)를 검사하도록 다시 썼고, 가짜 D1이 SQL 문자열만 본다는 한계를 파일 주석에 명시했다. 남긴 것: ③(`email_verified` 미검사 + upsert 비원자성)과 ⑥(콜백 catch가 `ApiError`만 접음)은 BE-13에서 인가 경계를 손댈 때 함께. `npm run lint`·`test`(23건)·`build` 통과.
